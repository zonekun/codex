## 【パターン 4: 誤読・ミス原因分析】

### 事象

コンセンサスFY判定のバグ修正作業で以下を実施:

1. BQ VIEW `V_LATEST_DISCLOSURE` を新規作成（fin_summary から当期FYを導出）
2. `scripts/lib_conse_csv_from_view.py` を修正: `_fetch_latest_fy_end()` -> `_fetch_current_fy_map()`、フィルタ `fy > latest_fy` -> `fy >= current_fy`
3. `scripts/export_consensus_csv.py` を同様に修正

コード修正完了 -> 動作確認のフローで、「関連MDの更新」ステップを自発実行しなかった。ユーザーの指摘で初めてMD更新を実施。

### AIの思考回路（推定される判断チェーン）

1. バグ修正タスクの認知フレーム: 「FY判定バグを直す」-> コード修正 -> テスト -> 完了報告。この認知フレームに「MD更新」が含まれていなかった
2. VIEW新規作成はBQ操作であり、「スクリプト変更」の延長として処理された。新規BQリソース（VIEW）の作成がdata_catalog更新のトリガーとして認識されなかった
3. CLAUDE.md の「知見ファイル整合義務」の発火条件（「既存スクリプトの動作・出力・依存関係を変更した場合」「プランMDに記載された作業を実施・完了した場合」）は読み込まれていたはずだが、タスク完了時の認知リソースがコード修正の正確性検証に割かれ、MD整合チェックまで到達しなかった
4. MR-041（2026-04-30）で**まったく同じドメイン**（コンセンサス/022 MD）の同種事故が発生し、再発防止策が実施されていたにもかかわらず、その教訓が今回のタスクで想起されなかった

### 直接原因

CLAUDE.md §知見ファイル整合義務に明記された発火条件 3 つのうち 2 つに該当していたが、いずれもチェックされなかった:

| 発火条件 | 該当状況 | チェック実施 |
|---------|---------|------------|
| `scripts/` 配下のスクリプトの動作・引数・出力を変更した commit 前 | `lib_conse_csv_from_view.py` / `export_consensus_csv.py` の関数名・フィルタ条件を変更 | **未実施** |
| `gcloud deploy/create/update/delete` 完了直後 | BQ VIEW `V_LATEST_DISCLOSURE` を CREATE VIEW で新規作成 | **未実施** |
| バックフィル等のマイルストーン完了時 | 該当しない | -- |

### 根本原因

**意志依存型の再発防止策が4度連続で機能していない。**

| 事故 | 日付 | ドメイン | 対策の性質 |
|------|------|---------|----------|
| MR-041 | 2026-04-30 | コンセンサス/022 MD | CLAUDE.md にルール追加（意志依存） |
| MR-054 | 2026-05-01 | バックフィル/プランMD | memory feedback 追加（意志依存） |
| MR-060 | 2026-05-02 | Scheduler/013 MD | 発火条件の明確化（意志依存） |
| **今回** | **2026-05-12** | **コンセンサス/022 MD** | -- |

4件すべての再発防止策は「ルールの記載」「memory の追加」「発火条件の明確化」であり、いずれも **AIが自発的に想起・参照することを前提とした意志依存型**。タスク完了時の認知負荷が高い状況では想起されないことが4回の実績で実証された。

### MD上の原因

CLAUDE.md §知見ファイル整合義務のルール自体は十分に明確で、発火条件も3つ列挙されている。MD の表現・構成に問題はない。**問題はルールの存在ではなく、タスク完了フロー内でのチェックポイント強制の仕組みが欠如していること。**

### MD構成原因

CLAUDE.md → 知見MD の参照導線は機能している（高頻度参照テーブルにコンセンサス関連の項目あり）。ただし、これは「コンセンサスに関するタスクを受けたとき」に発火する導線であり、「コンセンサス関連コードを変更したとき」に発火する導線ではない。CLAUDE.md の知見ファイル整合義務は「変更後」のチェックであり、「変更前」に参照する高頻度参照テーブルとは発火タイミングが異なる。

### 再発防止の方向性

**5度目を防ぐには意志依存型からの脱却が必要。** 具体的な選択肢:

1. **hook / pre-commit チェック**: `scripts/` 配下のファイルが staged されている場合、対応する知見MDのパスを表示し、更新確認を促すメッセージを出力する。技術的には `PreToolUse` hook で `git commit` 前にチェック可能
2. **コミットメッセージテンプレート**: スクリプト変更を含むコミットのメッセージに `[MD更新: xxx.md]` または `[MD更新不要]` の明示を義務化。記載がない場合に警告
3. **タスク完了チェックリストの強制読み込み**: commit 前に 004_coding_conventions.md のチェックリストを強制参照させる仕組み

### 対策スコープ

本事故は「コンセンサス固有の問題」ではなく、「任意のスクリプト改修後のMD整合チェック漏れ」という汎用パターン。MR-041/054/060 が示す通り、ドメインを問わず発生する。対策はドメイン固有のfixではなく、仕組みレベル（hook/CI/テンプレート）で打つべき。

## 【重大な指摘】（即修正）

### #1 同一ドメインでの同一パターン再発（MR-041 -> 今回）

- **箇所**: CLAUDE.md 知見ファイル整合義務（system-reminder内の記述）、docs/reviews/041_md_update_after_code_change.md
- **問題**: MR-041 はコンセンサススクリプト改修後に 022 MD の更新を漏らした事故。今回もコンセンサスFY判定ロジック改修後に 022 MD + data_catalog 2 ファイルの更新を漏らした。ドメインまで一致する完全な再発
- **AIの誤読パターン**: ルール自体の理解は正しいが、タスク完了時の認知フローにルール確認ステップが組み込まれておらず、自発的な想起に依存している
- **トリガー**: スクリプト改修 -> テスト -> 完了報告のフロー。バグ修正の正確性検証に認知リソースが集中し、MD整合チェックが後回し（結果として未実施）になる
- **影響**: MD更新が遅延する間、次のセッション/AIが旧ロジック（`_fetch_latest_fy_end` / `fy > latest_fy`）を前提にコンセンサス関連の作業を行うリスク
- **根拠**: MR-041（2026-04-30）の再発防止として CLAUDE.md にルールが追加されたが、12日後の同一ドメインで同一パターンが再発
- **推奨対応**: [方向性] 意志依存型ルール追加では5度目を防げない。以下のいずれかの構造的強制を検討:
  - (A) `PreToolUse` hook で `git commit` 時に `scripts/` 配下ファイルの staged を検知 -> 「関連知見MD・data_catalog の更新確認は完了していますか？」をプロンプト表示

  - (C) スキル `code-reviewer` のレビュー項目に「関連MD整合チェック」を追加（レビュー時に漏れを検出）
- **MD修正だけで足りるか**: **いいえ**。4度の再発が示す通り、ルール記載だけでは防げない。構造的強制が必要
