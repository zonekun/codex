# 028: head -5 パイプによる意図しないCloud Run Job二重起動

**日時**: 2026-04-29 18:07 JST
**重大度**: Medium（データ損失なし、リソース浪費＋手動介入が必要だった）
**カテゴリ**: 運用ミス（破壊的操作の事前検証不足）

## 事象

2017-H2 バックフィル開始時、`monitor_backfill.py` の動作確認のため以下を実行:

```bash
PYTHONUTF8=1 python scripts/monitor_backfill.py config/backfill/2017_full_run2_h2.yaml 2>&1 | head -5
```

**意図**: スクリプトがYAML設定を正しくパースできるか、最初の数行の出力で確認したかった。

**実際の挙動**:
1. `monitor_backfill.py` が起動し、YAML パース → Cloud Run Job `tdnet-load-daily` を即座にサブミット（`tdnet-load-daily-gs44w`, 18:07:15 JST）
2. `head -5` がパイプを閉じ、Python プロセスに SIGPIPE → プロセス終了
3. しかし Cloud Run Job は既にサブミット済みで、GCP 上で実行継続
4. 直後に本番用として `run_in_background=true` で再実行 → 2つ目の Job をサブミット（`tdnet-load-daily-s5lsv`, 18:07:43 JST）
5. 同一日付範囲（20170701-20171231）の Load Job が2つ並走する状態に

**対処**: `gcloud run jobs executions cancel tdnet-load-daily-gs44w` で孤立ジョブを手動キャンセル。データ損失なし。

## 根本原因

1. **`head -5` パイプの特性を考慮しなかった**: `head -N` はN行読んだ後にパイプを閉じるが、書き込み側プロセスは SIGPIPE を受けるまで実行を続ける。副作用のあるスクリプトでは、出力前に副作用（Job サブミット）が完了している可能性がある
2. **「パース確認」に本番実行コマンドを使った**: `--dry-run` オプションの使用や、設定ファイルの読み込みだけを行う別コマンドを使うべきだった
3. **CLAUDE.md §破壊的操作の dry-run 先行ルールを適用しなかった**: Cloud Run Job のサブミットは「他者に見える変更」であり、破壊的操作に該当する

## 影響範囲

- Cloud Run Job 1実行分のリソース浪費（キャンセルまでの約5分間）
- 手動介入（キャンセルコマンド実行）が必要だった
- データ損失・データ不整合なし（キャンセルが間に合った）

## 再発防止策

### 判定基準
- **副作用のあるスクリプトの動作確認に `| head -N` を使ってはいけない**
- Cloud Run Job / Workflow / 外部API呼び出しを行うスクリプトは「破壊的操作」として扱う

### チェックリスト
1. スクリプトの動作確認には `--dry-run` を第一選択とする
2. `--dry-run` がない場合、設定ファイルのバリデーションだけを行う別手段を使う（例: `python -c "import yaml; yaml.safe_load(open(...))"`)
3. `| head -N` パイプは、副作用のない読み取り専用コマンド（`cat`, `grep`, `gcloud ... list`）にのみ使用する
4. 万が一二重起動した場合、即座に孤立実行をキャンセルする

## 関連ルール

- CLAUDE.md §破壊的操作は必ず dry-run 先行
- CLAUDE.md §「破壊的操作」の定義 → 「他者に見える変更」
