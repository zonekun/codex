## 【パターン 2/4: 原因分析】

### 1. 事象

fin_summary BQテーブルの5/12-17データ欠落をユーザーから報告され、AIが裏取りなしで「J-Quants APIの1-2日遅延が原因」と報告。実際は自コード（`_resolve_dates()` で DATE_MODE="t" が02:00実行時にtodayを返すバグ）が原因だった。

### 1.5. AIの思考回路（推定）

判断チェーン再構成:
1. 「fin_summaryに5/12-17のデータがない」→ データソースはJ-Quants API
2. 「J-Quants APIからデータが来ていない」→ **ここで分岐**: (A)自コードがAPIを正しく呼んでいるか確認 vs (B)API側に問題があるか確認
3. (B)を選択: 「金融データAPIには一般的に遅延がある」という**一般知識（=推測）**を根拠に「1-2日遅延」と報告
4. **§4.2 不発火**: 「データ欠落」を「外部データソースの問題」と即座にフレーミングし、「自コードの問題」というフレームを検討しなかった

**分岐(B)を選んだ推定理由**:
- 「APIのデータが欠落」→ 「APIの遅延」は因果として自然に見える（確認バイアス）
- 自コードを調べる手間（ソース読み→実行ログ確認→日付ロジック追跡）より、外部仕様の説明が認知的にコスト低い
- §4.2「自分を先に疑う」は知っているが、「データ欠落=取得側の問題」のフレーミングが先に成立したため§4.2の発火条件（「ユーザーが異常報告」→「自コードを先に検証」）を通過してしまった

### 2. 直接原因

- CLAUDE.md §4.1「事実確認が可能なことを確認せずに発言しない」の不遵守
- CLAUDE.md §4.2「外部要因より先に自分を疑う」の不遵守
- ルール自体は明確。ルールの認識ではなく**発火タイミング**の問題

### 3. 根本原因

**同型事故の反復構造**: MR-035(企業名推測)/MR-073(原因推測)/MR-119(列ズレ説捏造)/MR-142(曜日推測)に続く5件目以上の「確認可能な事実を推測で断定」事故。意志依存型の再発防止策（「次から確認する」）が繰り返し提案され、いずれも無効だった。

根本的には:
1. §4.1/§4.2 の発火は**AIの自発的判断**に完全依存しており、構造的強制が存在しない
2. 「データ欠落の原因調査」という特定タスクパターンで、外部帰責バイアスが発動しやすい

### 4-1. MD上の原因

CLAUDE.md §4.2 の記述:
> 異常報告を受けたら外部要因より先に自分を疑う: ユーザーが「動いていない」「おかしい」「壊れている」「アホ」「違う」等を報告したら、外部要因の前に**自分の直前の実行内容を知見MDの記載手順と照合**して自己検証する。

この記述は明確。しかし:
- **「自分の直前の実行内容」のスコープが曖昧**: 「今セッションで自分が書いたコード」なのか「プロジェクト内の自動実行スクリプト全般」なのか。本件では02:00のcron実行スクリプトであり、「直前の実行内容」には該当しないとAIが解釈した可能性がある
- **ただし**: 「動いていない」等のトリガーワードにデータ欠落報告は十分に該当するため、発火すべきだった

### 4-2. MD構成原因

- CLAUDE.md §4.2 からスクリプト調査への導線はない（スクリプト一覧・実行スケジュールへの参照がない）
- しかしこれはMD構成の問題というより、§4.2 が明示的に適用される場面でAIが適用しなかった行動の問題

### 5. 再発防止

提出MDの再発防止策(案)の評価:

| # | 案 | 評価 |
|---|-----|------|
| 1 | コード修正（06時以前はtoday-1） | **有効** [方向性]。ただし仕様詳細（確報/速報の公開時刻考慮、祝日前日の扱い等）は別途設計要 |
| 2 | 行動原則の再確認 | **無効**。MR-035/073/119/142 で同型対策が繰り返し失敗した実績あり。意志依存型 |
| 3 | 裏付けなしなら報告しない | **部分有効**。正しいが§4.1の再掲。新規の構造的防止にならない |

**追加すべき再発防止策**:

A. **データ欠落調査の初動チェックリスト化**（知見MD追記）: 「データ欠落報告を受けたら、(1)該当スクリプトの実行ログ確認 → (2)日付ロジック・実行時刻の確認 → (3)APIの実打鍵 の順で調査。外部仕様の説明は(1)(2)で問題なしを確認後に限る」

B. **§4.2 のトリガーワード拡充**（CLAUDE.md微修正）: 現行「動いていない」「おかしい」「壊れている」「アホ」「違う」に加え、「欠落」「ない」「来ていない」「入っていない」を追加。データ不在系の報告で§4.2が確実に発火するようにする

C. **コード側のガード**（仕組み側）: `_resolve_dates()` にログ出力を追加し、02:00実行時に「today=YYYY-MM-DD を返却」と記録。実行ログを見れば即座にバグを特定できるようにする

### 6. 新規リスク

- 追加策Bでトリガーワードを増やすと、外部要因が真の原因の場合にも自コード検証を強制し、調査が遅延する可能性。ただし§4.2は「自己検証で問題なしと確認した場合のみ外部要因を検討」であり、自コード検証が空振りならそこで終わるため実害は軽微
- 追加策Aのチェックリスト化は、対象スクリプトが不明な場合に「どのスクリプトを調べるか」の判断が必要。data_catalog.md等との連携が前提

### 7. 対策スコープ

- 案1（コード修正）: 本スクリプト固有fix
- 案2-3: §4.1/§4.2 の再掲。汎用だが無効
- 追加策A: 「データ欠落調査」パターン固有の知見MD化。004 §デバッグ手順等に追記候補
- 追加策B: CLAUDE.md §4.2 のトリガーワード拡充。汎用
