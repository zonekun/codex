# 021: バックグラウンドタスク完了通知のLINE返信を処理しなかった

**日時**: 2026-04-29
**重要度**: MEDIUM
**カテゴリ**: 運用ミス（LINE返信見落とし）

---

## 事象

send_ntfy_and_wait()をBash(run_in_background=true)で実行。バックグラウンドタスク完了通知(task-notification)を受信した際、出力ファイルに含まれるユーザー返信(id=742「008作業続行」)を読まなかった。

コンテキストクリアハンドリング手順（新設したばかりのルール）に従い「/clear待ち、新タスク処理しない」と宣言して待機状態に入ったため、バックグラウンドタスクの完了通知が来ても出力を読まず、ユーザーの返信を見落とした。

## 根本原因

1. send_ntfy_and_waitをrun_in_background=trueで実行した場合、task-notification完了時に**出力ファイルを読んでユーザー返信を確認する義務**が明文化されていない
2. コンテキストクリア待機状態に入った結果、全てのアクションを止めてしまい、バックグラウンドタスク完了通知すら処理しなかった
3. コンテキストクリアハンドリングルールの「新タスク処理を開始しない」を「一切のアクション停止」と過剰解釈した

## 再発防止

- バックグラウンドで実行したsend_ntfy_and_waitのtask-notification完了時は、**必ず出力ファイルを読んでユーザー返信を処理する**
- コンテキストクリア待機中でも、バックグラウンドタスク完了通知の処理は行う（ユーザーの返信がクリア指示の撤回や続行指示の可能性があるため）

## 【パターン 2: 誤読・ミス原因分析】

### 事象

LINE会話モード中、`send_ntfy_and_wait()` を `Bash(run_in_background=true)` で実行していた。並行してユーザーからコンテキストクリア指示を受け、L107に従い /clear を案内して待機状態に入った。その後、バックグラウンドの `send_ntfy_and_wait()` がユーザーの返信（id=742「008作業続行」）を受信して完了し、task-notification が発火した。しかしAIは「/clear待ち」状態にいたため、task-notification の出力ファイルを読まず、ユーザーのLINE返信を見落とした。

### 読み手がどう解釈した可能性があるか

1. **L107「新タスクの処理を開始しない」を全アクション停止と解釈**: 「/clear待ち」宣言後、L107に従い一切の処理を停止。task-notificationの出力読み取りも「処理」に含まれると判断
2. **task-notification を「新タスク」と誤分類**: task-notification はシステムが生成するイベントだが、AIにとっては「新しい入力」として到着する。「新しい入力=新タスク」とL107の「新タスクの処理を開始しない」に該当すると判断
3. **ユーザーの返信がtask-notification の出力ファイル内にあることを認識していなかった可能性**: バックグラウンドで実行した `send_ntfy_and_wait()` の戻り値（ユーザー返信）はstdoutに出力され、task-notification完了時に出力ファイルとして参照可能になる。この間接的な格納場所を認識していなければ、task-notification を「プロセスが終了した」という情報のみと誤認し、出力を読む動機が薄くなる

### 直接原因

CLAUDE.md L107の「新タスクの処理を開始しない」が、バックグラウンドタスク完了通知（task-notification）の処理を含むかどうかが未定義。AIは「/clear待ち」状態で受信したtask-notificationを「新タスク」と同一視し、L107に従って処理を見送った。

### 根本原因

1. **L107の「新タスク」の定義が不在**: 020レビューでL107を追加した際、「新タスク」はユーザーからの新規作業指示を想定していた。しかし「バックグラウンドタスクの完了通知」は新規作業指示ではなく既存タスクの結果報告であり、L107の射程外であるべきだった。この区別がルール文面に反映されていない
2. **バックグラウンド `send_ntfy_and_wait()` 完了通知の処理義務が未明文化**: task-notificationを受信したら出力ファイルを読んでユーザー返信を処理する、という義務がCLAUDE.mdにも068にも書かれていない。068 L228は「返信到着時に通知される」で終わっており、「通知された後に何をするか」が欠落
3. **ルール追加時の複合シナリオ検証不足**: L107の追加は020レビューで推奨されたが、「コンテキストクリア待機中にバックグラウンドタスクが完了する」という複合シナリオはStep 8cの副作用シミュレーションで検出されなかった。単一ルールの正しさと、既存ルール群との組合せの正しさは別問題であり、後者の検証が不十分だった

### 誤読を許した MD 上の原因

| 箇所 | 問題 |
|------|------|
| `CLAUDE.md:107` | 「新タスクの処理を開始しない」の「新タスク」がバックグラウンド完了通知を含むか不明。既存タスクの完了イベントとの区別基準がない |
| `CLAUDE.md:107` | コンテキストクリア待機中でも処理すべき例外（バックグラウンドタスク完了、timeout、エラー等）が未定義 |
| `CLAUDE.md:100` | 非同期サブタスクフローの(c)「サブタスク完了を待つ」がtask-notification到着時の具体的アクション（出力ファイル読み取り）を含意しているか不明 |
| `068:228-236` | バックグラウンド完了通知を受けた後の処理フロー（出力ファイル読み取り→返信抽出→次のアクション）が欠落 |
| `CLAUDE.md:100-107` | L100（完了を待ち報告）とL107（クリア待ちで処理停止）の競合時の優先順位が未定義 |

### 再発防止の方向性

1. **L107に例外事項を追加**: コンテキストクリア待機中でも「既に起動済みのバックグラウンドタスクの完了通知は処理する」ことを明記。「新タスク」の定義を「ユーザーからの新規作業指示」に限定し、バックグラウンド完了通知は含まないことを明示
2. **バックグラウンド `send_ntfy_and_wait()` 完了時の処理義務を明文化**: task-notification受信時に出力ファイルを読んでユーザー返信を確認する義務を068知見ファイルまたはCLAUDE.mdに追加
3. **ルール間の優先順位ガイドライン**: 「コンテキストクリア待機」と「バックグラウンドタスク完了」が競合した場合、バックグラウンドタスク完了の処理を優先する旨を明記。理由: バックグラウンドタスクの出力にはユーザーの返信が含まれている可能性があり、その返信がコンテキストクリア待機の前提を覆す内容（「クリア不要、作業続行」等）である可能性がある
