## 【パターン 4: 原因分析】

### 事象

ユーザーが「ソースコートとskill両方」（原文）と指示。これは `/code-reviewer` エージェントを起動してソースコードと skill MD 両方をレビューさせる意図だった。しかし Claude Code はスキル MD と対象ファイルを Read し、自分自身で5件の指摘を列挙した（手動レビュー）。ユーザーが「レビューワ起動という意味だったが レビュー済みなのでもうよい」と訂正。

### AIの思考回路（推定）

1. ユーザー入力「ソースコートとskill両方」を受信
2. 「レビュー」系の文脈からレビュー作業と認識
3. **分岐点A（致命的）**: 「レビューに（出して）」を「レビューして」と解釈。「に」の省略先（「出して」=エージェント起動）を補完せず、直接実行を選択
4. CLAUDE.md §10 知見索引テーブル L183「レビュー系エージェント（3種）」を参照すべきだったが、セマンティックマッチの結果、テーブルを参照しても「レビュー」→「レビュー系エージェント」のルーティングが「Agent起動」ではなく「知見MDのRead」への導線であるため、ルーティング先ファイルを読む→自分でレビュー、の経路に流れた
5. **分岐点B（構造的）**: §8 L145 の Agent/Skill 区分を参照すべきだったが、§10 テーブルからの導線で §8 をスキップ。テーブルの参照先は skill 正本であり、§8 の「Agent = 独立実行→結果返却」の制約が発火しなかった
6. 対象ファイルを Read → 指摘を自分で生成

### 直接原因

「レビュー」というユーザー入力に対して、以下の2段階でルーティングが失敗した:

1. **意図解釈の失敗**: 「レビューに」を「レビューして（自分で実行）」と解釈し、「レビューに（出して）→ Agent 起動」という意図を読み取れなかった
2. **§8 Agent 制約の未参照**: たとえ「レビューして」と解釈した場合でも、§8 L145 で `/code-reviewer` は Agent（独立実行→結果返却）と定義されており、メインエージェントの直接実行は禁止されている。この制約が参照されなかった

### 根本原因

**MR-110 の再発防止策（セマンティックマッチ許可: CLAUDE.md L161）が、この事故クラスに対して実効性を持たない。**

MR-110 は「テーブルのキーワードマッチ失敗→フォールバック探索で時間浪費」を問題とし、セマンティックマッチを許可する文言修正で対策した。しかし今回の事故は「テーブルマッチの成否」ではなく「マッチした後の行動選択」の問題である:

- テーブル L183 に到達しても、参照先は `/code-reviewer` etc.（スキル正本のポインタ）
- ポインタを踏んでスキル MD を Read した場合、「このスキルは Agent で起動すべき」という制約はスキル MD 内にあるが、Read した時点で「自分がレビュアーモードに入る」パスが開く
- つまり **テーブルマッチ → スキルMD Read → インライン実行** という経路は、MR-110 の対策では塞がらない

MR-110 の苦情欄で「#2（セマンティックマッチ許可）が根本対策であり、#1（キーワード列挙）は不要」と判断されたが、実際には **#2 はルーティング精度の改善であって、ルーティング先での行動制約ではない**。今回の事故は #2 の射程外。

### MD上の原因

**MDの記述は明確。問題は行動側にある。**

- CLAUDE.md §8 L145: Agent 区分は明確に定義されている
- code-reviewer skill MD L10-14: インライン実行禁止は明記されている
- 097 §1-4: メインエージェントの禁止事項も明記されている

MDの品質・表現に問題はない。問題は、これらの制約が「参照されなかった」ことにある。

## 【MD群の構造・導線分析】（Step 6 部分実行）

### CLAUDE.md からの到達可能性

2つの到達経路が存在するが、いずれも行動強制力を持たない:

1. **§8 経路**: CLAUDE.md §8 L145「Agent（独立実行→結果返却）: `/code-reviewer`」→ 到達可能だが、タスク受領時に §10 テーブルが先に参照される構造のため、§8 を経由しない
2. **§10 テーブル経由**: L183「レビュー系エージェント（3種）」→ `/code-reviewer` → skill MD Read → 「Agent で起動すべき」制約に到達。しかし Read した時点でインライン実行パスが開く

**構造的欠陥**: §10 テーブルは「何を読むか」の導線であり、「どう実行するか」（Agent vs インライン）の導線を持たない。§8 の Agent/Skill 区分は §10 テーブルとは独立したセクションであり、テーブル参照→スキル実行のフローに §8 が介在しない。

### コンテキスト圧縮後の可用性

- §8 は CLAUDE.md の一部であり圧縮後も利用可能
- ただし §8 は宣言的（Agent 一覧を列挙するのみ）であり、「レビューと言われたら Agent 起動せよ」という行動指示ではない。圧縮後にこの宣言的情報から行動を推論する負荷は高い

### MD間導線の健全性

- §8 と §10 の間に相互参照がない。§10 テーブルの L183 は skill 名を列挙するが、§8 の Agent 制約へのポインタがない
- テーブル L183 の「必ず読むファイル」列は `/code-reviewer` 等のスキル名だが、これは「このスキルを Agent で起動せよ」なのか「このスキル MD を Read せよ」なのか曖昧。テーブルの他の行は知見 MD のパスを示し「Read せよ」の意味だが、L183 だけはスキル名を示しており性質が異なる

## 【エスカレーション判定】

### 構造的強制（hook / validator）で防げるか

**防げる。以下の2段階で検討可能:**

1. **UserPromptSubmit hook**: ユーザー入力に「レビュー」が含まれ、かつ「自分で」「直接」等の直接実行指示がない場合に、「/code-reviewer または /md-reviewer を Agent で起動しますか?」と確認を促す hook。**[方向性]** — hook の具体実装はスコープ外だが、技術的に実現可能（`.claude/settings.json` の hooks セクションで UserPromptSubmit イベントに prompt-based hook を設定）

2. **§10 テーブルへの行動種別列の追加**: テーブルに「Read」「Agent起動」の区分列を追加し、L183 は「Agent起動」と明記する。これにより AI はテーブル参照時点で Read ではなく Agent 起動を選択する。**[方向性]** — MD修正のみで対応可能

### md-reviewer のスコープ

本件の根本対策は以下の2つに分かれる:

- **MD導線の改善**（md-reviewer スコープ内）: §10 テーブルに行動種別を追加、§8 と §10 の相互参照を追加
- **hook / validator の実装**（md-reviewer スコープ外）: UserPromptSubmit hook の設計・実装はコード側の作業
