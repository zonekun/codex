## 【パターン 2 のみ: 誤読・ミス原因分析】

### 事象

088プランMDの更新日時が `2026-05-01 02:30 (JST)` と記載されていた。コミット実時刻は `2026-04-30 13:30:12 +0900` (JST)。作業時間帯は 4/30 20:00-23:00 JST。`02:30` という値はJSTとして不自然であり、UTC値 (17:30 UTC = 02:30 JST翌日) にJSTラベルだけ付与されたか、コンテキスト圧縮後にシステム時刻(UTC)を参照してJST変換を忘れたかのいずれか。

Phase 3/4の完了日も `2026-05-01` とされており、同一セッション内で複数箇所に波及していた。

### 読み手がどう解釈した可能性があるか

- 「4/30の20時に作成されたプランが、5/1の02:30に更新された」 → 深夜に別セッションで作業したと誤認
- 「Phase 3/4は5/1に完了した」 → 作業タイムラインの1日ずれ
- Codex等の外部実行担当が参照した場合、作業日の誤認がスケジュール管理に影響

### 直接原因

AIがプランMDの更新日時を記述する際に、正確なJST値を取得せず、内部的に保持していた時刻情報（おそらくUTCまたは不正確な値）をそのまま `(JST)` ラベル付きで記載した。

### 根本原因

1. **CLAUDE.md §時刻表示ルールの適用範囲の盲点**: 同ルールは外部ソースからの時刻変換を主に想定しており、「AIが自分でMDに日時を書く」際の正確性検証プロセスが定義されていない
2. **コンテキスト圧縮後の日時認識**: Claude Codeのコンテキスト圧縮によりセッション内で蓄積した時刻情報が失われ、圧縮後に不正確な時刻を生成した可能性がある。これは構造的な障害モードだが、CLAUDE.md にもスキルにも対策記述がない
3. **プランMDの更新日時の正本不在**: 更新日時はAI手書きであり、git commitタイムスタンプという客観的な正本が存在するにもかかわらず照合する運用がない

### 誤読を許した MD 上の原因

- `CLAUDE.md:87-91` — §時刻表示ルールの3項目は全て「変換して表示」「変換してから思考」「コード上で`datetime.now(tz=...)`」というパターン。AIがMDに日時を手書きする際の自己検証義務を導出できない
- `skills/planning.md:60` — `YYYYMMDD_HHMMSS: 作成日時（JST、末尾）` とあるがこれはファイル名の命名規則であり、MD本文中の日時メタデータの記述ルールではない
- プランMDテンプレート (`docs/plans/_template_refactor.md:3`) — `**作成日時**: YYYY-MM-DD HH:MM JST` と記載があるが、この値をどう取得すべきか（システムコマンドで取得する/git commitと照合する等）の指示がない

### 再発防止の方向性

1. **CLAUDE.md §時刻表示ルールに「AI自身が日時を記述する場合」の項目を追加**: 具体的には「MD作成・更新時の日時は `date` コマンド等で現在時刻を確認して記述する」旨を明記
2. **コンテキスト圧縮後の日時取得**: 圧縮後に日時が必要な場合は必ず `date` コマンドで現在時刻を再取得するルールの追加を検討
3. **プランMDの更新日時は必須ではなく任意**: git commitタイムスタンプが正本であるため、MD本文中の更新日時はあくまで参考値。正確性が保証できない場合は書かない方がましという選択肢もある
