## 【パターン 4: 誤読・ミス原因分析】

### 1. 事象

2つの事象が報告されている:

**事象1**: 決算短信の構造読み取りで「1件1件丁寧に」と複数回念押ししたにもかかわらず、途中からPythonスクリプトを書いてパターン化しようとした。

**事象2**: 「文章を成形せよ」と指示したのに、Pythonスクリプトを書き始めた。

### 2. 読み手（AI）の解釈

AIは以下のように解釈した可能性が高い:
- 「1件1件丁寧に」→ 品質要求（丁寧に処理せよ）であり、手段制約（手動で処理せよ）ではない
- 「文章を成形せよ」→ テキスト処理タスク → Pythonで処理するのが自然
- パターンが見えた → コード化した方が効率的・再現可能・エラーが少ない

### 3. 直接原因

AIの「コード化デフォルト」行動が、ユーザーの手動処理指示を上書きした。CLAUDE.md §指示の字義優先（L331）は「ユーザー指示は、AIの技術的判断より常に優先する」と定めているが、AIが「手段選択」をこのルールの射程に含めて認識していない。

### 4. 根本原因

**(a) MR-071「改良バイアス」の変種**: MR-071では「そのまま移植せよ」に対して技術スタックを差し替えた。今回は「手動で処理せよ」に対してPythonスクリプトを書いた。共通する根本原因は「AIの技術的判断がユーザーの明示的手段指定を上書きする」傾向。

**(b) CLAUDE.md §指示の字義優先の射程不足**: L331の「技術的判断」は「アルゴリズム選択」「ライブラリ選択」に解釈が偏りやすく、「手段選択（コード vs 手動）」が明示的に含まれていない。

**(c) 手動処理トリガー語彙の欠如**: §既存コード移植ルール（L284）は「そのまま使え」「コピペせよ」等のトリガー語彙を持つが、手動処理指示（「1件ずつ」「君が判断して」「成形せよ」）に対応するトリガー語彙リストが存在しない。

- 「手動処理指示ルール」のトリガー語彙（「1件ずつ」「丁寧に」等）が、コード作成タスクで使われた場合に誤発火するリスク: 例えば「1件ずつテストケースを丁寧に書いて」→ コード作成が手動処理と誤認される可能性。ただし「対象タスク」条件（文章成形、構造読み取り等）で絞っており、コード作成タスクは対象外。「判断基準」にも「ユーザーはAIの言語能力を使いたいのか、コードを書かせたいのか」とあり、コード作成指示は除外される。リスクは低い

**(ii) クロスルール競合**:
- §既存コード移植ルール（L284）と新規「手動処理指示ルール」は同セクションに並列配置。両者の発火条件は重複しない（移植ルール: 「そのまま使え」系 / 手動処理ルール: 「手動で」系）。同時発火しても矛盾しない（両方とも「ユーザー指示に従え」という同方向の制約）
- §指示の字義優先（L331）の射程拡大（「手段選択を含む」の追加）は、既存の適用範囲を狭めない。追加のみであり既存ルールとの競合なし

**(iii) 状態依存シナリオ**:
- ライン会話モード中に手動処理指示を受けた場合: 通常と同様にルールが適用される。特段の状態依存リスクなし
- Codex への委譲時: Codex は CLAUDE.md を参照しないため、このルールの適用外。Codex に手動処理タスクを委譲する場面は想定されない

**(iv) 再発防止策の実効性**:
- 「手動処理指示ルール」は意志依存型か? — トリガー語彙を明示的にリストしている点で、「注意する」「気をつける」よりは具体的。ただし最終的にはAIがルールを参照して判断する必要があり、完全な構造的強制ではない
- 代替の構造的強制案: PreToolUse hook で Write 対象が .py ファイルかつ直近のユーザー発話に手動処理語彙が含まれる場合に警告を出すことは理論上可能だが、誤検知が多く実用的でない
- **現実的な強制策**: §指示の字義優先の射程明示（#2）と手動処理指示ルール（#1）の二重防御が最善。MR-071後に§既存コード移植ルールが追加され、同種の「そのまま移植」違反は再発していない実績から、ルール明文化は一定の実効性がある

### 8d. 事後確認事項

1. CLAUDE.md に手動処理指示ルールを追加した後、手動処理指示が正しく認識されるか — 次回の手動処理タスク（adapter修正、構造読み取り、文章成形等）で検証
