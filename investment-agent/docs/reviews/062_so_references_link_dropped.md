## 事象の概要

コミット `557e15f` で structure-optimizer（レビュー 027_structure_optimization.md）の推奨に基づき「CLAUDE.md 561→273行 3フェーズ構造圧縮」を実施。その際、CLAUDE.md の `### 外部リファレンス管理（docs/references/）` セクション（ソース種別テーブル + 保存先パス、約10行）を丸ごと削除した。

削除の判断根拠: RD-1（Rebuild層）の実施で知見索引テーブルを INDEX.md に外部化する際、外部リファレンス管理セクションもまとめて INDEX.md に移動すれば十分とした。

しかし INDEX.md は能動的に Read しない限り参照されず、CLAUDE.md の高頻度参照テーブルだけが**毎セッション自動ロードされる唯一の導線**である。2026-05-02 にユーザーが「リファレンスとして取り込み」と指示した際、高頻度参照テーブルに `docs/references/` への導線がないため発火せず、`docs/knowledges/` 配下にリファレンスフォルダを新規作成しようとする記憶喪失が発生した。

---

## 根本原因分析

### 1. 到達可能性の2方向を混同した

structure-optimizer の Step 5 は到達可能性を「読み取り到達可能性」と「書き込みトリガー到達可能性」の2方向で評価する。しかし、本件では**さらに重要な第3の観点が欠落**していた:

- **自動ロード導線 vs 能動的参照導線**: CLAUDE.md は毎セッション自動ロードされるが、INDEX.md は AI が能動的に Read する必要がある。「INDEX.md に残っている」は「能動的参照で到達可能」であり、「自動ロードで発火する」とは全く異なる。

圧縮時の推論は「INDEX.md に残す = 到達可能性: 中（2ステップ）」だったが、実態は以下の通り:

| 状態 | 到達可能性 | 条件 |
|------|-----------|------|
| CLAUDE.md 高頻度参照テーブルに記載 | **高（自動発火）** | ユーザーが関連タスクを言及すれば即座に Read |
| INDEX.md に記載 | **中（能動的参照）** | CLAUDE.md §知見管理 の指示に従って INDEX.md を Read した場合のみ |
| どちらにも未記載 | **低（glob/grep）** | AI が自発的に探索した場合のみ |

問題は、圧縮前は「高」だった到達可能性が圧縮後に「中」に低下したことを **structure-optimizer が検知しなかった** 点にある。

### 2. 「圧縮による導線喪失」の検証プロセスが不在

027 のレビュー出力には RD-1 の実施方針に以下が記載されている:

> INDEX.md の構成: 現行の索引テーブルをそのまま移動 + 恒久ルール vs 時点情報の区分 + 知見ファイル命名規則 + テンプレート情報 + **外部リファレンス管理もINDEX.mdに移動**

「移動する」の一語で処理されており、「移動した結果、自動ロードで発火する導線が消える」というリスク評価が完全に抜けている。これは RD-1 が「削減行数」と「INDEX.md への移動完了」のみを成否判定に使い、**移動元（CLAUDE.md高頻度参照テーブル）に代替導線を残す必要性**を検証していなかったことを意味する。

### 3. 高頻度参照テーブルの選定基準が「使用頻度」のみ

027 RD-1 で高頻度テーブルに残す10エントリの選定基準は「週1回以上参照されるタスク」だった。`docs/references/` への取り込みは週1未満の低頻度タスクであるため、基準に従えば除外は正当である。

しかし、問題は頻度ではなく**代替導線の有無**だった。TDnet ETL や決算モデルは INDEX.md を経由しても到達可能だが（AI がこれらのタスクを受けた時点で INDEX.md を Read する行動が発火するため）、「リファレンスとして取り込み」は docs/knowledges/ のタスクとして INDEX.md を読む動機がない。`docs/references/` は docs/knowledges/ の知見ファイルとは別の管理体系であり、INDEX.md の知見索引テーブルを通る必然性がないのである。

## 再発防止策（structure-optimizer 自身への自己改善フィードバック）

### P1: Step 5 到達可能性評価に「圧縮による導線喪失リスク」観点を追加

structure-optimizer の Step 5 で圧縮推奨を出す際、以下の検証を必須化する:

**検証項目**: 「この項目を CLAUDE.md から削除（INDEX.md 等に移動）した場合、セッション開始時の自動ロードで発火する導線が残るか」

具体的には:
- CLAUDE.md 高頻度参照テーブルから削除する項目がある場合、その項目が INDEX.md 経由でも到達可能かだけでなく、**INDEX.md を Read する動機が発生するか**も検証する
- 動機が発生しない場合（対象が docs/knowledges/ 以外の管理体系である場合等）、高頻度参照テーブルへの残留を推奨する

### P2: 到達可能性テーブルに「自動ロード vs 能動的参照」の区別を明示

現行の到達可能性テーブル（高/中/低/不到達）に以下の注記を追加:

- **高（自動ロード）**: CLAUDE.md 高頻度参照テーブルに明記。セッション開始時に自動ロードされ、タスク言及で即発火
- **中（能動的参照）**: INDEX.md に掲載。AI が INDEX.md を能動的に Read した場合のみ到達

**重要**: 圧縮推奨で「高→中」の降格が発生する場合、その項目が INDEX.md を Read する文脈で自然に到達可能かを必ず検証すること。到達可能でない場合、降格は導線喪失に等しい。

### P3: CLAUDE.md 高頻度参照テーブルからの削除は「到達可能性の低下」として扱う

CLAUDE.md の高頻度参照テーブルは「自動ロード + パターンマッチで即発火」という最高の到達可能性を持つ。ここからの削除は、たとえ INDEX.md に残しても、到達可能性の低下である。

この認識を structure-optimizer のスキル定義に明文化する。
