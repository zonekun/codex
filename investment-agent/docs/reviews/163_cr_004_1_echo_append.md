## 【サマリー】

- 変更の要約: code-reviewer / md-reviewer の 004-1 ログ追記を Read+Edit から echo >> に切り替え、追記 1 回あたり ~741 行分のトークン消費を削減する計画
- 品質評価: **C** — 目的と動機は妥当だが、技術選定に構造的欠陥がある（echo >> の追記位置が 004-1 のファイル構造と不適合）
- 主要リスク:
  1. echo >> は EOF 追記だが、004-1 は末尾が傾向分析セクションであり蓄積エントリの外に書き込まれる
  2. 蓄積エントリは日付降順で先頭側に最新日を配置するルール。echo >> では降順を維持できない
  3. md-reviewer の苦情受付例外が計画に含まれていない

## 【パターン4のみ: 新規計画評価】

### 技術選定の妥当性

**echo >> は 004-1 のファイル構造と不適合であり、計画の核心部分に構造的欠陥がある。**

004-1 の実際のファイル構造（742行）:

| 行範囲 | 内容 |
|--------|------|
| L1-13 | ヘッダー・書き込み権限 |
| L14-112 | タグカタログ |
| L114 | `## 蓄積エントリ（新しい順）` |
| L116-127+ | 蓄積エントリ本体（`### YYYY-MM-DD` 見出し + 日付降順） |
| L715-741 | `## 傾向分析ログ` セクション（2026-05-02 初回分析結果 + 今後の分析スコープ） |

`echo >> <file>` は常に **EOF（L742 の後）に追記**する。つまり:

1. **蓄積エントリセクションの外**（傾向分析ログの後）に書き込まれる
2. 蓄積エントリの「新しい順」（日付降順）ルールを維持できない
3. 傾向分析実行時に、蓄積エントリと分析結果が混在して解析不能になる

計画の注意事項（L63）に「`tail` で末尾数行を確認し、同日見出しが無ければ見出し行も echo >> で追加する」とあるが、これは末尾が蓄積エントリの末尾だという誤った前提に基づいている。実際の末尾は傾向分析セクションである。

**[方向性] 代替案**: 以下のいずれかを検討すべき:
- (a) `tail` ではなく `Read` の `offset` 指定で L114-130 付近のみ部分読み込み（~15行）→ 最新日付見出しの直下に Edit で 1 行挿入。全件 Read の ~741 行 → ~15 行に削減でき、トークン節約の目的を達成しつつ構造を維持できる
- (b) 傾向分析セクションを別ファイルに分離し、004-1 を蓄積エントリのみにする。その上で echo >> を使う場合は昇順に変更する必要がある（ただし既存エントリの並び順を変更するコストが発生）
- (c) 004-1 の追記位置ルール（L33-37）を「日付昇順・末尾追加」に変更し、echo >> と整合させる。ただし傾向分析セクションが末尾にある問題は残る

いずれの案でも、傾向分析セクションが蓄積エントリの後にある構造を考慮する必要がある。

### 既存システムとの統合

- [ ] **追記位置ルールとの不整合（重大）**: 004-1 L33-37 の追記位置ルール（`### YYYY-MM-DD` 見出し配下、日付降順、同日内は末尾追加）と echo >> の EOF 追記が矛盾する。計画はこの不整合を認識しているが（L63）、対策の `tail` 確認は末尾が傾向分析セクションであることを見落としている
- [ ] **タグカタログ新規追加の例外（適切に識別済み）**: 計画 L61 で offset 指定の部分 Read → Edit を許可。妥当
- [ ] **苦情受付の例外（code-reviewer のみ識別）**: 計画 L62 で Read + Edit 必須を正しく識別。ただし md-reviewer の苦情受付（`skills/md-reviewer.md` L407-411）にも同一の例外が必要だが計画に未記載
- [ ] **md-reviewer 側の修正範囲**: 計画の変更対象 B（`skills/md-reviewer.md` L376-403）は追記ルールの範囲。md-reviewer の苦情受付セクション（L407-418）への例外明記が抜けている。code-reviewer 側は L418-435 の苦情受付に対する例外を Step 1 で記載する想定だが、md-reviewer 側の Step 2 で同等の対応が必要

### リスク・コスト

- **GCP課金・処理時間**: 該当なし（ローカル操作のみ）
- **トークン節約効果**: Read 741行（~3,000 トークン）の削減が目的。レビュー頻度が 1 日数回として、月間 ~100 回 × ~3,000 = ~300K トークンの節約見込み。効果は実在する
- **エンコーディングリスク**: Windows 環境で `echo >>` を使う場合、PowerShell のデフォルトエンコーディングは UTF-16 LE（BOM付き）。CLAUDE.md §6 で MD ファイルは `utf-8` 指定が義務。Bash ツール経由なら UTF-8 だが、明示的にエンコーディング指定の注記が計画に必要
- **撤退基準**: 定義なし。ただし変更の性質上、問題が出たら Read+Edit に戻すだけなので低リスク

### 抜け漏れ

- [ ] **004-1 の傾向分析セクションの存在**: 計画が変更対象 C（004-1 L8-14）のみを Read 対象としており、L715-741 の傾向分析セクションの存在を把握していない。これが echo >> 方式の根本的な問題を引き起こしている
- [ ] **md-reviewer 苦情受付の例外**: 上記「既存システムとの統合」で指摘済み
- [ ] **既存エントリとの整合**: 仮に echo >> を採用した場合、既存の ~600 件のエントリは日付降順で蓄積エントリセクション内にある。新規エントリだけが EOF に書かれると、ファイル内で2箇所にエントリが分散する

### 目的・スコープの明確性（任意）

- 非スコープの明示はないが、計画の性質上（3ファイルへの記述追加）問題にならない

## 【重大な指摘】（即修正）

### #1 echo >> の追記位置が蓄積エントリセクション外になる

- 箇所: `docs/plans/tools-004_code_review_findings_log_20260513_105502.md:63`
- 事象: `echo >>` は EOF に追記するが、004-1 の末尾は傾向分析セクション（L715-741）であり蓄積エントリセクション（L114-700付近）ではない。エントリが傾向分析の後に書き込まれ、ファイル構造が破壊される
- トリガー: 計画実施後の最初のレビュー実行時
- 影響: 蓄積エントリの日付降順が崩壊。傾向分析時にエントリが 2 箇所に分散して集計不能
- 根拠: `004-1_code_review_findings_log.md` L114（蓄積エントリ見出し）、L715-741（傾向分析ログセクション）の配置
- 推奨対応: **[方向性]** Read の `offset` パラメータで L114-130 付近（~15行）のみ部分読み込みし、最新日付見出し直下に Edit で 1 行挿入する方式に変更。トークン消費は 741行 → ~15行に削減でき、目的を達成しつつ構造を維持できる。具体的な実装方式は提出元に委ねる

### #2 md-reviewer の苦情受付例外が未記載

- 箇所: `docs/plans/tools-004_code_review_findings_log_20260513_105502.md:30-36` (Step 2)
- 事象: Step 2 は「Step 1 と同一の追記ルール変更を適用」とだけ記載。code-reviewer 側で識別された苦情受付の例外（L62）が md-reviewer 側に反映される保証がない
- トリガー: md-reviewer で苦情取り消し処理が発生した場合
- 影響: md-reviewer が「Read/Edit 禁止」を遵守しようとして苦情処理（既存行の削除 + 不備記録の追記）が不可能になる
- 根拠: `skills/md-reviewer.md` L407-411（苦情受付は ①対象特定 → ②004-1 該当行削除 → ③不備記録 → ④レビューMD更新 の 4 ステップで Read+Edit が必須）
