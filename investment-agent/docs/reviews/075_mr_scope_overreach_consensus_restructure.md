## 【パターン 2: 誤読・ミス原因分析】

### 事象

ユーザーが「P0から着手: BQテーブル DROP→CREATE → VIEW/TVF再作成 ここまで実行」と指示。AIはプランMDを Read 後、ステップ1-4だけでなくステップ5-6（書き込み側スクリプト改修）のソースコードまで Read し着手準備を行った。

### 読み手の解釈

「P0から着手」→ プランMD上のP0セクション全体が実行対象 → P0には「BQスキーマ」と「書き込み側スクリプト改修」の2ブロックある → 両方実行すべき

「ここまで実行」の制約は、AIの解釈の中で「VIEW/TVF再作成」がP0前半の最終ステップであるという事実の**確認**として処理され、P0後半の除外を意味する**制約**としては処理されなかった。

### 直接原因

1. **プランMDの構造バイアス**: 同一優先度ラベル（P0）配下の2つのH3がAIに「同一実行バッチ」と認識された
2. **「ここまで実行」の解釈失敗**: 修飾語の機能（列挙の終端を示す制約）を読み取れず、列挙の最後の要素を強調する表現として処理した

### 根本原因

CLAUDE.md に「ユーザーの即時指示がプランMDの構造的スコープを狭める場合、即時指示の範囲を厳守する」という明示ルールが存在しない。

現行の関連ルール:
- L332「技術的判断より指示の字義を優先する」— トリガーが「指示反復時」に限定されており、初回指示では発火しない
- L327「推測で発言してから確認するな。確認してから発言せよ」— 実行範囲の確認義務を含意するが、「プランMD参照時にユーザー指示の範囲を再確認する」という具体的行動に落ちていない

### MD上の原因

**プランMD側**（`docs/plans/tools-022_consensus_load_20260505_125600.md:70,77`）:
- 2つのH3が同じ「P0:」プレフィックスを共有。AIが優先度ラベルで実行単位を判断する際に、2つのサブセクションが1つの実行バッチに統合される
- ステップ番号が連番（1-6が切れ目なく続く）。構造的区切りがH3見出しのみで、AIの「次のステップへ」という流れに歯止めがかからない

**CLAUDE.md側**（L332）:
- 「指示の字義を優先する」ルールが「指示反復時」のみの発火条件。プランMD読了直後に適用されるべき「ユーザー指示のスコープ再確認」義務が不在

### MD構成原因

- CLAUDE.md L332 の「技術的判断より指示の字義を優先する」は本事故の根拠になり得るが、「指示反復時の自問ルール」という見出し配下にあるため、初回指示での適用が導線上弱い
- プランMDを読んだ後に「ユーザーが指定した範囲はプランMDのどこからどこまでか」を確認するステップが、CLAUDE.md にもプランMDテンプレートにもない
- 009レビュー（VM同期手順で操作境界逸脱）と同構造の問題: 参照文書（プランMD/手順書）の構造が、ユーザー指示の範囲制約を上書きする

### 再発防止の方向性

1. **CLAUDE.md に汎用ルール追加**: プランMD参照時に、ユーザー指示の字義による範囲限定を構造的バイアスより優先する義務
2. **プランMDテンプレートの構造改善**: 同一優先度内のサブセクション間に明示的な「独立実行可能」マーカーを設ける（任意改善）
3. **既存ルールの適用範囲拡大**: L332「技術的判断より指示の字義を優先する」の発火条件から「指示反復時」限定を外す

### 対策スコープ

本問題は CONSENSUS 再構成固有ではなく、**あらゆるプランMD参照タスクで再発する汎用パターン**。ユーザーがプランMDの一部だけを指示した場合に、AIがプランMDの構造的単位（P0/P1ラベル、連番ステップ）を実行範囲と誤認するリスクは全プランMDに存在する。

### 8a. 正本帰属チェック

- **Q2**: 「ユーザー指示の字義が最上位」という原則は L332 に含意されるが、発火条件が限定的で実効性が低い。独立ルール化が妥当
- **Q3**: 本問題は全プランMDで再発可能。CLAUDE.md への汎用ルール追加がスコープとして正しい

既存ルールとの衝突チェック:
- 「知見ファイルは最後まで読む」（L329）: 衝突なし。読む義務と実行範囲の制約は別レイヤー
- 「ジョブ完了時の記録義務」（L334）: 衝突なし。完了後の記録義務は実行範囲の制約とは独立
- CLAUDE.md §プランMD作成時のルール: 衝突なし。作成時ルールと実行時ルールは別フェーズ

### 8c. 副作用シミュレーション（4段階）

**(i) 単体副作用**:
- 「実行範囲厳守」ルール追加後、AIが逆方向に過剰制約される可能性: ユーザーが「P0をやれ」と範囲限定なしで指示した場合に、P0全体を実行すべきか迷う可能性。→ ルール文面に「限定している場合」という条件を含めているため問題なし。限定語がない場合はプランMDの構造に従う
- 「判断に迷う場合はユーザーに確認する」の追加で、過剰な確認が発生する可能性。→ 範囲限定語の有無という明確な判定基準があるため、不要な確認は生じにくい

**(ii) クロスルール競合**:
- 同セクション内「推測で発言するな」（L327）との関係: 補完的。実行範囲の不明点も「確認してから実行する」と整合
- 「マルチターン入力の待機」（L331）との関係: 衝突なし。待機ルールは入力完了判断、本ルールは実行範囲判断
- L332 改訂後の「指示の字義優先」: 新規追加ルール（プランMD参照時）と改訂ルール（字義優先の一般化）が重複するが、前者が具体例、後者が一般原則として補完関係

**(iii) 状態依存シナリオ**:
- LINE会話モード中のプランMD参照: ルール適用に影響なし。LINE経由でも同じ字義優先原則が適用される
- コンテキスト圧縮後のプランMD参照: 圧縮後にプランMDを再読したとき、前回の実行範囲が圧縮で消失する可能性。しかし本ルールはユーザーの即時指示に依存するため、圧縮による劣化なし

**(iv) 再発防止策の実効性**:
- 「意志依存型」判定: 本ルールは「プランMD参照時に範囲限定語を検出したら→プランMDの構造を根拠に拡大しない」という判定基準を含む。単なる注意喚起ではなく、行動の判断基準を提供している
- ただし、hook/validator による構造的強制はない。AIが読み飛ばすリスクは残る。しかし現時点で「プランMD参照のたびに強制チェック」を実装する仕組み（pre-tool hookでプランMD Readを検出する等）は実装コストに見合わない
