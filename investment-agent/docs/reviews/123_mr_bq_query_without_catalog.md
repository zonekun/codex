## 【パターン 4: 運用事故 — 自己の行動不備記録】

### 事象

ザラ場ツール反省会でGCS results.csv の銘柄に対応する株価騰落率をBQから取得しようとした際:

1. data_catalog.md を参照せず、推測でプロジェクトID `and-and-and` とカラム名 `CODE` を使用
2. 1回目: テーブル `and-and-and:STOCK.STOCK_PRICE_JQUANTS` → 403エラー（プロジェクトID誤り）
3. 2回目: 正しいプロジェクトID `gmailpj-357912` に修正するも `LEFT(p.CODE, 4)` を使用 → 400エラー（カラム名 `CODE` は存在しない）
4. 3回目: data_catalog.md のスキーマ定義を Read し、`p.TICKER` で成功

計3回のSQL発行、うち2回がエラー。data_catalog.md を最初に読んでいれば1回で成功していた。

### 違反した既存ルール（5件）

| # | ルール | 所在 | 文言（要約） |
|---|--------|------|-------------|
| 1 | データ参照ルール | CLAUDE.md L161 | 推測で試行する前に data_catalog.md で確認。逐次試行は禁止 |
| 2 | BQクエリ作成ルール | CLAUDE.md L165 | SQLを書く前に data_catalog.md でカラム名確認。推測禁止 |
| 3 | 高頻度参照テーブル | CLAUDE.md L218 | BigQueryを使うコードを書く → 002_bigquery.md |
| 4 | 推測禁止ルール | CLAUDE.md L325 | 推測で発言してから確認するな。確認してから発言せよ |
| 5 | memory feedback | feedback_data_catalog_first.md | BQスキーマ調査前に data_catalog.md を確認 |

### 既存ルールの文言はAIが理解可能だったか

**はい。完全に理解可能。** 5件のルールはいずれも:

- 行為指示が具体的（「data_catalog.md で確認する」「推測で書かない」）
- 禁止事項が明示的（「逐次試行は禁止」「推測でカラム名を書かない」）
- トリガー条件が明確（「SQLを書く前に」「テーブル名・カラム名が不明な場合は」）

AIが「ルールの意味がわからなかった」「曖昧で判断できなかった」という余地はゼロ。**これはMDの可読性の問題ではなく、AIの行動実行の問題。**

### ルール遵守のトリガー導線は存在したか

**はい。6箇所の独立した導線が存在。**

1. CLAUDE.md L159: データカタログ参照義務
2. CLAUDE.md L161: データ参照ルール（MR-117で追加）
3. CLAUDE.md L165: BQクエリ作成ルール
4. CLAUDE.md L218: 高頻度参照テーブル「BigQueryを使うコードを書く」
5. CLAUDE.md L227: 高頻度参照テーブル「銘柄属性・会社名・業種を取得」（MR-117で追加）
6. memory `feedback_data_catalog_first.md`

タスク「BQから株価騰落率を取得する」は、導線#1, #2, #3, #4 のいずれからもdata_catalog.md参照に到達可能。導線の不足ではない。

### 構造的強制（hook / validator / テンプレート埋込）で防げた事故か

**はい。** 以下の構造的強制が考えられる:

- **PreToolUse hook on BQ MCP tool**: `mcp__gcp__bq_query` ツール使用前に、直近のコンテキストで data_catalog.md を Read していなければ警告を出す hook
- ただし、この hook は「Read したかどうか」をコンテキストから判定する必要があり、正確な判定は難しい。また、MCPツール以外のBQアクセス（Pythonスクリプト内のSQL等）には適用されない

**現実的に最も有効な対策**: hook による技術的強制は判定精度の問題があり過剰。本事故の根本原因は「MD改善で防げる範囲を超えた、AIの行動特性の問題」であり、MDの追加修正よりも**この事故パターンの記録と蓄積による傾向分析**が適切。

### 直接原因

AIがBQクエリを書く直前に、CLAUDE.md §データストアの3つのルール文（L159, L161, L165）のいずれも参照しなかった。6箇所の導線がすべてバイパスされた。

### 根本原因

- **MDの問題ではない**: ルールは十分に明確で、導線も十分に多重。MR-117で追加された2件の導線（L161, L227）を含め、6箇所の独立した到達経路が存在する
- **AIの行動実行の限界**: CLAUDE.md は毎セッションのコンテキストにロードされるが、タスク実行中に「BQクエリを書く→まずdata_catalog.md」という行動チェーンが自動的に発火する保証はない。特に、ザラ場反省会という「分析タスク」の文脈では、AIは結果を出すことに注力し、データアクセスの手続きルールの参照を省略しやすい
- **MR-117の同日再発**: MR-117の修正がCLAUDE.mdに反映された後の同一セッション（または直後のセッション）で再発。MR-117の修正自体は正しかったが、「ルールが書いてあれば遵守される」という前提が成立していない

### MD上の原因

- **なし**: MDの表現・構成・導線に改善余地はない。6箇所の多重防御は十分

### MD構成原因

- CLAUDE.md → data_catalog.md の導線は6箇所で十分
- memory feedback も存在
- 構成上の欠陥は検出されない

### 再発防止の方向性

1. **MD追加修正は不要**: ルール文言も導線も十分。これ以上の追記は冗長化を招くだけ
2. **蓄積記録**: 004-1 に `behavior:unverified-claim` として記録し、同パターンの蓄積傾向を監視
3. **根本的対策の方向性**: BQ MCPツール使用時のPreToolUse hookが技術的には可能だが、判定精度と過剰制約のトレードオフがある。現時点では蓄積による傾向分析を優先

### 対策スコープ

- **個別fix**: 不要（MDは十分）
- **汎用ルール**: 不要（CLAUDE.md L161/L165 で汎用ルール化済み）
- **構造的強制**: PreToolUse hook は選択肢だが、現時点では過剰。蓄積で同種事故が3回以上になった場合に hook 導入を検討
