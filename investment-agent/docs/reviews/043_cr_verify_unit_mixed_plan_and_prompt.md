## 1. 検証プラン レビュー

### 1.1 全体評価

v1 からの改定で「Codex 自己申告の数値照合」から「実物 PDF をダウンロードして独立検証」へ大きく方針転換しており、ユーザーの「実物を見て検証せよ」という指示に正しく応えている。6 ステップの構成は論理的に整合しており、検証の方向性は適切。

### 1.2 指摘事項

#### [High] gemini_vision 98社の field_count=0 問題がプランに含まれていない

- **内容**: checkpoint.json を実際に確認したところ、133社のうち gemini_vision に分類された98社は、97社が `field_count=0` である。これは Gemini が regex を断念して gemini_vision を返した結果だが、fields が空のアダプタは Phase 6 の実抽出時に Gemini Vision にフィールド定義なしで丸投げすることを意味する。Step 3 で「gemini_vision 選択の妥当性」を5社検証するが、「fields=0 で実運用に耐えるか」という観点が欠落している。
- **リスク**: 修正前も gemini_vision（fields 空）だった可能性が高いので実害は限定的だが、「修正の結果として正しいか」という検証目的からすると、この 97/98 社が修正前と実質同じアダプタに戻っただけなのか、劣化したのかを確認すべき。
- **推奨修正**: Step 3 に以下を追加:「gemini_vision で field_count=0 の社について、修正前アダプタも同様に field_count=0 だったことを確認する（差分なし=退行なし）。field_count が減少した社があれば個別調査。」

#### [High] Step 1 の「ランダム10社」では 237→133 への絞り込みロジックを検証できない

- **内容**: Codex の引継ぎでは「237社を再分類→133社が simple_table に遷移」と報告されている。Step 1 は「133社からランダム10社」を independent に再分類するが、これは「133社が本当に simple_table か」を検証するだけであり、「残り104社が本当に complex_table のままか」の検証は Step 6 で3社のみ。237→133+104 の分割が正しいかを検証するには、104社側のサンプルも Step 1 と同じ10社規模が必要。
- **推奨修正**: Step 6 のサンプル数を 3社→5社に増やし、Step 1 と合わせて「133社から10社 + 104社から5社 = 15社で再分類テスト」とする。104社側で false negative（本当は simple_table なのに complex_table 判定）が1社でもあれば、全104社を再スキャンする追加ステップを明記。

#### [Medium] Step 2 の regex 抽出テストに「修正前は抽出できなかった」ことの確認がない

- **内容**: Step 2 は修正後の regex アダプタで PDF から値を抽出できるかをテストするが、これだけでは「修正の効果」がわからない。修正前はこれらの社が gemini_vision（fields 空）だったはずなので、「修正前は regex 抽出パスに到達できなかった → 修正後は到達して正しく抽出できる」というビフォーアフターの対比がないと、改善の検証にならない。
- **推奨修正**: Step 2 の方法に追加:「修正前の extract_adapter.json（Step 4 で取得する旧版）の extraction_method が gemini_vision であり fields が空だったことを確認し、修正による改善（regex 化 + fields 定義追加）を定量的に示す。」

#### [Medium] Step 5 のコード単体テストに「円安」「円建て」等の境界ケースがあるが、修正後コードで既に対処済みかの確認が不明

- **内容**: Step 5 で「エッジ（円安、円建て、空文字列）」をテストケースとして挙げているが、Codex handoff の review_followup に「Low指摘（円安等の境界条件）はユーザー判断により対応不要」と記載されている。つまり「円安」に `"円"` がマッチする可能性は既知だが未修正。修正後コードの `stripped.replace("百万円", "").replace("千円", "").replace("億円", "")` 後に「円安」の「円」が残るため、`_detect_unit_mixed("受注高 1,500百万円 円安影響")` は `True` を返す。
- **リスク**: これが実際の PDF テキストに出現する頻度は低いが、テストケースとして挙げるなら期待結果を明記すべき。「円安→False が正しいが現行コードでは True を返す（既知の limitation）」なのか「円安→True でよい」なのかが曖昧。
- **推奨修正**: Step 5 のエッジケース表に各テストケースの「期待結果」列を追加。「円安」「円建て」は「True を返すが運用上の影響は軽微（該当 PDF が存在する場合は complex_table にフォールバックするだけ）」と注記。

#### [Medium] Step 3 の「反証テスト」が1社のみ

- **内容**: 「実はregexでも抽出可能だったのでは?」を1社だけで検証するのは少なすぎる。98社の gemini_vision のうち、Gemini が regex を提案しなかった理由は多様（同名ラベル重複、複数表混在、特殊フォーマット等）であり、1社の反証テストでは代表性がない。
- **推奨修正**: 反証テストを3社に増やし、notes の理由カテゴリが異なる社を選ぶ（例: 同名ラベル重複1社、複数表混在1社、セグメント分割1社）。

#### [Low] PDF DL の保存先ディレクトリ名が Step ごとに異なる可能性

- **内容**: 実行上の制約に `C:\tmp\verify_unit_mixed\` と記載されているが、Step 1〜6 で同じディレクトリを使うのか、Step ごとにサブディレクトリを切るのかが未定義。同じ PDF を複数 Step で使う場合（Step 2 と Step 4 で同じ社を検証する場合等）、即削除ルールとの整合性が不明。
- **推奨修正**: ディレクトリ構成を明記: `C:\tmp\verify_unit_mixed\step{N}\{ticker}\` とし、各 Step 完了後にそのサブディレクトリを削除。複数 Step で同じ社を検証する場合は再 DL する旨を注記。

#### [Low] サンプリング数の統計的根拠がない

- **内容**: 各 Step のサンプル数（10社、5社、3社等）は経験則的に設定されているが、母集団サイズに対する統計的な妥当性が未記載。133社中10社（7.5%）は手動目視検証としては妥当な範囲だが、判定基準「10社中9社以上」の根拠がない。
- **推奨修正**: 重大な問題ではないが、判定基準の設定理由を1行注記すると透明性が上がる。例:「手動 PDF 検証のコスト制約上、母集団の 5-10% をサンプリング。1社の不一致は偶発エラーとして許容し、2社以上の不一致で系統的問題を疑う。」

## 2. 6:40起動プロンプト レビュー

### 対象プロンプト

```
6:40 JST 起動。双方向ライン会話モードを開始する。memory の line_conversation_mode.md を active: true に更新してから、docs/plans/20260501_060000_verify_unit_mixed_fix.md の検証プランに従い、Phase 5 unit_mixed バグ修正 + 133社アダプタ再生成の検証作業を開始する。全ての応答は send_ntfy_and_wait() で送信すること。
```

### 2.1 指摘事項

#### [High] プランの Step 1 から即座に作業開始するのか、概要報告してからユーザー承認を待つのかが曖昧

- **内容**: プロンプトは「検証作業を開始する」とだけ書いているが、ユーザーの原指示は「6:40になったら双方向ライン会話モード開始。そこから作業開始する」。双方向モードの趣旨は、ユーザーとの対話を通じて進めることである。起動直後に Step 1 の PDF ダウンロード+再分類テストを無言で始めるのか、まず「プランの概要を報告して承認を得てから Step 1 に進む」のかで、ユーザー体験が大きく異なる。
- **推奨修正**: プロンプトに「まずプランの概要と本日の作業手順を LINE で報告し、ユーザーの承認を得てから Step 1 に着手する」を明記。

#### [Medium] memory の line_conversation_mode.md の timeout 値の指定がない

- **内容**: CLAUDE.md に「LINE timeout は memory の line_conversation_mode.md の値を優先」と明記されている。プロンプトで timeout の値を指定せずに起動すると、memory に既存の timeout 値がある場合はそれを使うが、ない場合はデフォルト 10800秒になる。検証作業は PDF ダウンロード+分析で各 Step 数分かかるため、Step 間の報告で timeout が短すぎると問題になる。
- **推奨修正**: これは起動プロンプトではなく memory 側の設定問題なので、起動プロンプトの修正は不要。ただし memory の line_conversation_mode.md に適切な timeout 値（10800秒推奨）が設定されていることを事前確認する旨の注記を追加。

#### [Low] CronCreate のトリガー後、コンテキストが空の状態で起動する点への配慮がない

- **内容**: CronCreate で起動する場合、会話コンテキストは空（新規セッション）の状態で始まる。プロンプトはプラン MD のパスを明記しているので作業内容は特定できるが、「Codex handoff を確認する」という CLAUDE.md の起動時義務チェックが走る可能性がある。検証プランの作業に入る前に handoff チェックで時間を消費するリスクがある。
- **推奨修正**: 影響は軽微（handoff チェックは1分以下）だが、プロンプトに「handoff.md のチェックは今回スキップ」と明記すると無駄がなくなる。
