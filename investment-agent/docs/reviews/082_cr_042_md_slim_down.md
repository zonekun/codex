## 【重大な指摘】（即修正）

### #1 英語PDF対応の5ステップ修復手順が042-1のE3-4移行で情報ロス

- 箇所: `docs/plans/20260505_210400_042_md_slim_down.md:54`（移行テーブル E3-4行）
- 事象: 042本体L418-438の「英語のみ公開」セクションは5ステップの具体的な `gemini_custom_prompt` 設計指示を含む（日英ヘッダー対応表、会計年度境界、海外店舗除外、Year total除外、ラベル階層明記）。E3-4「英語PDF対応→Gemini+日英対応プロンプト」の1行では修復手順の再現が不可能。
- トリガー: 新たに英語のみ公開に切り替えた企業が出現し、`/monthly-error-autofix` がLayer 1でE3-4を即適用しようとした時
- 影響: gemini_custom_promptに必須5項目のうち一部しか設定されず、抽出失敗（海外店舗データ混入、Year total誤取得等）
- 根拠: 042-1の既存パターン（E3-1, E3-2等）の修復手順は3-4ステップで完結する構造。5ステップ+サブ項目付きの手順は042-1のフォーマットに収まらないか、収める場合は他パターンと粒度が不均一になる
- 推奨対応: (a) 042-1のE3-4に修復手順として全5ステップを省略なく記載する。(b) 042本体には「英語PDF対応の詳細手順は042-1 E3-4参照」のポインタ1行を残す（完全削除ではなく参照残し）

### #2 ThreadPoolExecutor罠・Geminiプロンプト改修がルール凝縮の対象として不適切

- 箇所: `docs/plans/20260505_210400_042_md_slim_down.md:70-71`（ルール凝縮テーブル末尾2行）
- 事象: 「ThreadPoolExecutor罠」と「Geminiプロンプト改修」は**コード実装の設計判断**であり、adapter修正では解決できない問題の記録。1行ルールに凝縮しても、将来同種のコード改修（例: 別のGemini呼び出し箇所にThreadPoolExecutor追加）時に「なぜmodule-level executorなのか」「なぜcontext managerを使わないのか」の理由が失われる。
- トリガー: extract_monthly_data.py の `_call_with_timeout()` 周辺を改修する新セッション
- 影響: context manager方式に「改善」してしまい、Gemini hang時にプロセス全体がブロックする既知バグの再発
- 根拠: これらは「落とし穴」ではなく「コード設計の根拠記録」。性質がadapterパターンと異なる。
- 推奨対応: ThreadPoolExecutor罠・Geminiプロンプト改修は**ルール凝縮ではなく、コード内のdocstring/コメントに設計根拠を移す**か、042本体に「コード設計根拠」として3-4行で残す。042-1（adapter修復パターンDB）への移行は不適切。

### #3 デバッグ知見（pdfplumber/HTML固有の罠）の移行先が未定義

- 箇所: `docs/plans/20260505_210400_042_md_slim_down.md:40`（L554-580判定行: 機能表のみ残す）
- 事象: L574-579のデバッグ知見5点は `/monthly-error-autofix` Layer 3の「PDF/HTML実物の詳細解析」で直接活用される。しかし計画では「042-1に移行」とのみ記載し、042-1のどのパターンに含めるかが未定義。042-1は「エラーパターン→修復手順」の構造であり、「pdfplumber の page.bbox がマイナスマージンを返す」のような横断的デバッグ知見を格納する場所がない。
- トリガー: autofix エージェントがLayer 3で新規PDFの詳細解析を試みた時、page.bbox のマイナスマージンで crop() が失敗
- 影響: 既知の回避策が失われ、Layer 3の調査に余計な時間を費やす
- 根拠: 042-1の既存パターンはいずれも特定のエラー症状→修復のペア。横断的なランタイム知見は構造的に入らない。
- 推奨対応: デバッグ知見5点は042本体の機能表の下に「実装上の注意点」として5行で残す（削除ではなく圧縮）。または042に「コード実装ノート」節を新設し、設計根拠（#2のThreadPoolExecutor罠含む）と合わせて10行程度で保持。
