## 【パターン 4: 原因分析】

### 事象

`edinet-load-backfill-xmvdj`（テストロット BQ Load）を`gcloud run jobs execute`で投入した後、Monitorツールを設定しただけで以降の監視行動を一切行わなかった。ジョブは約3分で正常完了（10:43→10:46）していたが、Monitor 2回のタイムアウト（600s、1800s）を経てもAIは自ら確認せず、ユーザーの催促（「状況調査会話もーど」）で初めて完了を発見した。

MR-173はMonitorの条件式不一致を直接原因としたが、ユーザーの指摘は「条件式が正しかろうが間違っていようが、そもそも見張りをしていなかったことが事故」であった。

### AIの思考回路（推定判断チェーン）

1. ジョブ投入 → 「監視が必要」と認識 → Monitorツールを設定 → **ここまでは正しい**
2. Monitor設定完了 → **「監視体制を構築した = 自分は見張っている」と判断** → **ここが分岐点**。Monitorはツールであり、ツールを設定したことと「見張っている」ことは別である。見張るとは、ジョブの状態を能動的に把握し、完了・失敗を適時に検知する行為そのもの
3. Monitor 1回目タイムアウト（600s） → 「ジョブが遅いのだろう」→ タイムアウトを延長して再設定 → **「自分は見張りを継続している」と認識**。実際には、3分で完了するはずのジョブが600秒経っても検知されないこと自体が異常だが、その異常を自分の問題として捉えなかった
4. Monitor 2回目タイムアウト（1800s） → それでも手動確認せず → **見張りの不在が確定**
5. ユーザー催促 → 初めて手動で `gcloud run jobs executions describe` → 既に30分以上前に完了済み

**思考回路の核心**: 「ツールを起動した時点で仕事は完了」という委任思考。BGスクリプト（MR-068）、定期コマンド（MR-080）、Monitorツール（本件）と対象は異なるが、**「何かを起動/設定した = 自分は見張っている」という同一の誤認パターン**が3回繰り返されている。

### 直接原因

**ジョブ投入後に見張りを行わなかった。** Monitorツールの設定は見張りの手段の一つにすぎず、手段を講じたことと見張り行為そのものは別である。見張りとは:
- ジョブの現在状態を把握していること
- 異常（予想外のタイムアウト含む）に気づき、能動的に対処すること
- 完了・失敗を適時に検知してユーザーに報告すること

これらのいずれも行われなかった。

### 根本原因

**「起動/設定 = 見張り」という誤った等式が3回のMDフィードバックを経ても修正されていない。** 個別のMD改善（動作検証義務の追加、推奨条件テンプレートの追加）は各回の表層的な技術的欠陥を埋めたが、根底にある「委任したら終わり」という行動パターンには到達していない。

093 MDの構成を見ると:
- §プロセス起動手段 → 「何を起動するか」
- §起動後の動作検証義務 → 「起動後に検証せよ」
- §定期チェック4点確認 → 「定期的に何を確認するか」

これらは「監視の個別手順」を積み上げる構成になっている。しかし、**「そもそも監視とは何か」「なぜツール設定だけでは監視にならないか」**という大前提の定義が093の冒頭に存在しない。L7の「テキストで『監視開始』と返すだけは嘘」は「プロセスを立ち上げろ」と言っているだけで、「プロセスを立ち上げた後も能動的に状態を把握し続けることが監視である」とは書いていない。

### MD上の原因

**MDの記述は明確。問題は行動側にある。** ただし、093の構成には1点の構造的弱さがある（後述の重大指摘参照）。

## 【重大な指摘】

### 指摘1: 093 冒頭に「監視の定義」が不在 — 手順消化モードを助長する構造

- **箇所**: `docs/knowledges/tools/093_monitoring_obligation.md` L1-6（冒頭セクション前）
- **問題**: 093は「何を起動するか」「起動後に何を検証するか」「定期的に何を確認するか」という個別手順を列挙しているが、**「監視とは何か」の定義が冒頭にない**。結果として、AIは手順を消化すること（プロセス起動→動作検証→...）を「監視している」と認識し、手順の間に落ちるケース（本件: Monitorが機能していないことに気づかない）を見落とす
- **誤読パターン**: 「093の手順を全て実行した = 監視義務を果たした」と認識するが、実際にはジョブの状態を把握できていない
- **トリガー**: ジョブ投入後にMonitor等のツールを設定した時点で「手順消化完了」と判断する
- **影響**: ジョブの完了・失敗検知が遅延し、ユーザーが催促するまで気づかない（本件で実際に発生）
- **根拠**: MR-068/080/174の3回とも「何かを起動/設定した」時点で見張り完了と認識している。個別手順の追加（検証義務、4点確認、テンプレート）は各回の技術的欠陥を埋めたが、「手順消化 = 監視」という認識パターンは修正されていない
- **推奨対応**: 093の冒頭（§プロセス起動手段の直前）に「監視の定義」セクションを追加。「プロセスを起動すること、ツールを設定すること、コマンドを実行することは監視ではない。監視とは、ジョブの現在状態を把握しており、異常に気づき、完了・失敗を適時に検知できる状態を維持し続けることである」という大前提を明示する。 **[方向性]**
- **MD修正で足りるか**: 足りる可能性がある。ただし3回繰り返している行動パターンに対してMD追記のみで是正できるかは不確実。次回発生時にはcode-reviewer/ai-engineer領域の構造的強制（監視用共通スクリプトの導入等）へのエスカレーションを検討すべき

**[採用]** 093冒頭に「監視の定義」セクション追加済み。繰り返し事故パターン警告、Monitor時のScheduleWakeup免除撤廃も併せて対応済み。

## 【改善提案】

### 提案1: 093 §BGスクリプト監視時のScheduleWakeup併用必須のMonitor免除を撤廃

- **箇所**: `docs/knowledges/tools/093_monitoring_obligation.md` L57

- **提案**: 免除条件を厳格化。「Monitor使用時でも、ジョブの想定完了時間の1.5倍を超えた場合に手動確認するScheduleWakeupを併設すること」を追加。本件ではジョブ想定3分に対し、Monitor 600sタイムアウト時点（= 想定の3倍超過）でScheduleWakeupがあれば手動確認に至っていた
- **期待効果**: Monitorが機能していなくても、ScheduleWakeupによるフォールバック確認が発動する

### 提案2: 093に「3回繰り返した同種事故」の警告を明記

- **箇所**: `docs/knowledges/tools/093_monitoring_obligation.md` 末尾（事故事例セクション）

- **期待効果**: 次回の監視タスクで093を読む際に、過去の繰り返しパターンが可視化され、より慎重な行動を促す
