## 【パターン2のみ: 改修プラン評価】

### 妥当性

**独立仮説（プランを脇に置いた独自推定）**:
- 症状: 火〜土 02:00 に実行されるジョブが毎回 0 件終了
- `_resolve_dates()` L107-111 を読むと、DATE_MODE="t" で `today = datetime.now(JST).replace(...)` → `return today, today` をそのまま返している
- J-Quants 確報は「前営業日 24:30（= 当日 00:30）」公開であり、02:00 JST 実行時点で "今日の日付" を渡すと当日分データはまだ存在しない → 0件
- 根本原因: スクリプトが "実行日" と "取得したい日" を同一視している。解決策は「実行時刻によって取得日をシフトするか」「外部から取得日を注入するか」のいずれか

**方向性照合**: プランの方針「Cloud Scheduler から `--shift-day=-1` を注入する外部パラメータ方式」は根本原因に対して適切に対処している。プログラム内時刻判定の代替として冪等性・テスト容易性が高い設計。**方向性に問題なし。**

### 副作用・デグレードチェック

- [x] **Colab 実行への影響**: 変更 1 で `shift_day=0` を Namespace に追加。`main()` で `args.shift_day` を参照するため、Colab ブランチでの `AttributeError` は解消される。ただし現時点（修正前）の Colab ブランチは `shift_day` 属性を持たず、変更 4 の `args.shift_day` 参照が修正前のコードでは `AttributeError` を発生させる点は、変更 1 と 4 が**セットで適用される前提**なら問題なし。
- [x] **`--from`/`--to` 指定時の挙動**: `if args.date_from:` ブランチでは `args.shift_day` は参照されない。明示的な日付指定時は shift_day が無視されるという設計で、これはプランの記載と一致しており意図的。デグレードなし。
- [x] **`_resolve_dates()` の他モード**: DATE_MODE="1" / "r" ブランチは変更 3 の after コードに含まれていない（省略記載）が、実装時にそのまま保持する前提。プランの before/after 記載が "t" ブランチのみを示しているため、**実装者が "1" / "r" ブランチを誤って削除するリスク**がある。→ 後述 [改善提案 #1]
- [x] **過去の緩和策剥がし**: 該当なし。新規パラメータ追加のみで既存ロジックへの副作用なし。
- [x] **BQ データ互換性**: DELETE → APPEND のロジック変更なし。互換性問題なし。

### 新規リスク

- **`--shift-day` に正値（例: 1, 7）を渡した場合の動作**: 未来日のデータを取得しようとする。J-Quants API は未来日に対して 0件を返すだけであり、BQ への DELETE は発動するが APPEND は 0件で終了する（`if not all_data: return` で安全に終了）。データロストのリスクはない。ただし意図しない DELETE が発生する点は注意。これはパラメータ仕様として許容範囲。
- **Cloud Scheduler の `message-body` 更新コマンドのトークン配列形式**: プラン P1-1 の `--message-body` JSON の `args` フィールドに `["--shift-day", "-1"]` とあるが、`-1` は負数であり Cloud Run Job の args として正しく渡されるかは環境依存。smoke test で確認必須（プランの検証戦略に含まれている）。

## 【重大な指摘】（即修正）

### #1 `elapsed` 未使用変数（情報欠如 + 将来的な混乱リスク）

- 箇所: `scripts/jquants_get_fin_summary.py:466`
- 事象: `elapsed = datetime.now(JST) - start_time` が計算されるが、成功完了時のログにも `send_mail` 成功通知にも使われていない。実行時間が記録されない。
- トリガー: 正常完了時に常に発生。
- 影響: ①パフォーマンス監視不能（ジョブが突然遅くなっても気付けない）、② `elapsed` を使う想定のコードが後から追加されると、既存の変数定義と意図が衝突する。
- 根拠: L466 の `elapsed` 定義後、L468 `log_cap.stop()` で終了し `elapsed` の参照箇所がない。
- 推奨対応: [方向性] `elapsed` をログ（structlog の INFO か print）に出力するか、定義自体を削除する。今回のプランスコープ外だが、変更 4 の `print("[日付確認]...")` 追加と同じタイミングで対処が望ましい。

### #2 `print()` 使用（CLAUDE.md §7 規約違反）

- 箇所: プラン変更 4 の after コード（新規追加行）、および `scripts/jquants_get_fin_summary.py` 全体（既存の print 呼び出し多数）
- 事象: プランの修正方針が `print(f"[日付確認] ...")` を追加しており、CLAUDE.md §7 の `print禁止。structlogを使用` に違反する。
- トリガー: 常に発生（実行のたびに print が呼ばれる）。
- 影響: ①ログが構造化されず、Cloud Logging でのフィルタリング・アラート設定が困難、②既存コード全体が print を多用しているため、新規追加行だけ structlog にしても統一性がない。
- 根拠: スクリプト L390, L391, L401, L415, L436, L437, L451, L454, L461, L462 等多数の print 呼び出し。プランの変更 4 も print を追加。
- 推奨対応: [方向性] 今回スコープ（4箇所の変更）に限れば、変更 4 の日付確認ログを `print` ではなく structlog の `logger.info("日付確認", date_from=..., date_to=..., shift_day=...)` に変更すること。既存の print 群の全面置換は今回スコープ外とする（別 P2 タスクとして積み上げる）。永続化先: `docs/knowledges/tools/004_coding_conventions.md` §ロギング

## 【改善提案】（可読性・保守性）

### #1 プランの before/after 省略が実装ミスを誘発するリスク

- 箇所: `docs/plans/tools-008_jquants_shift_day_20260517_150000.md` 変更 3（L89-103）
- 現状: after コードが `if DATE_MODE == "t":` ブランチのみを示し、`elif DATE_MODE == "1":` と `elif DATE_MODE == "r":` が省略されている。「`...` （省略）」等の明示もない。
- 提案: after コードに `elif` ブランチも含める（または `# (省略: "1"/"r" ブランチは変更なし)` を明記する）。実装者が「DATE_MODE="t" 以外のブランチは削除していい」と誤読するリスクを排除する。

### #2 エラーメール本文に `shift_day` を含める

- 箇所: `scripts/jquants_get_fin_summary.py:474-482`
- 現状: 例外発生時の `send_mail` に `date_label` は含まれるが、どの `shift_day` で失敗したかが不明。
- 提案: `args` が取得済みの場合、メール本文に `shift_day={args.shift_day}` を含める。ただし `parse_args()` が例外を投げた場合は `args` が未定義なので、`getattr(args, 'shift_day', '未取得')` で安全参照する。

### #3 フォーマット準拠チェック — P1-1 の「呼び出し側への波及」フィールド

- 箇所: `docs/plans/tools-008_jquants_shift_day_20260517_150000.md` P1-1（L150）
- 現状: 「呼び出し側への波及: なし（Scheduler → Cloud Run Job の HTTP body 変更のみ）」と記載。P1-1 はコード変更ではなく Scheduler 設定変更なので「なし」は適切。ただし P0-1 とのセットアップ依存関係（P1-1 は P0-1 のビルド完了後に実施）が記載されているが、P0-1 → P1-1 の依存が冒頭の優先度定義で明示されていれば十分。
