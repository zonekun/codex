## 【AI 誤読リスク】

1. **「モード継続」= 状態の保持 ≠ 行動の開始**: L71の「モード継続」をAIが「以降の応答でsend_ntfy_and_waitを使う状態を維持する」と解釈した場合、「以降の応答」が発生するまで何も行動しない。/clear直後はユーザーの画面入力またはシステムイベントが無い限り「以降の応答」は発生しないため、AIは受動的に待機する。これが今回のデッドロックの直接的な誤読パターン

2. **ループの前提条件の不可視性**: L73の同期ループは「send_ntfy_and_waitで返信受信 -> 処理 -> 結果をsend_ntfy_and_waitで送信」というサイクルだが、このサイクルは「既に最初のsend_ntfy_and_waitが呼ばれている」という前提を暗黙に持つ。/clear後にこの前提が成立しない場合、AIはサイクルの「どこから入るか」を判断できない

3. **起動時メニューとの競合**: CLAUDE.md §起動時メニューは「セッション開始時にメニューを表示する」と指示している。LINE会話モードがactiveの状態で新セッションが開始された場合、AIは(a)起動時メニューを画面に表示する（LINE会話モードのルールと矛盾）か(b)メニューを省略してLINE会話モードの復旧を行う（起動時メニューのルールと矛盾）かの判断を迫られる。この競合の解決基準がない

4. **068 L149への非到達**: 復旧時に068の初回発動ルール（L149）を参照すれば「即座にsend_ntfy_and_waitで初回通知を出す」というアナロジーが得られるが、L71からL149への導線がない。L71は「モード継続」としか書いていないため、AIはL149を「初回発動」の文脈でしか認識せず、復旧時に適用対象として想起しない

## 【パターン 2: 誤読・ミス原因分析】

### 事象

1. LINE会話モードが `active: true` の状態でユーザーが `/clear` を実行
2. 新セッション開始時、Claudeはmemoryの `line_conversation_mode.md` を確認し `active: true` を認識（L71の「チェック」は実行した）
3. しかし「モード継続」の具体的行動として send_ntfy_and_wait の自発送信を行わなかった
4. ユーザーはスマホ側にメッセージID（3桁ID）がないため、LINE経由でClaudeに指示を送れない
5. 結果、「双方向会話できない」デッドロック状態に陥った

### 読み手がどう解釈した可能性があるか

1. **L71「モード継続」= 状態フラグの保持**: 「active: trueを確認した。以降の応答でsend_ntfy_and_waitを使う。以降の応答はユーザーの画面入力またはシステムイベントが発生したときに生成される。現時点では待機」-- 受動的待機が「モード継続」の正しい解釈と判断
2. **ループの起点を自分から作る義務の不認識**: L73の同期ループを認識しつつも、「ループは既に回っている前提」と解釈。/clear後にループがゼロから再開する必要があるという認識がない。「ループが途切れた」ではなく「ループは次の入力から再開する」と考えた
3. **起動時メニュー表示が先行**: §起動時メニューに従い画面にメニューを表示しようとした（またはユーザーの最初のメッセージを待った）。LINE会話モードの復旧がメニュー表示より優先すべきだという判断基準がない

### 直接原因

CLAUDE.md L71の「復旧義務」が「memoryチェック」と「モード継続」の2ステップのみで構成されており、「モード継続」の具体的初動アクション（ファーストトリガーとなるsend_ntfy_and_waitの自発送信）が定義されていない。/clear後は前セッションのsend_ntfy_and_waitが完全に断絶しているため、AIが自発的に新しいsend_ntfy_and_waitを呼ばない限り、双方向ループは再開しない。

### 根本原因

1. **「モード継続」が状態宣言であり行動指示でない**: L71はモードの状態（active/inactive）の確認と維持を指示しているが、モード復旧時の具体的行動（ファーストトリガー送信）を指示していない。「継続」という動詞は「以前の状態を保つ」を意味するが、/clear後は「以前の状態」（実行中のsend_ntfy_and_waitのブロッキング）が完全に消失しているため、「保つ」べき実体がない
2. **ループの起点と定常運転の混同**: L73の同期ループは定常運転時のサイクルを定義している。ループの起点（最初のsend_ntfy_and_wait呼び出し）は068 L149で初回発動時のみ定義されている。/clear後の復旧という「2回目の起動」は、初回発動でも定常運転でもない第3のケースであり、どちらのルールもカバーしない
3. **/clearの特殊性の未認識**: L71はコンテキスト圧縮・ScheduleWakeup・CronCreate・/clearを等価に扱っている。コンテキスト圧縮では同一セッション内で直前のsend_ntfy_and_waitの文脈（ブロッキング中の状態）が残りうるが、/clearでは完全に断絶する。この差異がルールに反映されていない

### 副作用シミュレーション（8c）

**(i) 単体副作用**:
- ファーストトリガーが送信された後、ユーザーが画面で入力しようとしていた場合: ユーザーが画面入力で応答するケース。send_ntfy_and_waitがブロッキングでユーザーのLINE返信を待っている間に、ユーザーが画面で入力 -> Claudeは画面入力を処理しつつ、BG的にsend_ntfy_and_waitがタイムアウトを待つ。CLAUDE.md L78のFG必須ルールにより、send_ntfy_and_waitはFGでブロッキングしている。ユーザーの画面入力はsend_ntfy_and_waitのブロッキング完了後に処理される。このため、ユーザーの画面入力がファーストトリガーのタイムアウトまで待たされるリスクがある。**ただし、ユーザーが画面にいる場合は通常「LINE会話モード解除」を指示するはずであり、ファーストトリガーのLINE返信で解除を伝えることも可能。実害は限定的**
- ファーストトリガーの文面が固定的: 修正文案では「LINE会話モード継続中です。指示があれば返信してください。」を例示しているが、AIは状況に応じて文面を変更できる（例: 前セッションの作業内容の要約を含める）。文面は固定義務ではなくsend_ntfy_and_wait呼び出し義務が本質

**(ii) クロスルール競合**:
- L71（復旧義務+ファーストトリガー）× L73（同期ループ）: 競合なし。ファーストトリガーはL73の同期ループの起点として機能する。ファーストトリガー送信 -> ユーザー返信受信 -> 処理 -> 結果をsend_ntfy_and_waitで送信 -> ... とループが正常に回り始める
- L71（復旧義務+ファーストトリガー）× L82（コンテキストクリアハンドリング）: 競合なし。L82はLINE会話モード中にユーザーが「コンテキストクリア」を指示した場合の処理であり、/clear「後」のファーストトリガーとは時間的に非重複
- §起動時メニュー例外 × L71（復旧義務）: 競合なし。メニュー省略は復旧義務の前提条件として機能する
- §起動時メニュー例外 × 既存「クラッシュ再開モード時省略」: 競合なし。両例外は排他的条件（LINE会話モードactive vs クラッシュ再開モード）。仮に両方同時に成立した場合（LINE会話モードactive + クラッシュ再開モード）、いずれにせよメニューは省略される。LINE会話モードの復旧義務とクラッシュ復旧手順（`docs/knowledges/tools/085_crash_recovery.md`）の間の優先順位は新たな問題だが、今回のスコープ外

**(iii) 状態依存シナリオ**:
- 状態: /clear後 + active: true + ユーザーがスマホ -> ファーストトリガー送信 -> ユーザーがスマホで返信 -> ループ再開。今回の事故を直接阻止する正常パス
- 状態: /clear後 + active: true + ユーザーが画面前 -> ファーストトリガー送信 -> ユーザーが画面で「LINE会話モード解除」と入力 -> FGブロッキング中のため応答が遅れる。ただしユーザーのLINE返信で「解除」も可能なので回避策あり
- 状態: /clear後 + active: false -> memoryチェックでactive: false確認 -> ファーストトリガー不送信 -> 通常の起動時メニュー表示。正常パス。新規ルールは適用されない
- 状態: コンテキスト圧縮後（/clearではない） + active: true -> L71の復旧義務発動 -> ファーストトリガー送信。コンテキスト圧縮の場合、前のsend_ntfy_and_waitのブロッキングが残っている可能性がある。その場合、新たなsend_ntfy_and_waitがFGで呼ばれ、2つが同時にntfyトピックをpollする。L79（BG残存時もFGで実行可、IDフィルタで混信しない）により技術的に問題はない。ただし「コンテキスト圧縮後にファーストトリガーが本当に必要か」は疑問 -- 圧縮前のsend_ntfy_and_waitがまだ有効なら二重送信になる。**この点は改善の余地があるが、二重送信は「余計な通知が1つ届く」だけであり、デッドロック（通知が届かない）よりはるかに低リスク。安全側に倒す設計として許容可能**
