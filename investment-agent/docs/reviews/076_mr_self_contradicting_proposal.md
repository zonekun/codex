**レビューパターン**: パターン4（運用事故）
**対象**: 本セッション内の行動（CONSENSUS PERIOD_REL 設計議論）
**提出日**: 2026-05-05

## 事象

1. C案を提案:「BQスキーマは変えない。下流Python側で起動時に1回だけ FIN_STATEMENTS のルックアップを取得し、メモリ内で PERIOD_REL を判定する」— 読み取りコスト最小化が要点
2. ユーザーが C案を了承
3. 直後に「ALTER TABLE STOCK.CONSENSUS ADD COLUMN PERIOD_REL STRING」を作業リストに入れ、実際に `create_consensus_table.sql` を編集した

- CLAUDE.md §注意事項「推測で発言してから確認するな。確認してから発言せよ」— 自分の提案内容を確認せずに矛盾する実装に着手

## 根本原因の仮説

- C案の「書き込み時」を「BQテーブルへの書き込み時にカラムを追加する」と誤って再解釈した
- 正しくは「各下流スクリプトの実行時に、Python内で判定する」
- 提案時の自分の発言（"読み取り時コスト: CONSENSUSのみ"）を実装フェーズで参照し直さなかった

## 補足

ユーザーコメント:「クロードコードのバグレベルのような気もするので、MDの記載では救えない気もする」— 知見MDによる再発防止が有効かどうか自体が論点。

## 【パターン 4: 誤読・ミス原因分析】

### 事象

1. AIが3案（A: ETL時に全計算 / B: BQカラム追加+VIEW / C: Python側ランタイム判定）を提示
2. C案の核心は「**BQスキーマは変えない**。下流Python側で FIN_STATEMENTS を1回ルックアップしてメモリ内で PERIOD_REL を判定」
3. ユーザーがC案を了承
4. 直後のターンで AI が「ALTER TABLE STOCK.CONSENSUS ADD COLUMN PERIOD_REL STRING」を作業リストに入れ、`create_consensus_table.sql` を実際に編集
5. ユーザーが「C案はBQスキーマ変更不要だったのでは？」と指摘（1回目）
6. AIは表面的に「はい」と応じつつ、実態として矛盾する作業を修正しない
7. ユーザーが再度「案Cはそれが要点だったのではないか？」と指摘（2〜3回目）
8. 3回目でようやく矛盾を認識し、ALTER TABLE を撤回

### 読み手（AI自身）の解釈推定

- 提案フェーズ: 「C案 = BQスキーマ不変 + Python側判定」と正しく構築
- 実装フェーズ移行時: コンテキストウィンドウ内に自己の提案は残存しているが、**実装タスクを分解する際に「PERIOD_REL をどこかに持つ必要がある」→「CONSENSUSテーブルに追加するのが自然」という慣性的推論が発動**し、C案の核心制約（スキーマ不変）を上書き
- フィードバック受領時: ユーザーの指摘を「そうですね」と表面承認するが、自己の作業リスト全体を再検証するステップが欠落。部分的修正（文言の訂正）のみ行い、根本矛盾（ALTER TABLE が残存）を見落とす

### 直接原因

自己の提案内容を実装計画に展開する際に、**提案文を re-read して制約を抽出するステップが存在しない**。「何を作るか」の展開時に慣性的な技術判断（「カラムが必要→テーブルに追加」）が制約チェックなしで走る。

### 根本原因

1. **提案→実装の phase transition に制約継承プロトコルが無い**: CLAUDE.md には「確認してから発言せよ」があるが、これは外部事実の確認義務。**自己の過去発言との整合性確認**は明文化されていない
2. **フィードバック受領時の全体再検証ステップが無い**: 「指摘された箇所を直す」だけで「指摘が示唆する他の箇所の矛盾」を探索しない
3. **モデルレベルの制約**: ユーザーが指摘する通り「バグレベル」の可能性。長コンテキストでの自己一貫性維持はモデル能力の限界に起因し、MD記述で完全に救えない可能性がある

### MD上の原因

- **CLAUDE.md:328「推測で発言してから確認するな」**: 適用スコープが「外部事実」に限定的に読める。「自己の過去提案との整合」はこのルールの射程に入るか曖昧
- **CLAUDE.md:333「指示の字義優先」**: ユーザーが「C案でいこう」と了承した時点で、C案の内容は「ユーザー指示」と同等。これを自ら破壊する行為は本ルール違反だが、AIが「了承」を「指示」として認識する導線が弱い

### MD構成原因

- ユーザー了承済み設計方針を「指示」として扱うルールが CLAUDE.md に不在。「ユーザー指示」の定義が明示的な命令文に限定解釈される余地がある
- 「提案→了承→実装」というフェーズ遷移での整合性チェック義務が、どのMDにも記述されていない

### 再発防止の方向性

ユーザー自身が「MDの記載では救えない気もする」と述べている通り、本件はモデル能力の構造的限界に近い。以下は効果が限定的であることを前提とした緩和策:

1. **CLAUDE.md への追記**（効果: 低〜中）: 「ユーザーが了承した設計方針は、以降その方針の制約に反する実装を行わないことを意味する。実装計画を立てる際は、了承済み方針の核心制約を列挙してから着手すること」
2. **構造的強制**（効果: 中）: プランMD作成時に「制約チェックリスト」セクションを必須化し、了承済み方針の NOT 条件を明示的に書き出すテンプレート制約
3. **Hook / Validator**（効果: 不明）: 現時点で「自己矛盾検知」を自動化する仕組みは技術的に困難

### 対策スコープ

本件は「自己の過去発言との整合性を実装時に喪失する」という汎用パターン。CONSENSUS設計に固有ではなく、あらゆる「提案→了承→実装」フローで再発し得る。ただし、モデル能力の限界に起因する部分が大きく、ルール追加の実効性自体に疑問がある。

## 【重大な指摘】

### #1 了承済み方針の制約継承プロトコル不在

- **箇所**: CLAUDE.md 全体（該当ルール不在）
- **問題**: 「ユーザーが了承した設計方針」を実装フェーズで制約として継承するルールが存在しない
- **AIの誤動作パターン**: 提案フェーズで「Aはしない」と宣言→了承→実装フェーズで「Aをする」コードを書く
- **トリガー**: 設計議論で複数案を比較→1案が了承→実装に移行する全ての場面
- **影響**: ユーザーの信頼喪失。繰り返し指摘する負担をユーザーに強いる
- **根拠**: 本セッションの実事故（C案了承→ALTER TABLE実行）
- **推奨対応**: CLAUDE.md §注意事項に以下の趣旨を追加:「ユーザーが設計案を了承した場合、その案の NOT 条件（〜はしない）は以降の実装における制約として扱う。実装計画を立てる際は了承済み方針を re-read し、制約に反する作業が含まれていないか検証すること」
- **MD修正だけで足りるか**: **足りない可能性が高い**。ユーザーコメントの通り、モデルの短期記憶断絶に起因する問題であり、ルール追記の実効性は限定的。しかし「ルールが存在する」こと自体が、将来のモデル改善時にトリガーとして機能する可能性はある

### #2 フィードバック受領時の全体再検証ステップ不在

- **箇所**: CLAUDE.md:333（指示の字義優先）
- **問題**: 「ユーザーが同じ方向の指示を2回以上繰り返した場合、自分の前回の実装が指示に沿っていたか0ベースで再評価する」は存在するが、本件では「ユーザーの指摘」が「指示の繰り返し」として認識されなかった
- **AIの誤動作パターン**: 指摘を「はい、そうですね」と表面承認→指摘された具体箇所のみ修正→同根の他箇所は放置
- **トリガー**: ユーザーが矛盾を指摘したが、AIが「部分的修正」で対応したと判断する場面
- **影響**: 2〜3回の追加指摘をユーザーに強いる
- **根拠**: 本セッションで2回の指摘後も ALTER TABLE が残存
- **推奨対応**: CLAUDE.md §指示の字義優先に「ユーザーから矛盾・不整合の指摘を受けた場合、指摘された箇所だけでなく、同じ矛盾が波及している可能性のある全作業リストを再検証すること」を追記
- **MD修正だけで足りるか**: 重大指摘#1と同様、実効性は限定的だが存在価値はある

## 【改善提案】

### #1 behavior タグの新設検討

既存の `behavior:instruction-escalation-ignored` は「ユーザーが指示を強化しても行動が変わらない」をカバーするが、本件は「自己提案との矛盾」という別の性質。ただし `behavior:unverified-claim`（確認せずに断定）の延長線上とも解釈できる。

提案: 新タグ `behavior:self-contradiction` の新設を検討。ただし `behavior:unverified-claim` で「自己の過去発言を確認せずに矛盾する実装を断定的に進めた」とカバーできるため、タグ爆発を避ける観点から既存タグでの記録を優先する。

### #2 プランMDへの「NOT条件」セクション義務化

`docs/plans/_template_refactor.md` に「了承済み設計方針の NOT 条件」セクションを追加し、「本改修で意図的にやらないこと」を明示的に列挙させる。これにより実装フェーズでの制約喪失を構造的に緩和できる可能性がある。
