## 【パターン 4: 運用事故 -- 自己の行動不備記録】

### 事象

2020-H1バックフィルが 2026-05-03 02:06-06:53 JST に完了。load w5ps6 (4h56m) + 3 workflow 並列 (Q1/Q2a/Q2b) で9h43m。しかし087メトリクスMD・プランMD・memoryのいずれも更新されなかった。ユーザーが「2020 1h 終わってる」と指摘して発覚。

### 既存ルールの文言は AI が理解可能だったか

**Yes**。3件のルール全てが具体的かつ明確:
- CLAUDE.md L258: 「バックフィル等のマイルストーン完了時（プランMDのステータス更新と同時）」
- memory feedback_proactive_plan_md_update.md: 4点セットチェックリスト（087/プラン/memory/commit）
- memory feedback_backfill_metrics_auto.md: 「ジョブ完了検知時、命令なしで」

文言の曖昧性やMD構成の問題でAIが誤読した可能性は低い。**これはMD問題ではなく行動問題である**。

### ルール遵守のトリガー導線は存在したか

**部分的にYes、実効的にはNo**。

導線の存在:
- CLAUDE.md §知見ファイル整合義務 → 発火タイミング「バックフィル等のマイルストーン完了時」 -- **導線あり**
- memory feedback 2件 -- session開始時にメモリとしてロードされるため **導線あり**

導線の実効性の問題:
- いずれも**AIが能動的に参照する必要がある受動的ルール**。「バックフィルが完了した」というイベントを検知した時点でルールを想起し、チェックリストを実行するという**意志依存の連鎖**に依存している
- バックフィルは深夜〜早朝に完了することが多い（本件は02:06-06:53 JST）。完了時点でセッションが終了しているか、コンテキスト圧縮後に復帰している可能性が高く、**ルール想起のきっかけが失われる**

### 構造的強制で防げた事故か

**Yes**。以下の構造的強制が存在しなかった:
1. `monitor_backfill.py` の完了コールバックに087/プラン/memory更新を組み込む仕組み
2. workflow完了時のntfy通知に「087/プランMD更新を忘れるな」のリマインドを含める仕組み
3. セッション開始時に「未記録の完了バックフィルがないか」をチェックする仕組み

### 直接原因

バックフィル完了がセッション中断（深夜完了）を跨いだため、完了検知→記録の一連の流れが途切れた。新セッション開始時に「完了済みだが未記録のバックフィルがあるか」を確認するプロセスが存在しなかった。

### 根本原因

**041→054→060→064 の4連続再発が示す構造的問題: 意志依存型ルールの限界**

| # | 事故 | 日付 | 対策 | 対策の種別 |
|---|------|------|------|-----------|
| 1 | MR-041 | 04-30 | CLAUDE.md §知見ファイル整合義務 追加 | ルール追加（意志依存） |
| 2 | MR-054 | 05-01 | feedback_proactive_plan_md_update 追加、feedback_backfill_metrics_auto 拡張 | ルール追加（意志依存） |
| 3 | MR-060 | 05-02 | feedback_gcp_md_sync 追加 | ルール追加（意志依存） |
| 4 | MR-064 | 05-03 | **本件** | -- |

4回の事故に対して毎回「ルール文言の追加・拡張」で対策し、全て意志依存型。構造的強制（hook/validator/自動チェック/完了コールバック）は一度も導入されていない。

**意志依存型対策が機能しない理由**:
1. **コンテキスト圧縮・セッション断絶**: 深夜完了のバックフィルはセッション跨ぎになりやすい。新セッションではルール想起のきっかけ（「完了した」というイベント）が失われる
2. **ルール数の増加による注意分散**: CLAUDE.md + memory feedback が増えるほど、個別ルールへの注意配分が低下する
3. **タスク集中バイアス**: 次のバックフィル投入やユーザーからの新タスクに注意が向き、直前の完了記録義務が後回しになる

### MD上の原因

今回はMDの文言・構成に起因する誤読ではない。ルールは明確に記載されており、AIが正しく読んでいれば遵守可能だった。問題は**ルールの発火メカニズムが意志依存**であり、コンテキスト断絶時に発火しないこと。

### 再発防止の方向性

意志依存型ルール追加の限界が証明された。構造的強制へのエスカレーションが必要:

1. **monitor_backfill.py 完了コールバック**: workflow全完了時に、087/プラン/memoryの更新リマインドをntfy通知として送信する
2. **セッション開始時の未記録チェック**: CLAUDE.md またはスキルに「セッション開始時、直近のバックフィルYAMLの完了状態と087 MDの最新エントリを突合し、未記録があれば記録を優先実行」を追加（ただしこれも意志依存のためエスカレーション不十分）
3. **monitor_backfill.py に記録自動化を組み込む**: 完了検知時にログからメトリクスを収集し、087 MDの所定セクションに追記するスクリプト機能を実装する

MD修正だけでは防げない問題として、以下のソースコード・仕組み側の改善を指摘する。

### S1: monitor_backfill.py への完了時リマインド機能

- 対象: `scripts/monitor_backfill.py`
- 理由: 4度の再発が証明するとおり、意志依存型ルール（CLAUDE.md + memory feedback）では「バックフィル完了→MD更新」の連鎖が断絶する。特に深夜完了でセッション跨ぎになるケースで機能しない
- 推奨対応:
  - (最小): monitor_backfill.py の全ステップ完了時のntfy通知メッセージに「[要対応] 087メトリクス + プランMD + memory 更新を実行せよ」のリマインドテキストを含める
  - (中): 完了時にCloud Runログからメトリクスを自動収集し、087 MDの追記案をntfy通知に含める（AIが確認してcommitするだけの状態にする）
  - (最大): 完了時に087 MDへの自動追記 + プランMD更新 + git commitまで自動化する
- 検証方法: 次回バックフィル（2020-H2）完了時に、リマインドが届き記録が実行されるか確認

### S2: セッション開始時の未記録バックフィル検出

- 対象: CLAUDE.md またはセッション開始チェック
- 理由: セッション跨ぎでルール想起が失われる問題への対策
- 推奨対応: CLAUDE.md §起動時メニュー 近辺に「バックフィル実行中の場合、monitor_backfill.py のステータスと087 MDの最新エントリを突合し、完了済み未記録があれば記録を優先実行」を追加。ただしこれも意志依存であるため、S1の構造的強制と併用が望ましい

- 重大指摘 #2（注記追記）: CLAUDE.md §推測ではなく確認（「推測で発言してから確認するな」）と整合。docs数差異の原因を明記することで推測を排除
- 重大指摘 #4（構造的強制）: CLAUDE.md §知見ファイル整合義務の発火タイミングに「バックフィル等のマイルストーン完了時」が既に記載されており、この義務をコード側で強制する方向性はCLAUDE.mdの意図と整合する
- ソースコード波及 S2（CLAUDE.md追記案）: CLAUDE.md §起動時メニューとの関連。既存メニュー（1-3）にバックフィルステータスチェックを追加する形。ただし、毎セッション開始時に実行するチェックが増えることで、セッション開始のオーバーヘッドが増加する副作用がある。バックフィル実行中でない場合は不要なチェックとなるため、「バックフィル実行中の場合のみ」の条件付きが適切

### 副作用シミュレーション（8c）

**(i) 単体副作用**:
- 087 MDのセクション並び替え後、「最新の追記を末尾に行う」運用との衝突。現在は追記順（新しいデータが末尾に追加される）だが、並び替えると「年代順の正しい位置に挿入する」必要がある。これにより「追記位置の判断」という新たな負荷が発生する。ただし2020-H2以降は年代順に進行するため、実質的には「見積もりサマリの手前に追記」で済む
- 見積もりサマリ再計算後、残推定時間が小さくなることで「急いで投入しなくても余裕がある」という誤った安心感を与える可能性は低い（推定52h残は依然として大きい）

**(ii) クロスルール競合**:
- ソースコード波及 S1（ntfyリマインド追加）と既存のCLAUDE.md §知見ファイル整合義務は競合しない。S1はルールの強制発火メカニズムであり、ルールの内容自体は変わらない
- S2（セッション開始時チェック）とCLAUDE.md §起動時メニューは同一セクションに共存することになるが、起動時メニューが「ユーザーの最初のメッセージが新規タスク指示でない場合」のみ表示されるのに対し、S2のチェックは「バックフィル実行中であれば常に」となる。この条件の違いを明示しないと、「新規タスク指示がある場合はバックフィルチェックもスキップしてよい」と誤認する可能性がある

**(iii) 状態依存シナリオ**:
- バックフィルが実行中でない期間（2017-2022完了後）は、S1の完了リマインドもS2のセッション開始チェックも不要になる。これらの仕組みが「バックフィル完了後は無効化」されるべきか、将来のバックフィル（2023年再処理等）に備えて残すべきかの判断が必要

**(iv) 再発防止策の実効性**:
- 重大指摘 #4 で「構造的強制の導入」を推奨しているが、S1（ntfyリマインド）は「リマインドを読んで行動する」点で依然として半意志依存。完全な構造的強制はS1の「最大」案（自動追記+commit）のみ
- ただし完全自動化はデータの正確性検証が不可欠であり、実装コストが高い。実用的にはS1の「中」案（メトリクス収集+追記案をntfyで送信、AIがconfirmしてcommit）が実効性とコストのバランスが良い
