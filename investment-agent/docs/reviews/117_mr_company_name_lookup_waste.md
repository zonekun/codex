# 運用事故報告: BC突合NG銘柄の会社名取得に過剰なトークン・時間を消費

- 日時: 2026-05-08 19:00 JST
- 事故発生セッション: 7282da24
- 対象: BC突合結果のNG 16銘柄の会社名取得
- パターン: 2（誤読・ミス報告に対する改善レビュー）
- レビュアー: md-reviewer
- 出力先: `docs/reviews/117_mr_company_name_lookup_waste.md`

---

## 事象

BC突合（compare_monthly_buffett.py --offline）完了後、残存NG 70件/16銘柄をユーザーに報告する際、会社名の取得に以下の無駄な手順を踏んだ:

1. `data/master/company_master.csv` を pandas で読み込み → ファイルなし
2. adapter JSON の `company_name` フィールドを1社ずつ読み込み → 大半が ticker番号のみで会社名なし
3. `data/csv/listed_info.csv` を pandas で読み込み → ユーザーがツール使用を拒否（ここで指摘）
4. BQ `and-and-and.stock_data.listed_info` → テーブル不在
5. BQ MCP `and-and-and.jquants.listed_info` → 権限エラー
6. BQ MCP `gmailpj-357912.STOCK.STOCK_CODE_LIST` → カラム名不明でエラー2回
7. 最終的に `STOCK_CODE_LIST.TICKER` + `STOCK_NAME` で取得成功

合計 **7ステップ・4回のエラー** を経て、本来1クエリで済む情報を取得。

## 根本原因

- **data_catalog.md を参照しなかった**: CLAUDE.md §データストアに「BQ SQL発行前に data_catalog.md のスキーマ定義でカラム名を確認する」と明記されているにもかかわらず、推測でテーブル名・カラム名を試行した
- **BQの銘柄マスタテーブルの所在を把握していなかった**: `gmailpj-357912.STOCK.STOCK_CODE_LIST` の TICKER / STOCK_NAME が正解だが、data_catalog.md を読んでいればカラム名 `STOCK_NAME` は即座に判明した（catalog には `STOCK_NAME` とあるが、説明文には「銘柄名」としか書かれず「会社名」の語は不在）
- **逐次試行の判断遅延**: 1つ失敗するたびに別のアプローチを試す「もぐら叩き」パターン。最初に data_catalog.md で正しいテーブル・カラムを確認していれば1回で完了

## 影響

- ユーザー体験: 会社名16件という単純な情報取得に複数ターンを消費。ユーザーが「なにこまごまやってるんだ」と指摘
- トークン消費: 不要な BQ エラー4回 + pandas 読み込み試行 + adapter JSON 読み込み16ファイル分
- 時間: 約3分の遅延

## 再発防止

1. **銘柄マスタ参照は `gmailpj-357912.STOCK.STOCK_CODE_LIST` の TICKER / STOCK_NAME を第一選択とする** — adapter JSON や ローカル CSV を逐次試さない
2. **BQ クエリ発行前に data_catalog.md でテーブル名・カラム名を確認する** — CLAUDE.md §データストアの既存ルールの再徹底
3. **会社名が必要な場面では MCP BQ ツールで1クエリ発行** — pandas ローカル読み込みやファイル探索は行わない

## レビュー依頼

CLAUDE.md §データストア / §高頻度参照テーブル、および data_catalog.md の銘柄マスタ記載が、AIに対して「会社名を引くならこのテーブル」と明確に伝えられているかを評価してほしい。伝わっていなければ改善案を提示すること。

- 期待効果: AIが「COMPANY_NAME」を探してSTOCK_CODE_LISTで見つからないという混乱パターンを防止

### #2 CLAUDE.md §データ取得フォールバック順序にdata_catalog.md参照の前提を明記
