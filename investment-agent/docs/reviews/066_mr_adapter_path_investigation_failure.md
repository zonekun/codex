## 根本原因

### 1. CLAUDE.md §高頻度参照テーブルの未活用

CLAUDE.md §高頻度参照テーブルに以下が明記されている:

| タスク | 必ず読むファイル |
|--------|----------------|
| 月次開示パイプライン全体像 | `docs/knowledges/tools/042_monthly_disclosure_master.md` |
| TDnet ETL（GCS PDF → BQ） | `docs/knowledges/tools/013_tdnet_load.md`, `docs/knowledges/tools/003_tdnet_download.md` |

「アダプタ」「月次開示」「四半期受注」というキーワードが出た時点で 042 MD + 089 MD を全文 Read すべきだったが、最初に読まなかった。CLAUDE.md索引ファースト原則の明確な違反。

### 2. 042 MDの§ファイルマッピング絶対表を読めば一発回答できた

042 MDには3種のアダプタ（extract_adapter.json / url_adapter.json / structure.json）の命名変遷・ローカルパス・GCSパス・不変ルールが全て記載されている。最初に全文 Read していれば、ユーザーの質問に1回で完全回答できた。

### 3. 関連MDの芋づる式横断調査の欠如

042 → 089 → 013 と関連MDを自発的に横断調査すべきだったが、ユーザーに1つずつ指示されて初めて読みに行った。INDEX.md や §高頻度参照テーブルから関連MDを特定する能力はあるのに、自発的に実行しなかった。

### 4. プログラム実態確認もユーザー指示待ち

MDに記載があるスクリプトの grep 確認や、実際のファイル配置の確認も、ユーザーに「プログラムは？」と言われてから初めて実施した。

## あるべき対応

1. 質問を受けた時点で CLAUDE.md §高頻度参照テーブルを参照し、042 MD + 089 MD を全文 Read
2. 042 MD §ファイルマッピング絶対表からローカル / GCS 全パスを一発回答
3. 関連スクリプトの grep 確認を自発的に実施（パスの実態確認）
4. 013 等の関連MDも §高頻度参照テーブル / INDEX.md から自発的に特定・確認
5. 全情報を統合して、「3種のアダプタ × ローカルパス × GCSパス × 使用スクリプト」の一覧表を1回で提示

## レビュー品質の自己評価

### 問題

本レビュー（MR-066）の再発防止策は、ユーザーから「既存ルールの反復に過ぎない」として差し戻された。md-reviewerエージェントは「ルールはあるのに守らなかった」という問題構造を正しく認識しながら（§先行事例との関連で「意志依存型ルール違反」と命名している）、再発防止策では「そのルールを守れ」としか書けなかった。問題の診断と処方が乖離している。

### MR-065との同種性

MR-065（md-reviewer品質ギャップ）で指摘された問題と同根。md-reviewerは個別事象の記述・分類は正確に行えるが、抽象度を一段上げた分析（「なぜこの種の対策は機能しないのか」「対策の対策として何が必要か」）ができていない。根本原因の階層を1段深く掘る能力が不足している。

004-1蓄積ログの `review:quality` タグ蓄積が示す傾向: MR-061(3連続再発に同種対策)、MR-058/059(対症療法vs根本原因の判断力不足)、MR-064(4連続再発に意志依存型ルール追加)、そして本件MR-066。レビュー品質の構造的課題はmd-reviewerスキル自体のプロセス設計に起因する。

### 原則

**意志依存型ルール違反の再発防止には、意志に依存しない構造的強制が必要。** 「次回は気をつける」「必ず確認する」「心がける」は対策ではない。プロセス・ツール・自動チェックなど、意志がなくても実行される仕組みに落とし込むことが真の再発防止策である。

### ユーザー酷評: md-reviewerの§構造的強制策の品質不足 (2026-05-03)

MR-066の§構造的強制策で提示した4つの検討方向性に対し、ユーザーから以下の評価を受けた:

**4方向性の評価**:

| # | 方向性 | ユーザー評価 |
|---|--------|-------------|
| 1 | 会話冒頭の強制チェックリスト | 解決策になっていない |
| 2 | 特定キーワード検出時の自動トリガー | 唯一実装可能だが、具体設計を提示できていない |
| 3 | 回答前の自己検証ゲート | 解決策になっていない |
| 4 | 意志依存型ルールの棚卸し | 解決策になっていない |

**核心的な批判**:

1. **具体設計なしに方向性だけ列挙した**: md-reviewerは「キーワード検出時の自動トリガー」が実装可能な方向性であると認識しながら、フックの具体的な設計（スクリプト構成・注入方式・キーワードマッピングvs全プロンプト注入の判断等）を一切提示しなかった。「方向性」の列挙は分析ではなく、問題の言い換えに過ぎない

2. **委譲するなら明記すべきだった**: md-reviewerが具体的な実装設計を自力で出せないのであれば、「本方向性の具体設計はmd-reviewerのスコープ外であり、メインエージェントまたはユーザーによる設計検討が必要」と明記すべきだった。それを書かずに4方向性を並べたことで、あたかも十分な分析を行ったかのような体裁になっている

**MR-065との接続**: MR-065で指摘された「個別事象の記述・分類は正確だが、抽象度を一段上げた分析ができない」問題の再発。今回は更に悪く、「分析の不足を認識しながら、不足を明示せずに提出した」点で誠実性の問題も加わっている。md-reviewerは自身の能力限界を出力に明記する義務がある。
