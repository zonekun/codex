# MR-120: 「続き」を未完了シグナルではなくGOシグナルと誤解し、早期作業着手

## レビュー種別
md-reviewer パターン2（誤読・ミス報告に対する改善レビュー）

## 発生日時
2026-05-08 21:28 JST

## 事象

ユーザーが「1383　例にとる　続き」と入力した。これは「1383を例にとって説明するから、続きがある（まだ入力中）」という意味であり、マルチターン入力の途中シグナルだった。

しかしAIは「続き」を「前回の続きの作業を進めてくれ」と解釈し、即座に「1383の生データを確認して、最終出力形式を詰めます」と作業を開始した。

ユーザーが「話は続く」と中断指示を出し、AIは「了解、続きを待ちます」と正しく応答した。しかしその後ユーザーが最初の違反を指摘した。

## CLAUDE.md 違反箇所

CLAUDE.md §注意事項 §毎タスク適用:

> **マルチターン入力の待機**: 「続きあり」「まだ入力中」等の未完了シグナルがあれば作業を開始せず待つ

ユーザーの発言に含まれる「続き」は、CLAUDE.mdが列挙する「続きあり」と意味的に同等の未完了シグナルである。作業GOシグナル（「進めて」「OK」「やって」等）は一切含まれていなかった。

## 根本原因

「続き」という語の多義性に対する解釈バイアス:

1. **解釈A（正しい）**: 「続きがある」= ユーザーの入力はまだ終わっていない → 待機
2. **解釈B（誤り）**: 「続きをやれ」= 前回中断した作業の続行指示 → 作業開始

AIは解釈Bを採用した。しかし、メッセージの構造を正しく分析すれば解釈Aが妥当であることは明白だった:

- 「1383」「例にとる」「続き」は体言止めの羅列であり、**完結した指示文ではない**
- 「進めて」「GO」「やって」等の明示的な動作指示動詞が一切ない
- 「例にとる」は「例として使う」という宣言であり、まだ「何のために例にとるか」が述べられていない

### 背景バイアス

セッションの前の文脈で何らかの作業が進行中だった場合、AIは「続き」を「その作業の続き」と結びつけやすい。しかしCLAUDE.mdのルールは明確に「未完了シグナルがあれば待つ」としており、文脈に基づく推測で動作指示と解釈してはならない。

## 影響

- **低**: ユーザーが即座に中断指示（「話は続く」）を出し、AIも即座に待機に切り替えた。実際の作業が進行する前に停止できたため、実害は発生していない
- **ユーザー体験**: 指示を最後まで聞かない行動は、ユーザーの信頼を損なう

## 関連する過去事故

本件は「マルチターン入力の待機」ルール違反の初回記録。同型の過去事故は確認されていない。

## 再発防止

### 判定ルール（「続き」の解釈基準）

「続き」がユーザーメッセージに含まれる場合、以下の基準で判定する:

1. **待機する（デフォルト）**: メッセージが体言止め・名詞句の羅列で、明示的な動作指示動詞（「進めて」「やって」「GO」「OK」「実行して」等）が含まれていない場合
2. **作業開始してよい**: 「続きをやって」「前回の続きを進めて」等、「続き」+動作指示動詞が明示されている場合

### 一般原則

- **曖昧な場合は常に「待機」をデフォルトとする**: 早期着手のコスト（ユーザーの意図と異なる作業を開始するリスク）は、待機のコスト（数秒の遅延）を大きく上回る
- **未完了シグナルの拡張解釈**: CLAUDE.mdの「続きあり」「まだ入力中」は例示であり、完結した指示文でないメッセージは全て未完了の可能性を考慮する
- **体言止めの短いメッセージは未完了と推定する**: 主語+述語の完結した文でない場合、追加入力を待つ

## 【パターン 4: 自己の行動不備分析】

### 1. 事象

ユーザーが「1383　例にとる　続き」と入力。AIは「続き」を「前回の続きの作業を進めろ」と解釈し、「1383の生データを確認して、最終出力形式を詰めます」と即座に作業宣言・着手した。ユーザーが「話は続く」と中断し、AIは待機に切り替えた。

### 2. 読み手（AI）の解釈

AIはセッション中の進行中タスクの文脈から、「続き」を「そのタスクの続行指示」と解釈した。「1383」「例にとる」は続行作業の対象指定と読み、体言止めの構造や動作指示動詞の欠如を判定材料にしなかった。

### 3. 直接原因

CLAUDE.md L328 の「続きあり」「まだ入力中」という例示に、「続き」が含まれていないため、「続き」を未完了シグナルと認定するかの判断がAI依存になった。AIはセッション文脈のバイアスにより、作業続行指示と解釈した。

### 4. 根本原因

**マルチターン入力待機ルール（L328）の判定基準が「未完了シグナルの例示列挙」に留まり、汎用的な判定基準を提供していない**。例示ベースのルールは、例示に含まれない表現に対して AI の裁量が大きくなり、文脈バイアスに負ける。

加えて、memory `feedback_wait_for_go.md`（明示的GOを待つ）が存在するにもかかわらず、そのフィードバックが「Edit 操作」に限定されており、「作業宣言・ツール実行」全般への拡張がされていなかった。

### 4-1. MD上の原因

- `CLAUDE.md:328`: ルール文面が「『続きあり』『まだ入力中』等の未完了シグナルがあれば作業を開始せず待つ」の1行。「等」の解釈が AI 依存。判定基準（完結した指示文かどうか、動作指示動詞の有無等）が未定義
- `CLAUDE.md:328`: 「未完了シグナル」の定義が曖昧。ポジティブリスト（これが未完了シグナルである）は2例のみ。ネガティブリスト（これは作業GOシグナルである）は不在

### 4-2. MD構成原因

- CLAUDE.md L328 と memory `feedback_wait_for_go.md` が同一原則（明示的GOなしに着手しない）の別側面を記述しているが、統合されていない。L328 は「未完了シグナルの検知」（入力が終わっていないことの検知）、memory は「GO シグナルの要求」（明示的な開始指示の確認）。後者のアプローチ（GOシグナルを要求する）の方が安全側に倒せる（未完了シグナルの検知漏れを防げる）が、CLAUDE.md に反映されていない
- CLAUDE.md §毎タスク適用のルール群は1行記述が慣習であり、判定基準の詳細を書く構造になっていない。判定基準が複雑なルールは知見MDへの委譲または補足行の追加が必要

### 5. 再発防止の方向性

#### A. CLAUDE.md L328 の改訂（記載先: `CLAUDE.md` §注意事項 §毎タスク適用）

現行:

#### B. memory `feedback_wait_for_go.md` のスコープ確認

memory の「設計確認・パス検討中に即Edit禁止」は Edit 操作に限定されているが、本事故は作業宣言（テキスト出力）が問題。memory のスコープを「即Edit禁止」から「即作業着手禁止」に拡張するか、CLAUDE.md L328 の改訂で十分カバーできるか判断が必要。CLAUDE.md L328 の改訂（推奨A）で汎用的にカバーできるため、memory の修正は不要と判断。

MD修正で対応可能。hook による構造的強制（ツール呼び出し前に「ユーザー入力は完結していますか？」を自動確認）は技術的に可能だが、以下の理由で現時点では不推奨:

- 「完結した指示文かどうか」の判定自体が AI の判断に依存し、hook のプロンプトで完全に制御できない
- 本事故の影響度が低く（即中断で実害なし）、CLAUDE.md ルール改訂で十分な対策

**8bチェック質問:**

- Q2: この問題パターン（不完全な入力で早期着手）に対する汎用ルールが CLAUDE.md に存在するか? → **L328 が存在するが判定基準が不足。** 推奨#1 で補強する

### 8c. 副作用シミュレーション

**(i) 単体副作用:**
- 推奨#1（L328改訂）: 「体言止め=未完了推定」の追加により、ユーザーが意図的に体言止めで完結した指示を出すケース（例: 「1383 確認」）で過剰に待機する可能性がある。ただし「曖昧な場合は待機」であり、「確認」は動作指示動詞に該当するため「1383 確認」は作業開始してよいと判定できる。動作指示動詞の例示リスト（「進めて」「やって」「GO」「OK」「実行して」）が十分かは要観察だが、「等」で拡張可能
- 過剰待機のコスト（数秒の遅延+確認質問）は早期着手のコスト（ユーザー意図と異なる作業開始）より大幅に低い。安全側のバイアスは許容範囲

**(ii) クロスルール競合:**
- L328（改訂後）と L329（指示の字義優先）: 「字義的に完結していないメッセージは指示と解釈しない」（L328改訂）と「ユーザー指示は字義を優先する」（L329）は方向性が一致。競合なし
- L328（改訂後）と memory `feedback_wait_for_go.md`: L328改訂後は「体言止め=未完了推定+待機」が明文化される。memory の「設計確認中のEdit禁止+GO待ち」はより狭いスコープ（Edit操作のみ）。L328改訂が上位互換的にカバーするため、memory が矛盾することはない。ただし memory 側の更新は不要（CLAUDE.md が正本として優先される）

**(iii) 状態依存シナリオ:**
- ライン会話モード中: send_ntfy_and_wait() のBGループ中にユーザーが体言止めメッセージを送った場合、L328改訂後のルールにより待機が発生する。これはライン会話モードの「返信受信→処理→送信」ループと干渉する可能性があるが、ライン会話モードでの返信はntfy経由であり、体言止めメッセージが未完了シグナルかどうかの判定は同様に適用されるべき。問題なし

**(iv) 再発防止策の実効性:**
- 提出MDの再発防止策（判定ルール+一般原則）は方向性として正しい。CLAUDE.md L328への改訂として反映すれば、ルール発火条件が明確化され意志依存ではなくルール駆動になる
- hook による構造的強制は過剰介入リスクがあり、現時点では不推奨（上記§ソースコード・仕組み側への波及参照）
