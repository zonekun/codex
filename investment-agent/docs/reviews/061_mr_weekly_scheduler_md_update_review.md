## 【パターン 4: 運用事故・自己不備分析】

### 事象

メインエージェントが以下の作業を完了:
1. `ai_processing_flow.yaml` に `recent_only` パラメータ追加+switch分岐実装
2. Cloud Scheduler `tdnet-ai-weekly` 作成（毎週土 07:00 JST）
3. デプロイ完了

しかし、関連知見MD（013_tdnet_load.md）のステータス・現況サマリ・Schedulerセクションの更新、および workflows/ai_processing_flow.yaml のヘッダーコメント更新を、ユーザーから「適宜のMDファイル更新要」と明示的に指示されるまで実行しなかった。

### 読み手がどう解釈した可能性があるか

- 次のセッションが013_tdnet_load.mdを読んだ場合、「Scheduler 未設定」「週次AI処理は手動」と解釈し、不要なScheduler作成作業を提案・実行する可能性があった
- workflows/ai_processing_flow.yaml のヘッダーに `recent_only` が記載されていなければ、手動実行時にパラメータの存在を認識できず、バックフィルpending横取り事故を誘発する可能性があった

### 直接原因

GCPリソース変更作業（Workflow改修→Scheduler作成→デプロイ）の完了に意識が集中し、CLAUDE.md §知見ファイル整合義務のチェックを失念した。タスク完了判定が「GCPリソースが動作する」で止まり、「ドキュメントが実態と整合する」まで含めなかった。

### 根本原因

1. **「タスク完了」の定義にMD更新が含まれていない**: GCPリソース変更のワークフローに「ドキュメント更新」が最終ステップとして組み込まれていない
2. **同一パターンの3度目再発（041→054→060）**: 対策が毎回「手動チェックリスト追加」で終わり、強制発火の仕組み（hook / 自動検証）が導入されていない
3. **既存ルールの認知不足ではなく遵守不足**: CLAUDE.md §知見ファイル整合義務は明確に存在しており、知らなかったのではなく実行しなかった

### 誤読を許した MD 上の原因

- CLAUDE.md §知見ファイル整合義務（L213付近）: 義務の文言は正確だが、**発火タイミングの導線が弱い**。「変更した場合」と受動的に書かれており、作業フローの特定ステップとして組み込まれていない
- 013_tdnet_load.md: 現況サマリ（L21-57）に更新日が`(2026-04-27)`と記載されているため、「最近更新されている」印象を与え、追加更新の必要性を意識しにくい構造

### 再発防止の方向性

1. **手動ルール追加はこれ以上効果がない**: 041→054→060で3回同じ対策（手動チェックリスト）を繰り返し、いずれも再発。手動ルールの限界
2. **構造的対策案**:
   - (A) デプロイスクリプト/CloudBuild末尾にMD更新チェックのリマインダーをログ出力
   - (B) コミット時のpre-commit hookで「GCPリソース変更を含むコミットにMD変更が含まれない」場合に警告
   - (C) CLAUDE.md §知見ファイル整合義務を「義務の記述」から「作業フローの最終ステップとして強制参照」に格上げ
3. **現実的な最小対策**: CLAUDE.md §知見ファイル整合義務の直後に「チェックタイミング: コード変更commit直前、GCPリソース変更直後、バッチ完了時」と明示的タイミングリストを追加
