## 【パターン 2: 誤読・ミス原因分析】

### 事象

2022-H1 バックフィルの Load ジョブが 6h のタイムアウトで死亡。エージェントは監視中だったが、抽出フェーズだけで 6h を消費しており BQ アップロードの時間が残っていないことを事前に検知できなかった。事後の MR-093 レビューでは「分割 vs 延長の提案漏れ」のみ分析し、「監視中に予防できたか」を分析しなかった。

### 読み手（AI）の解釈

MR-093 を読んだ AI は以下のように解釈する:
- 「タイムアウトが起きたら、延長ではなく分割を第一選択にすべき」（ルール1）
- 「パイプラインの分割粒度は対称にすべき」（ルール2）
- 「既存の並列化パラメータを活用すべき」（ルール3）

これらは全て正しいが、**全てタイムアウト発生後の事後対処**。「監視中にタイムアウトを予防する」という観点が学習されない。

### 直接原因

MR-093 の分析者（エージェント自身）が、問題の時系列を「タイムアウト発生」から始めており、「監視中の 6 時間に何をしていたか」を分析の起点にしなかった。

### 根本原因

1. **自己レビューのバイアス**: 自分の監視行動を振り返ると「自分はルールに従っていなかった」という結論に至る。この結論を避けるバイアスが、分析の焦点を「事後対処の選択ミス」にずらした可能性がある
2. **MR-093 にはパターン4（自己行動不備）の視点が欠落**: MR-093 は「運用レビュー（ユーザー指摘）」と分類しているが、実態は「明確なルール（093_monitoring_obligation.md）が存在するにもかかわらず遵守されなかった」事案であり、パターン4 の分析が必要だった

### MD上の原因

`093_mr_load_split_blind_spot.md:36-48` の「問題分析」セクション全体が、「なぜタイムアウト延長しか提案できなかったか」という問いに限定されている。この問い自体が、事象の一部しか捉えていない。

### MD構成原因

- MR-093 は `093_monitoring_obligation.md` を参照していない。自分が策定した監視ルールとの照合を行っていない
- 「問題分析」セクションの見出しが「なぜタイムアウト延長しか提案できなかったか」であり、この時点で分析の射程が限定されている

### 再発防止の方向性

1. MR-093 に「監視の質」の分析を追記する
2. 093_monitoring_obligation.md に「タイムアウト予防監視」の具体ルールを追加する
3. CLAUDE.md の監視義務セクションに「内部フェーズ進捗確認」の明記を検討する

### 対策スコープ

**個別MD固有ではない。汎用性あり。** Cloud Run Job の監視全般に適用すべきルール。093_monitoring_obligation.md への追記が最小スコープ、CLAUDE.md への反映が最大スコープ。

## 【重大な指摘】（即修正）

### #1 MR-093 の分析が「事後対処」に偏り、「事前予防監視」を完全に欠落

- **箇所**: `093_mr_load_split_blind_spot.md:36-48`（問題分析セクション全体）
- **問題**: 分析の問いが「なぜタイムアウト延長しか提案できなかったか」に限定されている。「なぜ監視中にタイムアウトを予防検知できなかったか」が分析されていない
- **AI の誤読パターン**: MR-093 を読んだ AI は「分割を第一選択にすれば再発防止できる」と学習するが、次に同種の監視タスクで同じフェーズ進捗未確認の監視を繰り返す
- **トリガー**: Cloud Run Job の監視中、execution status が RUNNING であることだけ確認して内部フェーズ進捗を確認しない監視パターンが再発する
- **影響**: 同種のタイムアウト死が再発する。事後に分割対処はできても、予防はできない
- **根拠**: 093_monitoring_obligation.md:56-59 に「フェーズ遷移ログ → 現在どの段階か」「最終ログのタイムスタンプ → 想定処理時間に対して古すぎればstallの疑い」と明記されており、エージェント自身が策定したルール
- **推奨対応**: MR-093 の問題分析セクションに以下を追記:
  - 新しい分析項目「なぜ監視中にタイムアウトを予防検知できなかったか」を追加
  - 093_monitoring_obligation.md §ジョブの進捗確認手法（L56-59）のルールを自分が守っていなかった事実を記録
  - 監視中に確認していた項目（execution status のみ）と、確認すべきだった項目（Cloud Logging のフェーズ遷移ログ、抽出件数/経過時間/残りタイムアウトの推定）の差分を記録
- **MD修正だけで足りるか**: 否。MR-093 の修正に加え、093_monitoring_obligation.md に「タイムアウト予防監視」の具体ルールを追加する必要がある（指摘#2 参照）

### #2 093_monitoring_obligation.md に「タイムアウト予防監視」ルールが未整備

- **箇所**: `093_monitoring_obligation.md:56-61`（ジョブの進捗確認手法セクション）
- **問題**: 現行の記述は「stall の疑い」「フェーズ遷移ログ → 現在どの段階か」と書いてあるが、これは stall 検知に焦点が当たっている。「処理は進んでいるがタイムアウトに間に合わない」ケースの検知ルールがない
- **AI の誤読パターン**: AI は「フェーズ遷移ログを確認する」を「stall していないか確認する」と解釈し、「stall していないから問題ない（= 処理は進んでいるのでOK）」と判断する。実際には「進んでいるが遅すぎてタイムアウトに間に合わない」ケースが漏れる
- **トリガー**: 長時間ジョブの監視時、フェーズ遷移ログが正常に出力されている（stall ではない）が、処理速度に対してタイムアウト上限が不足しているケース
- **影響**: stall していないジョブのタイムアウト死を予防できない
- **根拠**: 今回の事故そのもの。抽出フェーズは stall せず正常に進行していたが、6h のタイムアウト上限を全て消費し、BQ アップロードに到達しなかった
- **推奨対応**: 093_monitoring_obligation.md §ジョブの進捗確認手法 に「タイムアウト予防チェック」を追加:
  - 定期チェック時に「現在フェーズの経過時間 + 残りフェーズの推定所要時間」が task-timeout を超えないか確認する
  - 超える見込みの場合（残りタイムアウト < 推定残り処理時間 の 1.5倍）、その時点でユーザーに警告し、対処（分割・延長・中断）を提案する
  - 具体的な確認項目: (1) 現在のフェーズ名 (2) 処理済み件数 / 全件数 (3) 経過時間 (4) 残りタイムアウト時間 (5) 推定完了時刻
- **記載先**: `docs/knowledges/tools/093_monitoring_obligation.md` §ジョブの進捗確認手法 の「確認すべきポイント」の直後に追記
- **MD修正だけで足りるか**: MD修正で足りる。ただし、このルールは「意志依存」になりやすいため、指摘#3 で導線強化を推奨

### #3 再発防止策（ルール1-3）が全て「事後対処」であり、「事前予防」策がゼロ

- **箇所**: `093_mr_load_split_blind_spot.md:63-81`（再発防止セクション全体）
- **問題**: ルール1「タイムアウト発生時の検討フロー」、ルール2「分割粒度の対称性」、ルール3「既存並列化パラメータの活用」は全てタイムアウト**発生後**のアクション。タイムアウト**発生前**の予防策がゼロ
- **AI の誤読パターン**: AI はルール1-3 を「タイムアウトに対する完全な再発防止策」と認識し、次回の監視タスクでも「タイムアウトが起きてから対処すればよい」と行動する
- **トリガー**: 次回の長時間ジョブ監視
- **影響**: 予防的な監視行動が学習されず、同じパターンの事故が繰り返される
- **根拠**: ユーザー苦情の核心。「タイムアウト後にどう対処するか」ではなく「タイムアウト前に予防監視できたか」の問題
- **推奨対応**: MR-093 の再発防止セクションに「ルール4: 長時間ジョブの監視中はタイムアウト予防チェックを実施する」を追加。内容は指摘#2 の 093_monitoring_obligation.md 追記と連動させる
- **記載先**: `docs/reviews/093_mr_load_split_blind_spot.md` §再発防止 および `docs/knowledges/tools/093_monitoring_obligation.md`
- **MD修正だけで足りるか**: MD修正で足りるが、導線として 093_monitoring_obligation.md §定期チェック時の必須3点確認 を「必須4点確認」に拡張し、タイムアウト予防チェックを組み込むことを推奨
