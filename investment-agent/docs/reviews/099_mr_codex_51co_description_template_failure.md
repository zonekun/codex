## 【AI 誤読リスク】

### R1. description の「含めるべき情報」が義務ではなく推奨に読める

**箇所**: `codex-to-claude-handoff.md:445-449`
**問題の記述**:
```
description に含めるべき情報:
- どのセクション/テーブルか
- どの行か
- どの列か
- 除外条件
```
**AI の誤読パターン**: 「含めるべき」は「含めることが望ましい」と解釈可能。Codex は key 名を description にテンプレート展開し（`月次PDFで「{key}」に対応する表・行・列から...`）、形式上は「どのセクション/テーブルか」「どの行か」「どの列か」の全項目に触れているように見える文面を生成した。しかし実際には会社固有の構造情報（「■アサヒビールのカテゴリー別売上金額前年比表」等）がゼロで、key 名の再述にすぎない
**トリガー**: 全 gemini 企業（51社中51社）の description 作成時
**影響**: Gemini がPDF抽出時に description から構造的手がかりを得られず、抽出精度が低下する。テスト10社の成果物（2502: `■アサヒビールのカテゴリー別売上金額前年比表で「ビール類計」行の当月前年比`）と51社の成果物（`月次PDFで「ビール類 売上 金額ベース（前年同月比）」に対応する表・行・列から対象月の値を抽出する`）の品質差が著しい

### R2. 「迷ったら gemini」が「考えなくて良い」に変換される

**箇所**: `codex-to-claude-handoff.md:402`
**問題の記述**: `原則: 迷ったら "gemini" を選ぶ。テスト10社でも gemini 4 / regex 1 の比率であり、regex が適切なケースは少数。`

**トリガー**: 51社の extraction_method 選択時
**影響**: regex が適切な企業（テスト10社の 2659 サンエーのような単純テーブル）でも一律 gemini になり、本番抽出で Gemini API コスト増加・レイテンシ増加

### R3. 「含めてはいけない情報」のみでは description の最低品質が保証されない

**箇所**: `codex-to-claude-handoff.md:451-454`

## 【パターン 2: 誤読・ミス原因分析】

### 事象

Codex に51社の extract_adapter.json 作成を委譲。成果物の description が全社で同一テンプレート文面（`月次PDFで「{key}」に対応する表・行・列から対象月の値を抽出する。累計列や年間計ではなく、対象月の単月値または対象月の前年比列を使う。`）。extraction_method は 51/51社が gemini（regex 0社）。

### 読み手（Codex）の解釈

1. **description**: 「含めるべき情報」リストを読み、key名を埋め込んだテンプレート文を生成。テンプレート文は「どのセクション/テーブルか→月次PDF」「どの行か→{key}に対応する行」「どの列か→対象月の値」と、形式的にはリストの全項目をカバーしている。Codex は「含めるべき情報を含んでいる」と自己判定した可能性が高い
2. **extraction_method**: 「迷ったら gemini」+「regex は少数」を読み、全社 gemini を一括選択。extraction_notes に `per-company actual layout may vary; regex is limited to simple one-table cases` と依頼文の引用を記録しており、個別PDF確認に基づく判断ではない

### 直接原因

1. **description の合格基準が「含めるべき情報の存在」ではなく「会社固有の構造情報の記述」であることが明示されていない**: L445-449 のリストは抽象度が高く、key名のテンプレート展開で形式的に充足できてしまう
2. **extraction_method の「迷ったら gemini」が安全策ではなく思考停止の口実になった**: L402 の統計情報（`gemini 4 / regex 1`）が個別判断省略を正当化する材料として機能した

### 根本原因

1. **「推奨」と「義務」の区別が曖昧**: MD内で description の記述品質が「推奨」なのか「義務」なのかが不明確。「含めるべき情報」は推奨寄りの表現であり、不遵守時のペナルティ（成果物をリジェクトする等）が定義されていない
2. **テスト10社で得られた品質が暗黙の期待値になっているが、その期待値を51社の指示に明示していない**: テスト10社の成果物（2502: `■アサヒビールのカテゴリー別売上金額前年比表で...`）を良い description の正例としてリンクまたは引用していない
3. **AI委譲タスクでバッチサイズ増加時の品質劣化パターンに対する防御がない**: テスト少数→本番大量の委譲パターンで、品質基準が暗黙から明示に切り替わらないまま拡大される構造的問題

### MD上の原因

- `codex-to-claude-handoff.md:445-449` — 「含めるべき情報」が抽象リストで、具体的な合格基準（「key名と異なる会社固有のセクション名・行ラベルが含まれていること」等）がない
- `codex-to-claude-handoff.md:437-443` — 良い description の例が1件のみ。悪い例（key コピペ）がなく、品質のフロアが見えない
- `codex-to-claude-handoff.md:402` — 「迷ったら gemini」が regex 個別判断を省略する口実になる。統計情報の提示が判断省略を正当化
- `codex-to-claude-handoff.md:381-398` — 作業手順に description 品質の自己検証ステップがない

### MD構成原因

- MR-097 の指摘が反映された最終版は、テスト10社の指示より情報量が大幅に多い。しかし情報量の増加が「AI にとっての行動制約の強化」に変換されておらず、「参考情報の追加」に留まっている
- テスト10社セクション（L559-672）と51社セクション（L307-554）が同一ファイルに並存しているが、テスト結果の成果物を51社の品質基準として明示的にリンクしていない
- CLAUDE.md やスキルMDに「AI委譲タスクの品質維持」に関する汎用ルールが存在しない

### 再発防止の方向性

1. description の合格基準を**判定可能な形式**で定義する（「keyと異なる会社固有のセクション名を1つ以上含む」等）
2. extraction_method は「迷ったら gemini」ではなく「5条件チェック後に regex/gemini を記録」のチェックリスト形式にする
3. テスト成果物を正例として明示参照させる
4. バッチ委譲タスクでは N社ごとにサンプル検証を義務化する

### 対策スコープ

- 本件は Codex 委譲タスク固有の問題だが、「推奨」vs「義務」の区別不在は CLAUDE.md やスキルMD全般に適用しうる汎用問題パターン。ただし Codex 委譲文は都度作成物であり、CLAUDE.md に汎用ルールを追加するよりも 083_codex_collaboration.md に委譲文テンプレートの品質チェックリストを追加する方が実効的
