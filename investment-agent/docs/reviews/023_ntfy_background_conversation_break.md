# 023: LINE会話モード中の send_ntfy_and_wait をバックグラウンド実行し会話ループ断絶

## 発生日時
2026-04-29 07:34〜14:20 JST

## 事象
2017-H1 TDnetバックフィル監視中、LINE双方向会話モード（active: true）にもかかわらず、`send_ntfy_and_wait()` を `Bash(run_in_background=true)` で実行。返信を受信・処理するプロセスが存在しないため、会話ループが断絶した。

## 影響
- 9通の通知が ntfy サーバーに配信済み（HTTP 200）だが、全て一方通行
- ユーザーの返信（「ロット一つ目投入　見張ること」）は初回のみ受信。以降の返信は全てタイムアウト扱い
- 同時間帯に別セッション（StructureOptimizer設計）がフォアグラウンドで正常に双方向会話を維持しており、対比でこのセッションの異常が顕在化
- ユーザーが起床後「きてないぞ」「会話もーどになってない」と指摘するまで約7時間気付かず

## 根本原因
ScheduleWakeup による定期監視ループ中、「`send_ntfy_and_wait` の返信待ちでブロックされると次の ScheduleWakeup が処理できない」と誤って判断し、`run_in_background=true` を使用した。

実際には：
- `send_ntfy_and_wait` はタイムアウト制御が可能（timeout パラメータ）
- ScheduleWakeup は独立したイベントであり、フォアグラウンド実行でもブロックされない
- 「ブロック回避」を理由に会話モードの根本機能（双方向性）を犠牲にした本末転倒

## 付随ミス
ユーザーが「MDレビュワーに報告」と明確に指示したにもかかわらず、「報告も必要ですか？」と確認を挟んだ。指示を受けたらそのまま実行すべき。

## 再発防止
1. **LINE会話モード中の `send_ntfy_and_wait` は絶対にフォアグラウンド実行**（feedback memory `feedback_ntfy_foreground_only.md` に記録済み）
2. `run_in_background=true` を使ってよいのは `send_ntfy()`（一方通行通知）のみ
3. 「ブロックが嫌」は `timeout` パラメータで解決する。会話機能の無効化で解決してはならない
4. 明確な指示に対して確認を挟まない（021 と同根の問題）

## 分類
- カテゴリ: LINE会話モード運用
- 重大度: 中（機能喪失7時間、データ損失なし）
- 関連: 021_line_reply_ignored_after_background.md（同系統の問題）

## 【パターン 2: 誤読・ミス原因分析】

### 事象

LINE会話モード（active: true）で 2017-H1 TDnet バックフィル監視中、ScheduleWakeup による定期起動のたびに `send_ntfy_and_wait()` を `Bash(run_in_background=true)` で実行した。返信を処理するフォアグラウンドプロセスがないため、9通の通知が全て一方通行になり、ユーザーの返信は受信されなかった。7時間後にユーザーが異常を検知。

### 読み手がどう解釈した可能性があるか

1. **068 L222 の見出し「フォアグラウンド実行によるセッションブロック」を問題パターンとして学習**: 068 は「フォアグラウンド実行 = セッションブロック = 問題」という因果関係を示している。AIは「フォアグラウンドで実行するとブロックされるから避けるべき」と判断し、L234の「OK: バックグラウンド実行」を採用した
2. **ScheduleWakeup との競合を独自に推論**: 「`send_ntfy_and_wait` のフォアグラウンド実行中に次の ScheduleWakeup が到着したらどうなるか」を AIが推論し、「ブロックされると次の ScheduleWakeup を処理できない」と誤結論。実際には ScheduleWakeup は独立イベントでフォアグラウンドブロック中でも到着可能だが、この動作仕様が CLAUDE.md にも 068 にも記述されていない
3. **LINE会話モード中の実行方法制約を認識していなかった**: CLAUDE.md L103 は「全ての応答は send_ntfy_and_wait で送信」としか書いておらず、フォアグラウンド必須の制約は CLAUDE.md に存在しない。068 L222-236 も LINE 会話モード中/外の区別をしていない

### 直接原因

068 L222-236 が「バックグラウンド実行 = OK」「フォアグラウンド実行 = セッションブロックの問題」と記述しており、LINE 会話モード中の例外を記載していない。AI はこの記述に従いバックグラウンド実行を選択した。

### 根本原因

1. **068 の「落とし穴」セクションが LINE 会話モードを考慮していない**: 068 は `send_ntfy_and_wait` の一般的な使い方を解説しており、LINE 会話モード（CLAUDE.md L92-108）という特定のコンテキストでの制約を含んでいない。068 と CLAUDE.md の間に、コンテキスト依存の実行制約を橋渡しする記述がない
2. **CLAUDE.md ライン会話モードセクションが「実行方法」を規定していない**: L103 は「何を使うか」のみ。「どう使うか」（フォアグラウンド必須、run_in_background 禁止）は CLAUDE.md ライン会話モードの守備範囲であるべきだが欠落している
3. **021 レビューの是正が問題の上流（実行方法の禁止）ではなく下流（完了通知の処理義務）に対策を打った**: 021 は「バックグラウンド実行後に完了通知を読まなかった」問題を是正したが、「LINE 会話モード中にバックグラウンド実行すべきでない」という上流の禁止に踏み込まなかった。結果として「バックグラウンド実行 + 完了通知を読む」が正しいパターンとして暗黙的に承認された

### 落とし穴: `send_ntfy_and_wait` のフォアグラウンド実行によるセッションブロック

**事象**: `send_ntfy_and_wait()` を Claude Code の Bash ツールでフォアグラウンド実行すると、timeout（デフォルト10800秒=3時間）の間セッション全体がブロックされ、他の操作が一切できなくなる。
