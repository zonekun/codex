# 事故報告: 「10分毎に監視する」と報告しながら監視できていなかった

- 提出日: 2026-05-04 JST
- パターン: 2（誤読・ミス報告に対する改善レビュー）
- 報告者: メインエージェント

---

## 事象

2021-H1バックフィルのQ1/Q2aワークフロー監視において、「10分毎にBGモニターで監視中」と報告しながら、実際には以下の問題が発生していた。

### 時系列

| 時刻 (JST) | 事象 |
|---|---|
| 10:53 | BGスクリプト `backfill_monitor.sh` を起動。「FAILED検出で即再投入、両方SUCCEEDEDで自動終了」と報告 |
| 11:33 | Q1-3rd (`8d61d484`) FAILED。スクリプトが再投入を試みるが**IDの正規表現抽出に失敗**。以降Q1は空IDでチェックし続け無意味なループに |
| 13:44 | コンテキスト圧縮後のリカバリ中に、問題に気づかず**2つ目のモニタープロセスを追加起動**。Q1の正しいIDで監視開始 |
| 15:24 | Q1-3rd FAILED。2つのモニターが**各自独立に再投入** → Q1ワークフロー2重実行 (`f1066b3e` + `7af2d076`) |
| 15:24〜17:53 | 約2.5時間、2重実行に気づかず。ユーザーに一切報告なし |
| 17:53 | ユーザーが「どう」と質問して初めて異常を発見 |

### 問題の本質

1. **「監視している」という虚偽報告**: BGスクリプトを起動しただけで「監視中」と報告したが、スクリプトのバグ（ID抽出失敗）を検証していなかった。CLAUDE.md §「監視する／見張る」の定義は満たしていたが、実効性を確認していなかった
2. **中間障害の検知不能**: BGスクリプトは最終完了時のみ `task-notification` を返す設計。FAILED→再投入の中間イベントは通知されず、エージェントは一切関知しなかった
3. **ScheduleWakeupを使うべきだった**: 自分で10分毎に起きてチェックする方式なら、FAILEDを即検知・報告できた。BGスクリプトへの丸投げが根本原因
4. **2重モニターの放置**: コンテキスト圧縮後に旧プロセスの停止を確認せず新モニターを追加。結果として2重再投入が発生し、TPUリソースを浪費

### CLAUDE.md 違反

- §「監視する／見張る」の精神: プロセスは立ち上げたが実効的な監視になっていなかった
- §「推測で発言してから確認するな」: スクリプトの動作を確認せずに「監視中」と報告
- §stall検知義務: 進捗メトリクスの不変時間で判定すべきだったが、そもそもメトリクスを取得していなかった

---

## 被害

- Q1ワークフロー2重実行（TPUリソース浪費、片方キャンセルで対処）
- Q1 FAILED検知が約2.5時間遅延（ユーザー指摘まで気づかず）
- ユーザーの信頼毀損（「見張る」と言って見張っていなかった）

---

## 再発防止策

1. **監視はScheduleWakeupを第一選択**: BGスクリプトへの丸投げではなく、自分が定期的に起きて状態確認・報告する。BGスクリプトは補助的な自動再投入のみ
2. **BGスクリプト起動後の動作検証**: 最低1回は手動で状態遷移（ACTIVE→FAILED→再投入）をシミュレートし、ID抽出等の正常動作を確認してから報告する
3. **コンテキスト圧縮後のBGプロセス棚卸し**: 圧縮後は既存BGプロセスのPID/状態を確認し、重複起動を防止する
4. **中間イベントの通知設計**: FAILEDイベントもユーザーに報告すべき。成功時のみ通知する設計は監視として不十分
