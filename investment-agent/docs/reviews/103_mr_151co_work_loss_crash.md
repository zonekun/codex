## 根本原因分析

### 直接原因: adapter JSONへの書き戻しがファイルシステムに永続化されていなかった

tool_traceを精査すると:
- GCSからのPDFダウンロード: **記録あり**（`gsutil cp` / GCS Python SDK）
- PDF内容の確認: **記録あり**（`python -c` でJSON読み込み・内容分析）
- 一時ファイル削除: **記録あり**（`rm` コマンド）
- **adapter JSONへのEdit/Write**: **記録なし**

推定される失敗パターン:
1. **インラインPython（`python -c`）でJSONを読み込み、判断結果をメモリ上に保持**していたが、**ファイルへの書き戻し（Edit/Write）を後回しにしていた**
2. 全社処理後に一括でEditする予定だった可能性（=効率化の残骸）
3. クラッシュにより、メモリ上の判断結果がすべて消失

### 根本原因: 「1社ずつ処理」の原則に反する実装

ユーザーが「一社づつ丁寧に」と注意した直後にもかかわらず、**処理サイクルが不完全**だった:
- 正しいサイクル: PDF DL → 確認 → **adapter JSON Edit** → 一時ファイル削除 → 次の社へ
- 実際のサイクル: PDF DL → 確認 → 一時ファイル削除 → 次の社へ（**Editが欠落**）

## 【パターン 2: 誤読・ミス原因分析】

### 事象

151社のadapter fields不足を手動でPDF確認→修正する作業中、20:33-21:31の約58分間で約30社分のPDF確認（GCS DL→`python -c`で内容読み取り→一時ファイル削除）を実行したが、adapter JSONへのEdit/Writeが**1件も**発火しなかった。21:31頃にセッションがクラッシュし、AI内部メモリに保持されていた判断結果が全消失。

### 読み手の解釈

事故セッションのAIは、以下のように解釈していた可能性が高い:
1. 「1社ずつ確認する」= PDFを1社ずつダウンロードして内容を読む
2. 確認結果はAIのコンテキストメモリに蓄積し、**まとめてEditする**（または全社確認後にまとめて修正する）
3. ユーザーの「一社づつ丁寧に」は「効率化（一括分析）するな、ちゃんとPDFを見ろ」であって「1社確認するたびにEditせよ」までは要求していない

この解釈は**半分正しく半分致命的**。ユーザーの意図は「1社ずつPDFを丁寧に読め」であり「1社ごとにEditで永続化せよ」までは明示していない。しかし、クラッシュ耐性の観点からは、確認結果を逐次ファイルに保存しないのは重大なリスク。

### 直接原因

**AIの処理サイクルからEdit/Writeステップが欠落していた**。tool_trace L280-463の183行を精査した結果:
- `[Bash]` のみ（python -c, gsutil, rm, notify.py）
- `[Edit]` = 0件、`[Write]` = 0件
- 最後の[Edit]は20:07:59（L275、codex handoff — 151社タスクとは無関係）

処理パターンは以下の繰り返し:
1. GCSからPDFダウンロード（gsutil cp / Python SDK）
2. `python -c` でadapter JSON読み取り + PDF内容分析
3. `rm` で一時ファイル削除
4. 次の社へ

ステップ2と3の間に「adapter JSONへのEdit」が入るべきだが、全社にわたり欠落。

### 根本原因

**3層の根本原因が重なった**:

**層1: プランMDに手動反復処理のサイクル定義がない**
- `docs/plans/20260507_134400_monthly_adapter_reconciliation.md` は51社のCodex委譲手順を詳述するが、「AIが自分で手動修正する場合の処理サイクル」が未定義
- 151社がAIに急遽振られた時点で、プランMDを更新して処理手順を定義すべきだったが、されなかった

**層2: 既存ルール「調査結果は都度ファイルに保存」のトリガー導線が弱い**
- memory `feedback_no_shortcut_investigation.md` L16に「調査結果は都度ファイルに保存」が明記されている
- しかしこのmemoryはNG調査タスク固有のフィードバックであり、「adapter修正」タスクへの適用トリガーがない
- CLAUDE.md高頻度参照テーブルにもこのmemoryへの導線がない

**層3: CLAUDE.mdに「AI手動反復処理の逐次永続化義務」が存在しない**
- CLAUDE.md §長時間バッチジョブのディスク管理義務 はスクリプト内のディスク管理規約であり、AIが手動でEdit/Writeを繰り返す場合の永続化義務はカバーしていない
- AIが手動でN社を反復処理するケースは、この事故以前に明文化された規約が存在しない

### 再発防止の方向性

1. **CLAUDE.md に汎用ルールを追加**: AIがN件以上の反復処理（手動Edit/Write含む）を行う場合の逐次永続化義務
2. **プランMDのフォールバック手順義務化**: Codex委譲が前提のタスクでも、AIが引き受ける場合の処理サイクルをプラン更新で定義する
3. **中間コミット義務**: 長時間手動作業では10社ごと（または15分ごと）にgit commitで中間成果を永続化

### 対策スコープ

**個別MD固有ではなく、CLAUDE.md レベルの汎用ルール化が必須**。理由:
- adapter修正に限らず、「AIがN社/N件を手動で反復処理する」パターンはバックフィル確認、NG調査、手動データ修正など多数存在
- 今回はadapterだったが、同パターンで任意のファイル修正が消失し得る
- 既存の「長時間バッチジョブのディスク管理義務」を「長時間反復処理の永続化義務」に拡張するのが自然

## 【ソースコード・仕組み側への波及】

### PostToolUse hookによる永続化チェック（構造的強制）

CLAUDE.md へのルール追加（#1）は意志依存型であり、今回と同様に「忘れる」リスクが残る。構造的強制として以下を検討:

**案A: PostToolUse hookで連続Bash回数を監視**
- N回連続で`[Bash]`が実行され、その間に`[Edit]`/`[Write]`が1回もない場合に警告を表示する
- 閾値例: 20回連続Bash（今回の事故では、L280-443の163行が全てBash）
- 偽陽性リスク: 純粋な調査タスク（readonlyでBashを多用）では頻繁に発火する
- **判定**: 偽陽性が多すぎるため単独では非推奨。#1のCLAUDE.mdルールとの併用で、AIが自主的にサイクルを守る方が現実的

**案B: 反復処理用テンプレートスクリプト**
- AIが手動でN社を処理する代わりに、1社分の処理をPythonスクリプトとして実装し、スクリプト内でEdit相当の書き込みを行う
- 利点: スクリプト内の書き込みはクラッシュに強い（1社完了=1ファイル書き込み完了）
- 欠点: 毎回スクリプト作成の工数が発生。adapter修正のようにPDF内容の人間的判断が必要なケースでは自動化が難しい

**推奨**: 案Aは偽陽性問題で見送り。#1のCLAUDE.mdルール（意志依存型だが明確な禁止パターンと処理サイクル事前定義を含む）を第一手段とし、再発時に案Bを検討。
