## 【パターン4: 新規計画評価】

### 技術選定の妥当性

**評価: 適切**

Markdown分割＋INDEX方式はこのプロジェクトの運用に合致している。根拠:

1. **2段階ルックアップは既存パターンと整合**: CLAUDE.md の高頻度参照テーブル → 知見MD という既存の2段階参照パターンと同じ構造であり、AIの動作として自然。新しい参照パターンの学習コストが低い
2. **粒度がBQテーブル単位**: 1テーブル = 1ファイルは、実際のクエリ作業（1回にスキーマを参照するテーブルは通常1-3個）と一致する。過分割（カラム単位）でも過粗（BQ全テーブル1ファイル）でもない
3. **GCS/CSV/APIの層別分割**: BQテーブルと異なり層全体が1ファイルなのは、各層のエントリ数が少ない（GCS 90行、CSV 154行、API 89行）ことから妥当。将来GCSが肥大化した場合にさらに分割可能な構造になっている

**1点の懸念**: `bq_fin_summary.md` が375行と突出して大きい。他のBQファイルの平均が約55行であることを考えると、`fin_summary` テーブルと `v_fin_summary_actual_for_q_on_q` VIEW を別ファイルにする選択肢がある。ただし、この2つは親子関係（VIEWの実体がfin_summary）であり、参照時は常にセットで必要になるため、現状の1ファイル方式で問題ない。

## 【重大な指摘】（即修正）

### #1 `load_catalog()` の戻り値変化に対する判断が欠落

- 箇所: `docs/plans/ad-hoc_data_catalog_split_20260508_225000.md:49`（影響を受けるコード・ドキュメント テーブル）
- 事象: 計画は `append_entry()` の問題のみ記載し、Phase 3 ステップ9で廃止予定コメントを付与する方針。しかし `load_catalog()` についての判断が完全に欠落している。分割後、`load_catalog()` は1,617行のフルテキストではなく120行のインデックスのみを返す。`discovery.py` L53 で `catalog = load_catalog()` を呼んだ後、LLMにカタログ内容を渡してデータ存在確認をする設計になっている
- トリガー: 将来 `discovery.py` の `check_availability()` を実装する際に、`load_catalog()` がスキーマ情報を含まないインデックスのみを返し、LLMがデータの有無を正確に判定できない
- 影響: `discovery.py` 実装時に `load_catalog()` の改修が暗黙の前提条件になるが、計画に記載がないため、実装者が気付かずインデックスのみでLLM判定を走らせる可能性がある
- 根拠: `src/datastore/catalog.py:14` — `CATALOG_PATH = Path("data_catalog.md")`、`src/datastore/discovery.py:53` — `catalog = load_catalog()`
- 推奨対応: 計画のリスクセクションに「`load_catalog()` の戻り値がインデックスのみに縮小するため、将来 `discovery.py` を実装する際は `load_catalog()` の改修（または個別ファイルの動的読み込み）が必要」と追記する。コード修正は不要（現時点で `discovery.py` は未実装のため）

### #2 Phase 3 のリンク更新対象ファイル数が過小評価

- 箇所: `docs/plans/ad-hoc_data_catalog_split_20260508_225000.md:53, 116`
- 事象: 計画は「約65ファイル」が `data_catalog` を参照すると記載し、Phase 0 で棚卸しを行う方針。しかし Grep 実測では **67ファイル** が参照しており（レビューMD自体を含む）、Phase 3 ステップ8 の「Phase 0 で特定したセクション直接参照を持つMDのリンクを更新」の作業量が見積もりに含まれていない。67ファイルのうち、セクション直接参照（`data_catalog.md §` 形式）を持つものは少なくとも `docs/reviews/117_mr_company_name_lookup_waste.md`（`data_catalog.md §STOCK_CODE_LIST`）が確認できる。大半のファイルは `data_catalog.md` というファイル名参照のみ（パス不変のため書き換え不要）だが、セクション参照の正確な件数がPhase 0 まで不明であることが見積もりのリスク
- トリガー: Phase 3 実施時にセクション直接参照が想定以上に多い場合
- 影響: 見積もり超過（30-40分 → 50-70分）。ただし、git revert 可能なため致命的ではない
- 根拠: `grep -rl "data_catalog" docs/ CLAUDE.md` の実測結果
- 推奨対応: (a) 見積もりを「50-70分（Phase 0 の結果に依存）」に修正、(b) Phase 0 完了後に作業量を再評価するチェックポイントを追加
