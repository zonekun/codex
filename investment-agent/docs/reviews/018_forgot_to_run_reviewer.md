# レビューMD提出忘れ — MDレビュワー起動せず待機だけした運用ミス

- 提出日: 2026-04-29 JST
- パターン: 2（誤読・ミス報告に対する改善レビュー）
- 報告者: メインエージェント

---

## 事象

ユーザーがLINEで「レビューを待て　出てきたら再度連絡」と指示した。これは docs/reviews/017_line_mode_no_reply.md を md-reviewer（Agent サブエージェント）に提出してレビューを実行し、結果が出たら LINE で報告せよ、という意味だった。

メインエージェントは「了解。MDレビュワーの結果が出るまで待機します。」とLINEで返答したが、**md-reviewer の Agent を起動しなかった**。何もせず単に待機した。

ユーザーがしばらく待ってから「まだか」と催促して初めて、md-reviewer を起動していなかったことに気づき実行した。

### 問題の本質

1. **「レビューを待て」を受動的待機と誤解**: ユーザーの指示は「レビュワーを実行して結果を待て」の意味だったが、「誰かがレビューしてくれるのを待て」と解釈し、自分でレビュワーを起動するアクションを取らなかった
2. **md-reviewer は自動で動かない**: md-reviewer は Agent ツールで明示的に起動するサブエージェントであり、提出MDを置いただけでは何も起きない。これを理解していれば「待つ」だけでは何も進まないことは自明
3. **LINE双方向モードでの指示解釈ミス**: LINEの短文から意図を正しく読み取れなかった

### 会話ログ（該当部分）

```
[LINE返信] ('042', 'レビューを待て　出てきたら再度連絡')

AI（LINE）: 了解。MDレビュワーの結果が出るまで待機します。
（← md-reviewer Agent を起動していない。何も実行せず待機）

ユーザー（コンソール）: まだか

AI: MDレビューをまだ実行していませんでした。今すぐ実行します。
（← ここで初めて Agent ツールで md-reviewer を起動）
```

## 根本原因

「レビューを待て」の主語を取り違えた。ユーザーの意図は「（お前が）レビュー（を実行して結果が出るのを）待て（、出たら連絡しろ）」であり、メインエージェントが md-reviewer を能動的に起動する指示だった。メインエージェントは「（外部の）レビュー（結果が来るのを）待て」と受動的に解釈した。

## 再発防止

- md-reviewer のレビュー提出MDを作成したら、次のアクションは必ず Agent ツールでの md-reviewer 起動
- 「レビューを待て」等の指示を受けたら、レビュワーが起動済みか確認する。起動していなければ即起動
- LINE の短文指示で意図が曖昧な場合、解釈を確認する `send_ntfy_and_wait()` を挟む

## 【パターン 2: 誤読・ミス原因分析】

### 事象

ユーザーがLINEで「レビューを待て 出てきたら再度連絡」と指示した。メインエージェントはdocs/reviews/017_line_mode_no_reply.mdの提出MDを既に作成していたが、md-reviewer Agentを起動せず「了解。MDレビュワーの結果が出るまで待機します。」とLINEで返答した。ユーザーが「まだか」と催促するまでAgentは起動されなかった。

### 読み手がどう解釈した可能性があるか

1. **「レビューを待て」を「外部プロセスの結果を待て」と解釈**: メインエージェントは「レビュー結果が出るのを待て」と読んだ。md-reviewerが自動で起動する仕組みがどこかにあると暗黙に想定した（実際にはない）。あるいは「既に起動済みだ」と誤認した
2. **提出MD作成で「レビュー依頼の作業」が完了したと認識**: skills/md-reviewer.md:19のステップ1（提出MD作成）を実行済みだったため、「レビュー依頼は出した」と認識。ステップ2（Agent起動）が脱落した。提出MDファイルの作成自体が「レビュー依頼のアクション」に見え、Agent起動は「レビュー実行」の別タスクと認識された
3. **LINE短文の「待て」に引きずられ受動的モードに入った**: ライン会話モードの「返信待ちループ」と「レビュー結果待ち」が混同され、「次のLINE返信（=レビュー結果報告）を待つ」状態に入った。しかし報告すべきレビュー結果を生むプロセスを自分で起動していなかった

### 直接原因

`skills/md-reviewer.md:17-31` のメインエージェント側手順ステップ1（提出MD作成）とステップ2（Agent起動）の間に、LINE返信処理が割り込んだ。返信処理後にステップ2の実行が想起されなかった。手順にステップ間の遷移制約（「ステップ1を完了したらステップ2を即実行すること」）が明記されていないため、割り込み後の復帰パスがなかった。

### 根本原因

1. **提出と起動の分離**: md-reviewer手順はステップ1（提出MD作成）とステップ2（Agent起動）を別ステップとして記述しているが、これらは**アトミックに（中断なく連続して）実行すべきペア操作**である。手順書がこの制約を明示していない
2. **ライン会話モード中の非同期サブタスク起動パターンが未定義**: ライン会話モードの動作フロー（CLAUDE.md:98）は「返信受信→処理→再送信」の同期的ループを前提としている。ユーザーの指示が「サブタスクを起動して結果を待ち、出たら報告せよ」というパターン（返信処理が即座に完了せず、サブタスクの完了を非同期で待つ必要がある）に対する動作フローが未定義
3. **「レビューを待て」の主語省略とmd-reviewerの手動起動前提の組み合わせ**: md-reviewerは提出MDを置くだけでは動かない（Agent起動が必須）という知識がAIの推論に活用されなかった。「レビューを待て」を正しく解釈するにはmd-reviewerの起動メカニズムの理解が前提だが、LINE短文処理の文脈ではその知識が想起されにくい

### 誤読を許した MD 上の原因

| 箇所 | 問題 |
|------|------|
| `skills/md-reviewer.md:17-31` | メインエージェント側手順のステップ1→2間に「即座に実行」「中断禁止」の制約がない。ステップ間に割り込みが入ると2がドロップする |
| `skills/md-reviewer.md:19` | 「提出用MDファイルに書き出す」がステップ1として独立しているため、「書き出し完了=依頼完了」と誤認される余地がある |
| `CLAUDE.md:98` | 動作フロー（ループ）が同期的処理を前提。「Agent起動→完了待ち→結果報告」のような非同期サブタスクパターンへの言及がない |
| `CLAUDE.md:92-105` 全体 | ライン会話モード中に「Xを待て」型の指示を受けた場合の解釈ガイドラインが不在。「待て」が能動的（自分で起動して待つ）か受動的（外部を待つ）かの判断基準がない |
| `skills/md-reviewer.md:13` | 「md-reviewerは必ずAgentツールで起動すること」は書かれているが、「提出MDを作成したら即座にAgentを起動すること。提出MDの存在だけではレビューは実行されない」という因果関係の明示がない |

### 再発防止の方向性

1. **md-reviewer手順に「提出→起動はアトミック」の制約を追記**: ステップ1完了後、他の作業に移る前にステップ2を必ず実行する旨を明記。「提出MDを作成しただけではレビューは実行されない。必ずAgentツールで起動すること」を注意書きとして追加
2. **ライン会話モードに「非同期サブタスク起動」パターンの動作フローを追加**: ユーザーの指示が「Xを実行して結果が出たら報告せよ」の場合: (a) サブタスク（Agent/Bash等）を起動 (b) 起動した旨をLINEで中間報告 (c) サブタスク完了後に結果をLINEで最終報告。この3段階フローをCLAUDE.mdに追加
3. **「〜を待て」指示の解釈原則を追加**: 「Xを待て」は「自分でXを起動/実行し、結果が出るのを待て」が第一解釈。外部プロセスが既に動いていない限り、受動的待機ではなく能動的起動+待機を意味する

### #1 LINE短文指示の解釈原則をCLAUDE.mdに追加

- 箇所: `CLAUDE.md:92-105`（ライン会話モードセクション）
- 現状: ライン会話モード中のLINE短文は主語省略・目的語省略が頻発するが、解釈ガイドラインがない。「レビューを待て」「デプロイして」「結果見せて」等の短文で、AIが文脈から正しく意図を補完する基準が不在
- 提案: ルール節に「LINE短文で意図が曖昧な場合（主語省略・略語等）、最も可能性の高い能動的解釈を採用する。特に「〜を待て」は「自分で〜を起動/実行して結果を待て」が第一解釈。解釈に自信がない場合は `send_ntfy_and_wait()` で確認を取る」を追加
- 期待効果: 「レビューを待て」を受動的待機と誤解するリスクを低減。解釈に自信がない場合のフォールバック（LINE確認）も定義される

### #2 md-reviewer手順をステップ統合で簡素化

- 箇所: `skills/md-reviewer.md:17-31`
- 現状: ステップ1（提出MD作成）とステップ2（Agent起動）が独立ステップ
- 提案: 「1. 提出MDを作成し、**直ちに** Agentツールで md-reviewer を起動する（この2つは中断せず連続実行）」のように統合記述にする。分離している現在の記述は、ステップ間割り込みのリスクを構造的に招く
- 期待効果: ステップ間割り込みによる起動忘れの構造的リスクを排除

## 【推奨検証（Step 8）】

### 正本帰属チェック（8a）

- 推奨修正の対象は `skills/md-reviewer.md`（md-reviewerの手順正本）と `CLAUDE.md`（プロジェクト最上位ルール正本）。いずれも正本ファイルへの修正であり、正本帰属に問題はない
- memoryや知見ファイルへの詳細情報追加は推奨に含まれていない

### 上位ルール整合性（8b）

- 推奨はCLAUDE.mdの既存ルール（ライン会話モード動作フロー、破壊的操作ルール等）と矛盾しない
- 「能動的解釈を第一解釈とする」（改善提案#1）は、CLAUDE.mdの「推測で発言してから確認するな」ルール（L539）と一見矛盾する可能性があるが、「解釈に自信がない場合はsend_ntfy_and_waitで確認を取る」というフォールバックを含めているため整合する。「能動的解釈」は推測での発言ではなく、「まず実行してみる」方向の行動指針であり、実行前に確認を取ることと両立する
- CLAUDE.md自体の修正提案（重大指摘#3）について: CLAUDE.md:98の動作フローに非同期サブタスクパターンを追加する推奨は、既存の動作フロー記述の拡張であり、既存ルールとの矛盾はない

### 副作用シミュレーション（8c）

1. **「中断せず即座に」が過剰に適用されるリスク**: Agent起動前にユーザーに確認を取るべきケース（レビュー対象が不明確、追加情報が必要等）で、確認を飛ばしてAgent起動してしまう可能性。ただし、提出MDを作成している時点でレビュー内容は確定しているため、Agent起動前に追加確認が必要なケースは稀。リスクは低い
2. **「能動的解釈」が暴走するリスク**: 「デプロイして」を即座にデプロイ実行と解釈して破壊的操作を実行する可能性。ただし推奨文案に「解釈に自信がない場合はsend_ntfy_and_waitで確認を取る」を含めており、また破壊的操作は既存のCLAUDE.mdルール（破壊的操作はdry-run先行）で別途ガードされているため、能動的解釈による暴走リスクは限定的
3. **非同期サブタスクパターンの追加がフロー記述を複雑化するリスク**: CLAUDE.md:98の動作フローに非同期パターンを追加すると、フロー記述が長くなり、AI が基本パターン（同期処理）と非同期パターンを混同する可能性。ただし、非同期パターンは「サブタスク起動が必要な場合」という条件付きであり、基本パターンの上位互換として自然に包含される

### 事後確認事項（8d）

- 修正実施後、ライン会話モード中にmd-reviewerの起動を指示された場合に、提出MD作成→Agent起動が中断なく実行されるか確認する
- 修正実施後、md-reviewer以外のサブタスク（Agent/Bash run_in_background等）の起動指示でも、能動的解釈が正しく適用されるか確認する
- 「能動的解釈」ルールが破壊的操作の実行を誘発していないか（dry-runルールとの整合性）を確認する

- 同種の事故（Agent起動忘れ）の過去発生回数。md-reviewer以外のAgentベースのサブタスクでも同種の起動忘れが発生しているか
