## 【パターン4のみ: 新規計画評価】

### 技術選定の妥当性

- 対策の方向性は妥当。スキルMD（AIへの指示文書）にガードレールとして回数上限を追記するアプローチは、スクリプト本体の修正なしで制御できる正しい層への介入
- 「最大3回」の閾値について: ガードレール#6（本番投入後の大ループ）は「最大2回」。ローカル検証ループは修復サイクル内の試行錯誤であり本番投入前のため、2回より多い3回は合理的。ただし根拠が計画MDに記載されていない

### 既存システムとの統合

- [x] **ガードレール#6との棲み分け**: 計画は「#6=本番投入後の大ループ、#8=ローカル検証ループ」と意図しており方向性は正しい。ただし現行のガードレール#6の文面は「同一tickerが2ループ失敗」であり、「ループ」がStep 2起点なのかStep 3起点なのか明示されていない。新#8追加時に#6の適用スコープも明確化すべき
- [x] **Step 4 NG分岐（L247）**: 現行は `NG → Step 3に戻り修正` の1行。ここに回数上限を追記する方針は適切。ただし計画の改修後テキスト「（同一ticker最大3回まで。3回失敗→エスカレーション）」は括弧内の補足であり、AIが制御フロー指示として見落とす可能性がある。Step 4本文の箇条書きとして独立した分岐（`3回NG → エスカレーション`）を追加する方が確実
- [x] **修復サイクル（L135-166）との関係**: 修復サイクル自体は1回の試行（修正→検証）を記述しており、反復制御はStep 4のNG分岐が担う。この構造理解は計画と一致しており問題なし

### リスク・コスト

- GCP課金への影響: ガード追加はコスト削減方向のため正。76回→最大3回で大幅削減
- **計数の永続化リスク**: AIエージェントが「同一tickerで何回目か」を追跡する手段が未定義。ワーキングメモリ（コンテキスト）に依存する場合、コンテキスト圧縮やセッション跨ぎで計数が消失し、事実上ガードレールが無効化される。ただしmonthly-error-autofixは単一セッション内完結を前提としたスキルであり、通常は10社以内の処理のため、実運用上はワーキングメモリで十分対応可能と考えられる。計画MDにこの前提を明記する程度で足りる
- 撤退基準: スキルMDへのテキスト追記のみであり、ロールバックは該当行の削除で完了。リスクは極めて低い

### 抜け漏れ

- [ ] **ガードレール#6の文面明確化**: 新#8追加に伴い、#6の「2ループ失敗」が「Step 6本番結果検証での2回失敗」であることを#6側にも明記すべき。現状の#6文面だけでは、#8追加後にAIが#6と#8を同一スコープと誤認するリスクがある
- [ ] **Step 3B（DL系）への波及**: 計画はE1-E5のextract adapter修復に焦点を当てているが、DL系（D1-D4）のStep 3B→Step 4ループにも同様の回数上限がない。DL系はGemini APIを呼ばないためコスト爆発リスクは低いが、対称性の観点で検討の余地あり（任意）
- [ ] **P0-2の`--since`適用条件**: `--since`で絞り込みが有効なのはGemini adapter かつ multi_month（`overwrite_past_months: true`）の銘柄のみ。単月PDF銘柄では最新1件しか処理しないため`--since`は不要。この条件分岐を補足テキストに含めないとAIが全Gemini銘柄に一律適用し、必要な検証範囲を見落とす可能性がある

### 目的・スコープの明確性

- 非スコープ（既存フロー構造変更・パターンDB改修・スクリプト本体修正の除外）が明示されており適切

## 【重大な指摘】（即修正）

### #1 ガードレール#6と#8の適用スコープ曖昧性

- 箇所: `skills/monthly-error-autofix.md:292` (既存#6) および計画P0-1a (新規#8)
- 事象: #6「同一tickerが2ループ失敗」の「ループ」がStep 2→Step 6の本番ループなのかStep 3→Step 4のローカルループなのか文面上不明。#8追加後、AIが#6を「ローカル3回の前に2回で止める」と解釈して#8が発動しない
- トリガー: monthly-error-autofixがローカル検証で2回NGを出した時点で#6に到達したと誤認し、3回目の試行なしにエスカレーション
- 影響: ガードレール#8の3回上限が事実上2回に縮退し、修復機会を1回失う
- 根拠: 現行L292の「同一tickerが2ループ失敗」はL274の「2回目の診断ループ（Step 2に戻る。同一tickerは最大2回まで）」を指すが、ガードレールセクション単体では文脈が読めない
- 推奨対応: **[方向性]** #6の文面を「同一tickerの**本番投入後**再診断が2回失敗」のように修飾し、#8の文面には「**ローカル検証（Step 4）**」を明記して、両者の適用フェーズを区別可能にする
