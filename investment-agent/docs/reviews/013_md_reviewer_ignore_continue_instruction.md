## 事象報告

ユーザーが md-reviewer に対してレビュー依頼を行う際、「続きあり」と伝えているにもかかわらず、md-reviewer（またはメインエージェント）が入力完了を待たずに勝手にレビュー作業を開始してしまう。

1. ユーザーが「MDレビューワへの依頼　〇〇〇〇　続きあり」のように、追加情報がある旨を明示している
2. にもかかわらず、エージェントが最初のメッセージだけでレビューを開始しようとする
3. 結果として、不完全な情報に基づくレビューが走る、またはユーザーが追加情報を入力する前に作業が進んでしまう

## 【パターン 2: 誤読・ミス原因分析】

### 事象

ユーザーが md-reviewer にレビュー依頼する際、「続きあり」と明示しているにもかかわらず、エージェントが入力完了を待たずに勝手にレビュー作業を開始してしまう。不完全な情報に基づくレビューが走るか、ユーザーの追加情報入力タイミングと作業開始タイミングが衝突する。

### 読み手がどう解釈した可能性があるか

1. **メインエージェント**: ユーザーのメッセージ中に「MDレビュー」「md-reviewer」等のスキル呼び出しトリガーを検知 → スキル手順に入り、提出 MD 作成またはサブエージェント起動に着手。「続きあり」は自然言語の一部として認識するが、作業開始を止めるルールが存在しないためスルーする
2. **サブエージェント（md-reviewer）**: 提出 MD を受け取った時点で情報が揃っていると判断。提出 MD に「情報不足」「追加情報待ち」等の明示的なフラグがなければ、手順 1 から実行を開始する

### 直接原因

1. **md-reviewer.md L534-543**: 「呼び出し時にエージェントが最初にやること」の手順 1-6 にユーザー入力完了性チェックのステップがない
2. **CLAUDE.md 全体**: マルチターン入力パターンに対する汎用的な待機ルールが定義されていない
3. **md-reviewer.md L11-31 の「起動方式」**: メインエージェントの責務に「ユーザー入力が完了してから提出 MD を作成する」が含まれていない

### 根本原因

- **暗黙的な前提の未明文化**: md-reviewer の設計は「ユーザーが一度のメッセージで必要な情報をすべて提供する」ことを暗黙に前提としている。複数ターンにわたって情報が段階的に提供されるケースが設計段階で考慮されていない
- **プロジェクト全体ルールの不足**: CLAUDE.md には多数の「事前確認ルール」（data_catalog 確認、知見ファイル確認、dry-run 等）があるが、「ユーザーの入力が完了しているか確認する」という最も基本的な前提条件が欠落している。これは md-reviewer に限らず、あらゆるスキルやタスクで発生し得る汎用的な問題
- **Claude Code の対話モデルの特性**: Claude Code はユーザーのメッセージを受け取った時点でアクションを起こす傾向がある。「何もせずに待つ」という行動は、明示的なルールがなければ発生しにくい

### 誤読を許した MD 上の原因

1. **`skills/md-reviewer.md:534-543`**: 「呼び出し時にエージェントが最初にやること」が入力完了を前提とした線形フロー。分岐条件（情報不足時の待機）が設計されていない
2. **`skills/md-reviewer.md:11-31`**: 「起動方式」のメインエージェント側手順に「ユーザーの入力が完了してから提出 MD を作成する」が含まれていない。手順 1「レビュー依頼内容をすべて提出用 MD に書き出す」は「すべて」という語を含むが、これは「ユーザーが提供した情報のすべて」であり「ユーザーの入力が完了していることを確認してから」とは読めない
3. **`CLAUDE.md`（全体）**: マルチターン入力パターンへの対応ルールが存在しない。「続きあり」「まだ入力中」「追加情報あり」等の日本語シグナルを検知して待機する仕組みがない

### 再発防止の方向性

1. **CLAUDE.md に汎用的な「マルチターン入力待機ルール」を追加**: これは md-reviewer に限らず全スキル・全タスクに適用すべき。「続きあり」「まだ入力中」「追加情報あり」「not done yet」等のシグナルをユーザーメッセージ中に検知した場合、作業開始前にユーザーの入力完了を待つ
2. **md-reviewer.md の「呼び出し時にエージェントが最初にやること」に前提条件チェックを追加**: 手順 0 として「ユーザーの入力が完了しているか確認。『続きあり』『追加情報あり』等のシグナルが含まれている場合は入力完了を待つ」を挿入
3. **md-reviewer.md の「起動方式」メインエージェント側手順に入力完了確認を追加**: 手順 1 の前に「ユーザーの入力が完了していることを確認してから提出 MD を作成する」を挿入

## 【改善提案】（中優先度）

### #1 「続きあり」シグナルの正規化

- 箇所: `CLAUDE.md` 注意事項セクション
- 現状: ユーザーが入力未完了を示すシグナルは自然言語の揺れが大きい（「続きあり」「まだ途中」「あとで追加する」「not done」「追加情報送る」「もう少し待って」等）。どの表現をシグナルとして検知すべきかが不明確
- 提案: CLAUDE.md のルールにおいて、代表的なシグナル表現を例示列挙する。ただし「例示であり網羅ではない」と明記し、類似表現も含めて判断するよう促す
- 期待効果: AI が「続きあり」以外の表現でもシグナルを検知できるようになる

### #2 md-reviewer.md の手順 3 の確認範囲を拡張

- 箇所: `skills/md-reviewer.md:540`
- 現状: 手順 3「上記を復唱してユーザーに確認」はパターンと出力先の確認のみ
- 提案: 手順 3 の確認範囲に「必要な情報がすべて揃っているか」を含める。例: 「パターン・出力先・必要情報の充足を復唱してユーザーに確認する。情報が不足していると判断した場合は、不足している情報を明示して追加入力を求める」
- 期待効果: パターン判定後にもう一度情報の充足性を確認する機会が生まれる

## 【推奨検証（Step 8）】

### 正本帰属チェック（8a）

- CLAUDE.md への「マルチターン入力の待機」ルール追加: CLAUDE.md はプロジェクト全体のエージェント行動ルールの正本であり、汎用的な行動制約はここに置くのが適切。正本帰属に問題なし
- md-reviewer.md への手順 0 追加: md-reviewer.md はスキル固有の手順の正本であり、スキル固有の前提条件チェックはここに置くのが適切。正本帰属に問題なし
- memory への書き込みは推奨していない。問題なし

### 上位ルール整合性（8b）

- CLAUDE.md への追加ルールは既存ルールと矛盾しない。既存の「指示があるまで勝手に実行しない」(L233) パターンと整合的
- md-reviewer.md の手順 0 追加は、手順 3「ユーザーに確認」(L540) と重複するように見えるが、手順 0 は「入力完了の確認」、手順 3 は「パターンと出力先の確認」で目的が異なる。重複ではない
- CLAUDE.md の他の注意事項（「推測で発言するな。確認してから発言せよ」L538 等）とも整合的

### 副作用シミュレーション（8c）

- **懸念 1**: ユーザーが「続きあり」と言っていないのに AI が過剰に待機する可能性。ルール文言を「シグナルが含まれる場合」に限定し、「文脈から判断」は補助的な位置付けとすることで軽減。ただしこの判断は AI の裁量に委ねられるため、完全には防げない
- **懸念 2**: 手順 0 の追加により手順番号がずれることで、既存のレビューで「手順 3 で確認した」等の参照が崩れる可能性。しかし既存レビューは完了済みの文書であり、実行時に参照されることはないため影響は軽微
- **懸念 3**: ルール追加が md-reviewer 以外のスキル（code-reviewer, planning 等）にも影響する。CLAUDE.md 側のルールは汎用的であるため、他のスキルでも「続きあり」時に待機するようになる。これは意図した効果であり副作用ではない
- **懸念 4**: ユーザーが明示的に「続きがあるが先に始めて」と指示した場合の扱い。推奨文言は「入力完了を待つ」であり、ユーザーの明示的な上書き指示には従うべき。この点は追加文言で明記しなくても、CLAUDE.md の「ユーザーの明示的な指示を優先する」の一般原則でカバーされる

### 事後確認事項（8d）

- 推奨実施後、ユーザーが「続きあり」と言った場合に AI が実際に待機するかを確認する
- 「続きあり」以外の未完了シグナル（「まだ途中」「もう少し待って」等）でも待機が発動するか確認する
- 「続きあり」シグナルがない通常のレビュー依頼で、AI が不必要に待機しないか確認する
- 他のスキル（code-reviewer, planning 等）でもマルチターン入力時に正しく待機するか確認する
