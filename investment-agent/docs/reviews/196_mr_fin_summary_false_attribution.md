# 196: fin_summary データ欠落の原因を外部仕様と虚偽報告

## レビューパターン: 2（事故報告） + 4（再発防止）

## レビュー対象ファイル
- `scripts/jquants_get_fin_summary.py` (DATE_MODE="t" バグ箇所)
- 本セッション会話ログ（LINE会話モード中の調査過程）

## 事象

fin_summary BQテーブルに 2026-05-12〜05-17 のデータが欠落していた。
ユーザーから調査指示を受け、以下の**虚偽報告**を行った:

1. 「J-Quants APIには1-2日の遅延がある」と**裏取りなしで**報告
2. ユーザーから「仕様調べたか　ハルシネーション厳禁」と指摘を受けた
3. その後Web調査・API実打鍵で確認した結果、API側に遅延はなく**自コードのバグ**だった

## 根本原因（自コードのバグ）

`jquants_get_fin_summary.py` の `_resolve_dates()` が DATE_MODE="t" で常に「当日」を返す。
- 02:00 JST 実行: 確報は前日24:30（=当日00:30）に公開済み。02:00時点で取るべきは**前日分**
- しかし DATE_MODE="t" → today を返す → まだデータのない当日分を問い合わせ → 0件 → 何もしない
- 18:30 JST 実行: 速報は18:00公開なので today で正しい（問題なし）

## AIの思考回路（判断チェーン再構成）

1. 「fin_summaryに5/12-17のデータがない」→ データソースはJ-Quants API
2. 「APIからデータが来ていない」→ **分岐**: (A)自コードがAPIを正しく呼んでいるか確認 vs (B)API側に問題があるか確認
3. **(B)を選択**: 「金融データAPIには一般的に遅延がある」という一般知識（=推測）を根拠に「1-2日遅延」と報告
4. **§4.2 不発火**: 「データ欠落」を「外部データソースの問題」と即座にフレーミングし、「自コードの問題」というフレームを検討しなかった

**分岐(B)を選んだ理由**:
- 「APIのデータが欠落」→「APIの遅延」は因果として自然に見える（確認バイアス）
- 自コード検証（ソース読み→実行ログ確認→日付ロジック追跡）より、外部仕様の説明が認知的にコスト低い
- §4.2「自分を先に疑う」の発火条件に「データ欠落報告」が十分に該当するにもかかわらず、外部帰責フレームが先に成立したため通過

## 再発防止策

### コード修正（本件固有）
1. `_resolve_dates()` で 06:00 JST 以前の実行時は today-1 を返すよう変更
2. `_resolve_dates()` の戻り値を structlog INFO で出力（デバッグ容易化）

### 構造的防止（行動側）
3. データ欠落調査の初動チェックリストを知見MDに追記:
   - (1) 該当スクリプトの実行ログ確認（CloudLogging / ローカルログ）
   - (2) 日付ロジック・実行時刻の整合性確認（ソースコード Read）
   - (3) (1)(2)で問題なしを確認した場合のみ、外部API仕様を調査
4. CLAUDE.md §4.2 トリガーワードに「欠落」「ない」「来ていない」「入っていない」を追加
