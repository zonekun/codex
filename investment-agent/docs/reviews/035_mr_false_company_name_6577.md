## 【パターン 2 のみ: 誤読・ミス原因分析】

### 事象
BQ クエリ結果に `TICKER=6577`, `FILER_NAME=Ｇ－ベストワンドット` と表示されていた。エージェントはこの結果を受け取った直後に「6577（ベイカレント・コンサルティング）」と報告し、以降の発言でも訂正しなかった。Dropbox フォルダ名にも `6577_baycurrent_monthly` と誤名を使用した。

### 読み手がどう解釈した可能性があるか
1. **事前学習知識の優先**: LLM は事前学習で「6577」というティッカーに対して「ベイカレント・コンサルティング」という企業名を（誤って）記憶しており、BQ 結果の FILER_NAME を注意深く読む前にその記憶を出力に使った。BQ 結果の FILER_NAME は「見えていたが読んでいなかった」状態
2. **確認義務の不発火**: CLAUDE.md の「推測で発言するな」ルールは認識していたとしても、エージェントが自分の出力を「推測」ではなく「既知の事実」と分類したため、確認フローが発火しなかった
3. **複数回の報告で自己強化**: 最初の誤りが訂正されずに繰り返されたことで、エージェント自身のコンテキスト内で「6577=ベイカレント」が既成事実化した

### 直接原因
**BQ 結果の FILER_NAME 列を企業名の正本として使用しなかった。** ティッカーコードから企業名への変換を、BQ 結果ではなく事前学習知識に依存した。

### 根本原因
1. **「推測」の定義が LLM の認知モデルに合っていない**: LLM にとって事前学習から引き出した情報は「推測」ではなく「知識」。CLAUDE.md のルールが「事前学習知識であっても、手元のデータと照合せよ」という粒度で書かれていないため、AI が「推測ではないから確認不要」と判断する余地がある
2. **同型事故（014）の再発防止が構造的でなかった**: 014 事故後に「完了報告前の裏取り」はルール化されたが、「BQ 結果に含まれるデータ属性をそのまま引用する」というより一般的なルールには昇格していない
3. **ティッカー→企業名の対応はヒューリスティックに依存しやすい**: 4桁の数字から企業名を想起するのは LLM が最も得意とする連想タスクであり、それゆえに「わざわざ確認する」動機が低い

### 誤読を許した MD 上の原因
- `CLAUDE.md:262` — 「推測で発言してから確認するな。確認してから発言せよ」の「推測」が、事前学習知識からの想起を含むか不明確
- `CLAUDE.md:262` — 例示が「データ属性はBQ・CSV等で、作業完了状態はRead/git logで」と抽象的。「BQ 結果に企業名が含まれている場合はその値を使え」という具体例がない
- ユーザー向け報告にティッカーと企業名を併記する際の「企業名の取得元」に関するルールが不在

### 再発防止の方向性
1. **CLAUDE.md:262 の例示を拡充**: 「データ属性」の具体例として「ティッカー→企業名の対応」「BQ 結果に含まれるカラム値」を追加。「事前学習知識より手元データを優先」を明示
2. **「事前学習知識は推測と同等」の原則を明記**: LLM の訓練データは古い・不正確な可能性があるため、手元に正解データがある場合は必ずそちらを使うルールを追加
3. **ユーザー向け報告での企業名引用ルール**: ティッカーと企業名を併記する場合、BQ/CSV/マスタデータから取得した値を使い、記憶から補完しない
