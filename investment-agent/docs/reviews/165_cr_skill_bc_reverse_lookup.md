## 【重大な指摘】（即修正）

### #1 Step 3A「診断の武器庫」(a) と Step 3C bc_ignore判定フロー の機能重複

- 箇所: プラン P0-1 (a) および `skills/monthly-error-autofix.md:145-171`（Step 3C）
- 事象: P0-1 (a)「BC値直接照合」は 042マスターMD §bc_ignore判定基準 の手順1-5をスキルに導入するものだが、Step 3Cのbc_ignore判定フローにも「GCS文書確認 → 中身を必ず確認 → 月次データあり/なし判定」という類似の逆引き作業が含まれている。エージェントが同一tickerに対して Step 3A武器庫 → Step 3C という順で進んだ場合、BC値の照合作業を二重に実行する可能性がある
- トリガー: E1-E5修復で行き詰まり、「これはfield誤認ではなくデータ不在かもしれない」と判断が揺れたとき
- 影響: トークン浪費・混乱（軽微だが設計上の曖昧さ）
- 根拠: Step 3Aの武器庫(a)が「bc_monthly_kpi.csvからBC値を取得してソース文書で検索」、Step 3Cが「GCS文書確認 → 中身確認 → 月次データあり/なし」で、BC値を起点に文書を見る操作が共通
- 推奨対応: **[方向性]** 武器庫(a)に「この技法はfield特定が目的。データ自体が存在しないと判明した場合はStep 3Cへ」という分岐指針を1行追加する。Step 3Cとの棲み分け（武器庫=field特定、3C=データ存在判定+bc_ignore）を明示することで重複作業を防ぐ

### #2 reconcile_bc_key_from_compare.py の前提条件未記載

- 箇所: プラン P0-1 (b)
- 事象: reconcile_bc_key_from_compare.py は `--compare-csv` として比較CSV（compare_monthly_buffett.py の出力）を入力に取る。しかしmonthly-error-autofixのフロー（Cloud Runエラーからの修復）では、比較CSVがまだ生成されていない可能性がある。スキルに技法として記載する際、この前提条件を明記しないとエージェントが存在しないCSVを引数に指定して失敗する
- トリガー: 月次Cloud Runエラー修復の初回実行時（比較CSVが未生成）
- 影響: エージェントがreconcileスクリプトを実行しようとしてエラー → 不要な調査ループ
- 根拠: `scripts/reconcile_bc_key_from_compare.py:8-10` のdocstringで `--compare-csv` が必須引数
- 推奨対応: **[方向性]** スキルへの記載時に「compare CSVが手元にある場合に使える。なければ先にcompare_monthly_buffett.pyを実行するか、(a)の手動照合を使う」旨の前提条件を1行添える
