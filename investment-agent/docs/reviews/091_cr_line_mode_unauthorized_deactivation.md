## 【サマリー】

- 変更の要約: 別セッションが共有memory `line_conversation_mode.md` を `active: false` に書き換えたことで、稼働中セッションのLINE双方向会話モードが不正に停止した運用事故の分析
- 品質評価: **C** — CLAUDE.md のルール「モード終了は明示的宣言のみ」は存在するが、複数セッションが同一memoryファイルを読み書きする競合シナリオが完全に想定外。設計上の構造的欠陥
- 主要リスク:
  1. 共有memoryにセッション固有の状態を保存する設計は、セッション間競合が原理的に防げない
  2. CLAUDE.md の「明示的宣言のみ」ルールは、memory file modified 通知に対する振る舞いを定義していない
  3. 別セッションが「自分のモード解除」を意図したのに共有memoryを書き換えたため全セッションに波及した

## 【事故の根本原因分析】

### 原因1: セッション固有状態を共有リソースに保存する設計欠陥

`line_conversation_mode.md` は `~/.claude/projects/.../memory/` 配下の共有memoryファイルである。このファイルは **全セッションから読み書き可能** であり、セッション間の排他制御メカニズムは存在しない。

LINE双方向会話モードの active/inactive 状態は本質的に **セッション固有** の状態である。理由:
- ユーザーはセッションAに対して「双方向モードオン」と指示する
- セッションBには同じ指示をしていない可能性がある
- セッションBが自身のモードを解除するつもりで `active: false` と書いた場合、セッションAのモードまで破壊される

つまり、「どのセッションがLINEモードか」という情報を **セッションIDなしで** 1つのフラグとして保存している時点で、複数セッション並行時の破綻は不可避であった。

### 原因2: CLAUDE.md ルールの適用範囲が「会話内指示」に限定されている

CLAUDE.md §ライン会話モードの該当ルール:

> **モード終了は明示的宣言のみ**: 「解除」「通常モードに戻す」等のみ。タスク切替指示を終了と推測しない

このルールは「ユーザーからの会話内メッセージ」を想定している。しかし今回の事故では、**system-reminder（memory file was modified）** という会話外のシグナルによってモード解除が誘発された。ルールが想定するイベント源は:

| イベント源 | ルールの想定 | 今回の事故 |
|-----------|-------------|-----------|
| ユーザーの会話内メッセージ | 想定済み | - |
| タスク切替指示 | 想定済み（推測するな） | - |
| memory file modified 通知 | **想定外** | これが発火 |
| 別セッションによるmemory書き換え | **想定外** | これが根本原因 |

### 原因3: 本セッション側の判断ミス

本セッション側のClaude が system-reminder を受信し、`line_conversation_mode.md` が `active: false` に変わったことを検知した際、以下の推論を行ったと推定される:

1. memory に `active: false` と書いてある
2. memory はプロジェクトの正本（source of truth）
3. 従って LINE 会話モードは解除された

この推論は、**memory の値を無条件に信頼する** という前提に基づいている。しかし CLAUDE.md のルール「モード終了は明示的宣言のみ」に従えば、**memory の値が変わったことは「明示的宣言」ではない** ため、モードを解除すべきではなかった。

ルールの字義に従えば、正しい判断は:
- memory が `active: false` になったが、**本セッション内でユーザーからの解除指示は受けていない**
- 従って本セッションでは引き続き `send_ntfy_and_wait` を使用する
- 矛盾を検知したことをユーザーに報告する

## 【重大な指摘】（即修正）

### #1 セッション固有状態を共有memoryの単一フラグで管理する設計の欠陥

- 箇所: `~/.claude/projects/.../memory/line_conversation_mode.md`
- 事象: `active: true/false` の単一フラグは「どのセッションがアクティブか」を区別できない。複数セッション並行時に片方がdeactivateすると全セッションに波及する
- トリガー: 2つ以上のセッションが同時に存在し、1つがLINE会話モード中に別のセッションが起動してモードを解除する
- 影響: 稼働中セッションの双方向通信が予告なく停止。ユーザーがスマホ側にいる場合、画面確認するまで通信断絶に気づけない
- 根拠: memory ファイルはプロジェクト全体で共有。セッションIDによる排他制御機構なし
- 推奨対応: 後述の再発防止策 A または B

### #2 CLAUDE.md に「memory変更による解除は無効」の明示ルールがない

- 箇所: `CLAUDE.md` §ライン会話モード — 「モード終了は明示的宣言のみ」
- 事象: 「明示的宣言」の定義が「ユーザーの会話内メッセージ」に限定されていることが暗黙的にしか読み取れない。memory file modified 通知を受信した場合の振る舞いが未定義
- トリガー: 別セッション（または自動プロセス）が memory を書き換え、system-reminder で通知された場合
- 影響: 本事故と同一の判断ミス（memory の値を鵜呑みにしてモード解除）
- 根拠: CLAUDE.md の文面に「memory の値変更はモード解除シグナルとして扱わない」という記述がない
- 推奨対応: 後述の再発防止策 C

### #3 別セッション側の「自セッション解除」が共有状態を破壊した

- 箇所: 別セッション（セッション 2ff782ef 以外）の動作
- 事象: 別セッションが自身のLINE会話モードを終了する際に `active: false` を memory に書き込んだ。これは「自分のモード状態を保存する」つもりだったが、結果として全セッションの状態を上書きした
- トリガー: 別セッションでユーザーが「解除」と指示 → そのセッションが memory を `active: false` に更新
- 影響: 稼働中の別セッション（本セッション）のモードが破壊された
- 根拠: memory のファイルが1つしかなく、複数セッションの状態を区別して保存する構造になっていない
- 推奨対応: 後述の再発防止策 A

## 【再発防止策】

### 策A: memory の設計変更 — セッションID付きの状態管理（推奨）

`line_conversation_mode.md` のフォーマットを以下に変更:

```yaml
---
name: ライン双方向会話モード
description: LINE双方向モードの有効/無効状態とtimeout設定
type: project
---
# セッション別の状態（セッション終了時に各自が自行を削除）
sessions: []
# 共通設定
timeout: 10800
```

**問題点**: Claude Code の memory にはセッションIDをプログラム的に取得・記録する仕組みがない。memory ファイルはフリーテキストであり、セッション間の整合性を保証する排他制御もない。従って、この策は**概念的には正しいが実装が困難**。

### 策B: memory による状態管理を廃止し、セッション内状態のみで管理（推奨）

LINE会話モードの active/inactive を memory に書かない。代わりに:

1. **セッション開始時**: memory の `line_conversation_mode.md` は **timeout 等の設定値のみ** を保持する
2. **モード有効化**: ユーザーが「双方向モードオン」と指示 → セッション内で状態保持（memory には書かない）
3. **コンテキスト圧縮後の復旧**: memory に `active: true` が書いてある場合 **かつ** 本セッション内で有効化した記録がある場合のみ復旧

**問題点**: 現行の「コンテキスト縮小・リセット後の復旧義務」はmemory を source of truth として復旧する設計。memory に書かないと、コンテキスト圧縮後に状態が失われる。

**妥協案**: memory には書くが、**「memory の active フラグが false に変わっても、本セッション内でユーザーから解除指示がない限りモードを維持する」** というルールを CLAUDE.md に追記する。これが策C。

### 策C: CLAUDE.md へのルール追記（即時適用可能、最小変更）

CLAUDE.md §ライン会話モード の「モード終了は明示的宣言のみ」の直後に以下を追記:

```
- **memory 変更はモード解除シグナルではない**: 別セッション・自動プロセスが memory の `line_conversation_mode.md` を `active: false` に書き換えた場合でも、**本セッション内でユーザーからの解除指示がない限りモードを維持する**。矛盾を検知した場合はユーザーに報告し、判断を仰ぐ
- **memory 書き換え時のセッション保護**: 自セッションで LINE 会話モードを解除する際、memory に `active: false` を書く前に「他セッションがアクティブでないか」を確認する手段がないことを認識する。解除時は memory の `deactivated_by` フィールドにセッションの識別情報（開始タスクの概要等）を記載し、他セッションが「誰が解除したか」を判定できるようにする
```

**記載先**: `CLAUDE.md` §ライン会話モード — ルールセクション（「モード終了は明示的宣言のみ」の後）

### 策D: memory フォーマットの拡張（策Cと併用）

`line_conversation_mode.md` に `activated_by` / `deactivated_by` フィールドを追加:

```yaml
active: true
timeout: 10800
activated_at: 2026-05-07T00:00:00+09:00
activated_by: "セッション2ff782ef — TDnetバックフィル監視"
deactivated_at:
deactivated_by:
```

これにより、別セッションが `active: false` + `deactivated_by: "セッションXXX — 別タスク"` と書いた場合、本セッション側は「自分が有効化したセッションとは別のセッションが解除した」ことを検知でき、**CLAUDE.md の策Cルールに従って無視する** 判断が可能になる。
