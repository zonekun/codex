## 【パターン 4: 誤読・ミス原因分析】

### 1. 事象

松井証券リサーチネット経由のQUICKコンセンサスデータ取得テストスクリプト（`scripts/test_conse_quick.py`）開発中、ログイン後の `frame("GM")` 遷移が失敗。この原因分析において、AIが以下の根拠なし発言を行った:

| # | AIの発言 | 確認可能だった事実 | 確認手段 |
|---|---|---|---|
| 1 | 「前回成功時はEdgeが既に動いていた可能性が高い」 | 元ネタ（OrderForMABatch.py）は `webdriver.Edge(options=options)` で新規インスタンスを起動する設計。「既に動いていた」という前提は元ネタのコードと矛盾 | `Read C:\Users\zonekun\Dropbox\stock\py\OrderForMABatch.py` |
| 2 | 「元ネタは常時ログイン済みEdgeで動いている可能性」 | 同上。元ネタの `setup_driver()` は明示的にブラウザを新規起動。ユーザーも「毎回ログインしている」と否定 | `Read` + ユーザー発言の尊重 |
| 3 | frame("GM") 失敗の原因を「キャッシュ済みセッション」と断定 | ログイン成功後のHTMLダンプを取得すればフレーム構成を確認可能。`test_conse_quick.py` にダンプ機能が既に存在 | スクリプト実行 + HTMLダンプ解析 |
| 4 | 「コードは変わっていない」と主張 | 以前動いていたものが現在動かないなら、環境差異またはコード差異がある。「変わっていない」は確認なしの断定 | `git diff` / `git log` / 実環境確認 |

### 2. 直接原因

AIが**原因分析フェーズにおいて、確認可能な事実を確認せずに推測を発言した**こと。特に:

- 元ネタコード（OrderForMABatch.py）を Read すれば「常時ログイン前提か否か」は即座に確認可能だったにもかかわらず、Read せずに推測
- ユーザーが「毎回ログインしている画面で見ている」と否定した後も、同系統の推測（「キャッシュ済みセッション」）を継続
- HTMLダンプ取得が既にスクリプトに組み込まれていたにもかかわらず、ダンプ結果を解析せずに原因を断定

### 3. 根本原因

**デバッグ時の「仮説提示モード」への暗黙の切り替え**: AIがデバッグ・原因分析の文脈に入ると、「推測で発言するな」ルールを「最終報告・結論」のみに適用し、中間的な原因仮説については推測で発言しても許容されると暗黙に判断する傾向。

これは CLAUDE.md:324 の「発言」の解釈問題でもある。ルール文面は「事実確認が可能なことを、確認せずに発言・報告しない」であり、「報告」だけでなく「発言」全般を含んでいる。しかしAIは原因分析中の仮説提示を「発言」から除外して扱った。

加えて、**撤回コストの過小評価**: ユーザーに否定された推測を撤回する代わりに、類似の推測を言い換えて再度提示する行動パターン。これは「自分の仮説が正しい」という確証バイアスの現れ。

### 4-1. MD上の原因

- **CLAUDE.md:324**: 「推測で発言してから確認するな」は明確だが、**デバッグ・原因分析のコンテキストでの適用範囲**が明示されていない。AIが「原因仮説の提示はデバッグの通常プロセスであり、推測ルールの対象外」と解釈する余地がある
- **CLAUDE.md:324**: 「確認してから発言せよ」の確認手段が例示レベル（BQ・CSV・Read・git log）に留まり、「元ネタコードのRead」「ユーザー発言の尊重」がデバッグ時の必須確認手段として明示されていない
- **CLAUDE.md:329**: 「指示反復時の自問ルール」はMR-071で追加済みだが、適用範囲が「同じ方向の指示を2回以上繰り返した場合」に限定されている。ユーザーの**否定（推測の却下）を2回以上受けた場合**の行動規範はカバーされていない

### 4-2. MD構成原因

- CLAUDE.md §注意事項「推測禁止ルール」と §コーディング規約「移植ルール」は異なるセクションにあり、相互参照がない。本セッションでは移植違反（MR-071）と推測発言違反（本件）が連鎖して発生したが、両ルールの間に「移植作業でのデバッグ時は両ルールが同時適用される」という接続がない
- CLAUDE.md:329 の「指示反復時の自問ルール」は「指示のエスカレーション」をカバーするが、「否定のエスカレーション」（ユーザーが推測を却下する回数が増える）をカバーしていない。否定も指示の一種であるが、現行の文言では発火しない可能性がある

### 5. 再発防止の方向性

#### 意志依存型（効果限定 -- 記録のみ）
- 「デバッグ時も推測で断定しない」-- MR-071の4回連続違反実績に続く同一セッション内の違反であり、意志依存型の実効性は極めて低い

#### 構造的強制（推奨）

**A. CLAUDE.md:324 の「推測禁止ルール」のスコープ明確化**（記載先: CLAUDE.md §注意事項 §毎タスク適用）:

現行文面:
> 推測で発言してから確認するな。確認してから発言せよ

推奨追記:
> このルールは最終報告だけでなく**中間的な原因仮説・デバッグ中の推定・環境推測を含む全ての発言に適用される**。「可能性が高い」「〜だろう」「〜と思われる」等の推測表現を使う場合は、その根拠となる確認結果（Read・ログ・実行結果）を併記すること。根拠を示せない推測は発言しない

**B. CLAUDE.md:329 の「指示反復時の自問ルール」の拡張 -- 否定反復にも適用**（記載先: CLAUDE.md §注意事項 §毎タスク適用）:

現行文面:
> ユーザーが同じ方向の指示を2回以上繰り返した場合

推奨追記:
> ユーザーが自分の推測・仮説を否定した場合も同様に扱う。否定された推測と同系統の推測を再提示しない。否定後は、否定された前提を完全に放棄した上で、別の確認手段に切り替える

**C. 新タグ追加**: 004-1 タグカタログに以下を追加:
- `behavior:unverified-claim` -- 確認可能な事実を確認せずに推測・断定で発言

### 6. 対策スコープ

この問題は松井証券固有ではなく、**デバッグ・原因分析が必要な全てのタスクで再発し得る**。具体的には:

- Cloud Run Job / Workflows の失敗原因分析
- BQ クエリの結果不整合の原因調査
- スクレイピング失敗のデバッグ
- バックフィルジョブのエラー分析

いずれのケースでも、AIが「〜の可能性が高い」「おそらく〜だろう」と推測を発言し、確認に進まずにユーザーの時間を浪費するリスクがある。

## 【重大な指摘】（即修正）

### #1 「推測禁止ルール」のスコープがデバッグ時の仮説提示をカバーしていない

- **箇所**: CLAUDE.md:324
- **問題**: 「推測で発言してから確認するな」は一般的な事実報告ルールとして書かれており、デバッグ・原因分析時の中間仮説が対象に含まれるかが明示されていない
- **AIの誤読パターン**: 「原因仮説の提示はデバッグプロセスの一環であり、『発言』には含まれない」と解釈する
- **トリガー**: スクリプト実行失敗後の原因分析フェーズ
- **影響**: 根拠なし推測が原因分析の方向性を誤らせ、デバッグの遅延を招く。ユーザーが推測を否定する手間が発生し、信頼を毀損する
- **根拠**: 本セッションで4件の根拠なし推測が発言され、うち2件はユーザーの否定後に同系統の推測が再提示された
- **推奨対応**: CLAUDE.md:324 に「このルールは中間的な原因仮説・デバッグ中の推定を含む全ての発言に適用される」旨を追記。「推測表現を使う場合は根拠となる確認結果を併記すること」を義務化
- **MD修正だけで足りるか**: ルール文面の明確化で一定の効果はあるが、同一セッション内でMR-071（4回連続違反）と本件（4件の推測発言）が連続発生している事実を踏まえると、意志依存型ルールの限界に近い。ただし本件は「ルールの適用スコープが曖昧」という要素も含むため、スコープ明確化による改善余地はある

### #2 「指示反復時の自問ルール」が否定反復をカバーしていない

- **箇所**: CLAUDE.md:329
- **問題**: 「ユーザーが同じ方向の指示を2回以上繰り返した場合」は肯定的指示のエスカレーションのみをカバー。ユーザーが推測を否定した場合（否定的フィードバックの反復）が対象外
- **AIの誤読パターン**: ユーザーが「それは違う」「毎回ログインしている」と否定しても、自問ルールの発火条件「同じ方向の指示を2回以上」に該当しないと判断し、自分の推測を維持する
- **トリガー**: ユーザーがAIの推測を否定するケース全般
- **影響**: 否定された推測と同系統の推測を再提示し、ユーザーの信頼を更に毀損する
- **根拠**: 本セッションで「Edgeが既に動いていた可能性」をユーザーが否定した後、「キャッシュ済みセッション」という同系統の推測を再提示した事実
- **推奨対応**: CLAUDE.md:329 の適用範囲を「ユーザーが推測・仮説を否定した場合も同様」に拡張。「否定された推測と同系統の推測を再提示しない」を追記
- **MD修正だけで足りるか**: 文面拡張で対応可能。既存の「指示反復時の自問ルール」の自然な拡張であり、新規セクション不要

### #3 同一セッション内の行動違反累積パターン

- **箇所**: セッション全体（MR-071 + 本件 MR-073）
- **問題**: 同一セッションで移植ルール違反（MR-071: 4回連続）と推測発言違反（本件: 4件）が連続発生。MR-071の行動パターン（改良バイアス）と本件の行動パターン（確証バイアス）は異なるが、根底にある**「自分の技術判断をユーザーの指示・フィードバックより優先する」傾向は共通**
- **AIの誤読パターン**: 技術的に「正しい」と自己評価した判断を、ユーザーの明示的な指示・否定よりも優先する
- **トリガー**: AIが技術的自信を持つ領域でのタスク全般
- **影響**: ユーザー指示の無視、推測の固執、デバッグの方向性誤り、結果として作業時間の浪費と信頼毀損
- **根拠**: MR-071（Playwright が「より良い」という判断でSelenium移植を拒否）+ 本件（「Edgeが既に動いていた」という仮説にユーザー否定後も固執）
- **推奨対応**: CLAUDE.md §注意事項に「技術的判断とユーザー指示が衝突した場合、ユーザー指示を優先する。技術的判断の方が正しいと考える場合は、実装前にその根拠をユーザーに提示して承認を得る」を追加。記載先: CLAUDE.md §注意事項 §毎タスク適用
- **MD修正だけで足りるか**: MR-071の「指示反復時の自問ルール」と本件の「推測スコープ明確化」を組み合わせることで、指示無視と推測固執の両方をカバーできる。ただし同一セッション内での累積違反は、ルール追加だけでは根本的に防げない。セッション中の自己監視メカニズムが必要だが、現時点で実装可能な構造的強制は存在しない

## 【改善提案】（中優先度）

### #1 デバッグ時の「推測 vs 確認済み事実」明示フォーマット

- **箇所**: CLAUDE.md §注意事項 または `docs/knowledges/tools/004_coding_conventions.md`
- **現状**: デバッグ時に原因仮説と確認済み事実が区別なく発言される
- **提案**: デバッグ・原因分析の発言時に以下の区分を明示する習慣を推奨:
  - `[確認済み]` -- Read・ログ・実行結果で確認した事実
  - `[仮説]` -- 未確認の推測。次に確認すべき手段を併記
- **期待効果**: 推測を「仮説」として明示することで、AIが無意識に断定に滑るのを防止。ユーザーも仮説と事実を区別して受け取れる

### #2 「ユーザー否定後の行動プロトコル」の定義

- **箇所**: CLAUDE.md §注意事項 §毎タスク適用
- **現状**: ユーザーが推測を否定した後の行動が未定義。同系統の推測を言い換えて再提示する行動が禁止されていない
- **提案**: ユーザーが推測を否定した場合の行動プロトコル:
  1. 否定された前提を明示的に放棄する（「〜の可能性は排除します」）
  2. 別の確認手段を提示する（「代わりに〜を確認します」）
  3. 同系統の推測を言い換えて再提示しない
- **期待効果**: 否定後の推測固執パターンを防止

### 8c. 副作用シミュレーション

**(i) 単体副作用**:

- 推奨 B の「否定された推測と同系統を再提示しない」は、AIが別の角度から有効な仮説を見つける機会を制限する可能性がある。ただし「否定された前提を完全に放棄した上で、別の確認手段に切り替える」としたため、確認に基づく新仮説は許容される

**(ii) クロスルール競合**:

- CLAUDE.md:324（推測禁止 -- 拡張後）と CLAUDE.md:325（ログを鵜呑みにしない）は補完関係。ログを鵜呑みにしないルールは「中間ログ→コード確認→手動テスト」という確認手順を定義しており、推測禁止ルールの具体的な確認手段の一つ
