## 【パターン 2: 誤読・ミス原因分析】

### 事象
2024/2025年 gap backfill が 04/25-04/27 に全4 Run 完了。プランファイルのヘッダーは「全完了」に更新済みだったが、以下3箇所が未更新のまま放置:
- `013_tdnet_load.md`:405 — 2024年「Run2待ち」
- `013_tdnet_load.md`:427 — 2025年「待ち」
- `active_jobs.md` — gap backfill エントリ完全欠落
- `memory/project_tdnet_backfill.md` — 04/08 時点の旧情報

### 読み手がどう解釈した可能性があるか
- バックフィル完了を確認した AI は、プランヘッダーを更新して「完了」とした
- しかし 013_tdnet_load.md や active_jobs.md の更新は「後片付け」チェックリストに active_jobs.md のみ記載、013 は記載なし
- セッション跨ぎで新セッションの AI はプランの「後片付け」を能動的に読み直さない

### 直接原因
1. **プラン「後片付け」の不完全なチェックリスト**: `013_tdnet_load.md` 更新と `memory` 更新が後片付け項目に含まれていない
2. **monitor_backfill.py 経由実行の hook 不発火**: PostToolUse フックは `gcloud run jobs execute` の直接呼び出しにのみ反応。Python スクリプト内部からの gcloud 呼び出しでは active_jobs.md に自動追記されない
3. **セッション跨ぎの状態伝播不全**: Run1/Run2 が異なるセッションで実行され、各セッションがプランヘッダーのみ更新。包括的な状態更新が最終セッションで行われなかった

### 根本原因
- バックフィル完了時に「どこを更新すべきか」の包括リストが CLAUDE.md や 013_tdnet_load.md に定義されていない
- プラン「後片付け」は個別プラン固有の作業のみ記載する設計で、プロジェクト横断の状態伝播は想定されていない

### 誤読を許した MD 上の原因
- `013_tdnet_load.md`:405-440 — インライン状態表示に「最終確認日」が無く、古い状態と最新状態の区別がつかない
- `20260425_001000_tdnet_2024_gap_backfill.md`:152-155 — 「後片付け」に `013_tdnet_load.md` 更新が欠落
- `20260425_091000_tdnet_2025_gap_backfill.md`:152-155 — 同上
- CLAUDE.md — バックフィル完了時の状態伝播先一覧が無い

### 再発防止の方向性
1. **バックフィルプランテンプレートに「完了時の伝播先チェックリスト」を標準化**: 013_tdnet_load.md / active_jobs.md / memory の3点を必須項目にする
2. **013_tdnet_load.md のインライン状態に日付を必須化**: `✅ 完了（YYYY-MM-DD確認）` 形式で最終確認日を明示
3. **monitor_backfill.py 完了時の active_jobs.md 自動追記**: スクリプト側で完了時に active_jobs.md に追記する機能を検討（hook 不発火の構造的対策）

## 【重大な指摘】（即修正）

### #1 プラン「後片付け」に知見ファイル更新が欠落
- 箇所: `docs/plans/20260425_001000_tdnet_2024_gap_backfill.md:152-155`, `docs/plans/20260425_091000_tdnet_2025_gap_backfill.md:152-155`
- 問題: 「後片付け」チェックリストに `013_tdnet_load.md` の該当セクション更新と memory 更新が含まれていない
- AI の誤読パターン: チェックリストが完全と解釈し、リスト外の更新作業を行わない
- トリガー: バックフィル完了確認時にチェックリストに従って後片付けする場面
- 影響: 知見ファイルが古い状態のまま残存し、後続セッションが誤判断
- 根拠: 実際に今回発生した事象
- 推奨対応: バックフィルプラン作成時に、後片付けに「013_tdnet_load.md 更新」「memory 更新」を標準で含める
- MD 修正だけで足りるか: 足りる。ただし今後の新プランにも適用するためテンプレートへの反映が望ましい

### #2 monitor_backfill.py 経由実行で active_jobs.md に自動記録されない
- 箇所: `data/logs/active_jobs.md` / PostToolUse hook 設計
- 問題: `gcloud run jobs execute` を Python 内部から呼ぶと PostToolUse フックが発火しない
- AI の誤読パターン: active_jobs.md に記録が無い = 実行されていない、と判断
- トリガー: active_jobs.md を参照してバックフィル実行状況を確認する場面
- 影響: 実行済みバックフィルの再投入を提案するリスク
- 根拠: 2024/2025 gap backfill 4 Run 分が全て記録漏れ
- 推奨対応: (a) monitor_backfill.py 完了時に active_jobs.md へ追記する機能追加、または (b) バックフィル完了確認時の手動追記をプランチェックリストで担保
- MD 修正だけで足りるか: 足りない。(a) はコード修正が必要。(b) は MD 修正で対応可能だが構造的には弱い
