## 【AI 誤読リスク】

### リスク1: 「一致」の定義不在

`CLAUDE.md:207` の「一致があれば」は、AI に以下の3つの解釈余地を残す:
- (a) タスク列の文字列と完全一致
- (b) タスク列に含まれるキーワードと部分一致
- (c) タスク列の意味とユーザー指示の意味が同義

AI は通常 (c) のセマンティックマッチを試みるが、テーブルが「レビュー系エージェント（3種）」のような**分類ラベル**で書かれていると、「ソースコードレビュー」→「レビュー系エージェント」のセマンティック距離が大きく、マッチに失敗する。

### リスク2: テーブルエントリの粒度不統一

テーブル内のエントリは2つのパターンが混在している:
- **タスク記述型**（マッチしやすい）: 「BigQueryを使うコードを書く」「スクリプトを新規作成・改修」「Cloud Run Jobにデプロイ」
- **分類ラベル型**（マッチしにくい）: 「レビュー系エージェント（3種）」「データ取り込み・更新タスク」

タスク記述型はユーザーの自然言語と近いためマッチしやすいが、分類ラベル型はメタ情報であり、ユーザーが実際に発する言葉とは乖離している。

## 【パターン 2: 誤読・ミス原因分析】

### 事象

ユーザーが「ソースコードレビューに」と指示。AIは高頻度参照テーブルをスキャンしたが、「レビュー系エージェント（3種）」という分類ラベルと「ソースコードレビュー」の自然言語入力がマッチせず、code-reviewer スキルの起動が遅延した。AIはフォールバックとして glob/grep 探索に入り、時間を浪費した。

### 読み手の解釈

AIがテーブルをスキャンする際、「ソースコードレビュー」に対して:
- 「レビュー系エージェント（3種）」→ 「レビュー」は含まれるが「ソースコード」が含まれない。「3種」の括弧が分類名を強調し、具体的なタスク指示とのマッチを阻害
- 「計画MD / プランの設計レビュー（内容妥当性）」→ 「レビュー」は含まれるが「計画MD」「プラン」が付いておりスコープ限定。ソースコードレビューとは別物と判断
- 「MDレビュー（AI可読性レビュー）」→ 「MD」が付いており対象外

→ テーブル内に「ソースコードレビュー」に直接対応するエントリが存在しないと判断し、フォールバックに落ちた。

### 直接原因

`CLAUDE.md:227` のタスク列「レビュー系エージェント（3種）」が**分類ラベル**であり、ユーザーが実際に使う自然言語（「ソースコードレビュー」「コードレビュー」「改修箇所のレビュー」「スクリプトレビュー」）と**語彙的にマッチしない**。

### 根本原因

高頻度参照テーブルの設計時に、**タスク列をユーザーの入力語彙ベースで設計する**という原則が明示されていなかった。テーブル作成者は「分類的に網羅されていればよい」と考え、速引き索引に必要な「自然言語の別名マッピング」を行わなかった。

### MD上の原因

- `CLAUDE.md:227`: タスク列「レビュー系エージェント（3種）」— 分類ラベルであり、ユーザーが発するであろう「ソースコードレビュー」「コードレビュー」「この改修をレビュー」等の自然言語とマッチしない
- `CLAUDE.md:209`: テーブルの見出し「頻出タスク・スキル別名の速引き」— 「スキル別名」と銘打っているが、実態は分類名であり別名（alias）になっていないエントリがある

### MD構成原因

- テーブルのタスク列の設計基準が未定義。「何をキーワードとして書くべきか」のガイドラインがない
- テーブルの「一致」判定基準が未定義（CLAUDE.md:207）
- テーブルに「ソースコードレビュー / コードレビュー」という直接的な行が存在せず、L227の分類名に包含される構造。AI はテーブルの1行1行を個別にマッチングするため、包含関係を推論で補完する負荷が高い

### 再発防止の方向性

1. **タスク列をユーザー語彙ベースに書き直す**: 分類ラベルではなく、ユーザーが実際に使う自然言語（動詞句・名詞句）をタスク列に列挙する
2. **テーブルの lookup 指示を明確化**: 「一致」の定義を「タスク列のキーワードがユーザー指示に含まれるか、またはユーザー指示の意図がタスク列の記述に包含されるか」と明示する
3. **テーブル設計原則を追記**: テーブルにエントリを追加する際は「ユーザーが実際にどう言うか」を想定し、**自然言語バリエーション**をスラッシュ区切りで列挙するルールを追加する

### 対策スコープ

本件は CLAUDE.md の高頻度参照テーブル全体に関わる設計問題であり、特定エントリの修正だけでは再発する。テーブル設計原則の明文化（CLAUDE.md 内）と、全エントリの横断的な語彙見直しが必要。

## 【改善提案】（中優先度）

### #1 テーブルのマッチ失敗時のフィードバックループ

- **箇所**: `CLAUDE.md:207`（フォールバック順序の定義付近）
- **現状**: テーブル → INDEX.md → glob/grep のフォールバック順序は定義されているが、フォールバックでスキルを発見した場合にテーブルを改善する仕組みがない
- **提案**: フォールバックで知見ファイル/スキルを発見した場合、テーブルの該当エントリにユーザーの実入力語彙を追加することを推奨する注記を追加する（INDEX.md §導線チェックリストに「テーブル語彙追加」を項目として追加）
- **期待効果**: テーブルのマッチ品質が運用を通じて漸進的に改善する

### #2 レビュー系3行の統合 vs 分割

- **箇所**: `CLAUDE.md:227-230`
- **現状**: レビュー系は L227（3種まとめ）、L228（code-reviewer パターン4）、L229（md-reviewer）、L230（structure-optimizer）の4行構成
- **提案**: L227 を廃止し、code-reviewer の汎用起動（パターン1-3）用の行を新設する。これにより:
  - 「ソースコードレビュー / コードレビュー / 改修レビュー / スクリプトレビュー」→ `/code-reviewer`
  - 「計画MD / プランの設計レビュー（内容妥当性）」→ `/code-reviewer` パターン4（既存 L228 維持）
  - 「MDレビュー（AI可読性レビュー）」→ `/md-reviewer`（既存 L229 維持）
  - 「リフォーム / 再開発 / MD最適化 / 構造最適化」→ `/structure-optimizer`（既存 L230 維持）
- **期待効果**: 分類ラベル行が消え、全行がタスク記述型になる。各スキルへのルーティングが明確化
