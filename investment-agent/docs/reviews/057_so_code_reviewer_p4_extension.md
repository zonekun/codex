## Quick Fix

### QF-1: パターン2/4 判定基準の「迷う場合」ルールが不十分 — 元指摘: SO独自 | 箇所: `計画MD:L80-L82` | 影響度: 低

**問題**: 計画MDのL82に「迷う場合: 『対象ファイル』に既存コードのパスがあるか → あり=パターン2、なし=パターン4」とあるが、これは **新規開発計画で既存コードを参照する場合**（例: 既存パイプラインに新ステージを追加する計画）に判定が揺れる。計画MD自身もリスクL251で同様の懸念を認識しているが、対策が「判定基準を明示」で循環している。

**改善案**: 判定の第一基準を「テンプレートフォーマット」に固定し、内容ベースの判定はフォールバックとする。具体的には:
1. `_template_refactor.md` フォーマット（P0/P1/P2 + 7フィールド構成） → パターン2（変更不要）
2. `skills/planning.md` §テンプレート形式（目的/背景/作業ステップ/成果物/完了条件） → パターン4（変更不要）
3. **どちらのテンプレートにも該当しない自由形式** → 「パターン判定不能」として、ユーザーにテンプレート選択を促す（**追加すべき**）

これにより「迷う場合」の判定が内容解釈（対象ファイルの有無）ではなく形式判定に閉じ、AI判断安定性が向上する。

### QF-2: 評価項目8個のうち項目1・6が汎用テンプレートのフィールドと重複 — 元指摘: SO独自 | 箇所: `計画MD:L102, L108` | 影響度: 低

**問題**: パターン4固有の評価項目のうち:
- 項目1「目的・スコープの明確性」は `skills/planning.md` §テンプレートの「目的」「完了条件」フィールドの存在チェックとほぼ同義
- 項目6「完了条件の検証可能性」も同テンプレートの「完了条件」フィールドの品質チェック

これらはパターン4固有というよりテンプレート適合性チェックであり、パターン2の「フォーマット適合性チェック」（L114-L128）と同構造の問題。

**改善案**: 項目1・6を「テンプレート適合性チェック」として切り出し、パターン4固有の評価項目は残り6個に絞る。または、項目1・6は残すがレビュー出力テンプレート側で「テンプレート適合性」と「内容的妥当性」を明示的に分離して記述量を減らす。

### QF-3: md-reviewer 責務境界セクションに「引き継ぎ提案」の具体的な表現が不足 — 元指摘: SO独自 | 箇所: `計画MD:L189` | 影響度: 低

**問題**: 計画MDのL189に「設計レビューが必要な場合は code-reviewer パターン4 への引き継ぎを提案する」とあるが、md-reviewer のレビュー出力テンプレート（L352-L503）にこの引き継ぎ提案を記載する場所が定義されていない。md-reviewer が引き継ぎを提案する場合、出力MDのどのセクションに書くべきかが不明。

**改善案**: md-reviewer の変更2で追加するセクションに1行追加:
```
引き継ぎ提案は md-reviewer 出力の【改善提案】または末尾の「確認できなかった事項」に記載する。
```

## Scoped Refactor

### SR-1: パターン4出力テンプレートとパターン2出力テンプレートの共通化検討 — 元指摘: SO独自 | 箇所: `計画MD:L113-L145` vs `code-reviewer.md:L198-L267` | 影響度: 中

**問題**: 計画MDの1b（L113-L145）で追加されるパターン4出力テンプレートは、パターン2出力テンプレート（code-reviewer.md L215-L229）と構造が類似している。どちらも「妥当性」「リスク」「抜け漏れ」を評価する。パターン1/3は共通テンプレートを使い、パターン2/4だけ別テンプレートを持つ構成になるが、code-reviewer.md にパターン別テンプレートが3種類（共通+P2+P4）並ぶとトークン効率が悪化する。

**改善案**: パターン2/4の共通構造を抽出し、差分のみを各パターン固有として定義する。具体的には:
- 共通: 「妥当性」「リスク」「抜け漏れ」の3軸は両パターンで共通
- パターン2固有: 「副作用・デグレードチェック」「フォーマット適合性チェック」
- パターン4固有: 「技術選定」「段階的検証計画」「データカタログ整合」「既存システム統合」

これにより、code-reviewer.md の追加行数を +60-70行から +40-50行程度に削減できる。ただし「共通部分の参照」が複雑になると可読性が下がるため、重複を許容して独立させる判断も合理的。**初版は独立テンプレートで進め、004-1蓄積ログにパターン2/4の共通指摘が蓄積された段階で共通化を検討**するのが現実的。

### SR-2: CLAUDE.md 高頻度参照テーブルの行が「計画MDの設計レビュー」では発見されにくい — 元指摘: SO独自 | 箇所: `計画MD:L199` | 影響度: 中

**問題**: 計画MDの変更3（L199）で追加される CLAUDE.md の行:
```
| 計画MDの設計レビュー | `skills/code-reviewer.md` パターン4 |
```
CLAUDE.md 高頻度参照テーブルの左列はタスク記述（例: 「スクリプトを新規作成・改修」「Cloud Run Jobにデプロイ」）であり、ユーザーの自然な指示文（例: 「この計画をレビューして」「プランの妥当性をチェックして」）との一致度がやや低い。

**改善案**: 左列を「計画MD / プランの設計レビュー」に変更し、ユーザーが「プラン」「計画」どちらの語彙を使っても到達できるようにする。また、INDEX.md 側（変更4）も同様に「計画MD / プランの設計レビュー」に揃える。

### SR-3: planning.md への逆参照（変更5）の記載位置が「呼び出し側からの参照」末尾で埋もれる — 元指摘: SO独自 | 箇所: `計画MD:L219` | 影響度: 中

**問題**: 計画MDの変更5（L219）で `skills/planning.md` §呼び出し側からの参照の末尾に1行追加する設計だが、この節（planning.md L269-L274）は既に4行の箇条書きがあり、5行目として追加される。AI が planning.md を読む際、「呼び出し側からの参照」節は計画作成フローの後段にあり、計画を**作成する**文脈で読まれるため、レビュー導線としての注目度は低い。

**改善案**: planning.md §テンプレートの冒頭コメント部分（L282付近）に「対象読者」として code-reviewer パターン4 を明記する方が効果的。テンプレート自体に「このテンプレートで作成した計画は code-reviewer パターン4 でレビュー可能」と書くことで、計画作成者がレビュー導線を自然に認知する。変更5の末尾追記は残しつつ、テンプレート冒頭にも1行追加する。

### SR-4: 004-1 蓄積ログへのパターン4用タグが未定義 — 元指摘: SO独自（相互作用問題） | 箇所: `計画MD全体` vs `004-1_code_review_findings_log.md` | 影響度: 中

**問題**: パターン4のレビュー結果も「004-1蓄積ログに追記」される（code-reviewer の既存ルール §不備蓄積ログへの追記 による）。しかし、004-1のタグカタログ（format系/logic系等）はパターン1/2/3向けに設計されており、パターン4固有の指摘（例: 「技術選定の過剰設計」「段階的検証計画の欠落」「データカタログ未参照」）をタグ付けするための語彙が不足している。

計画MD自身はこの点に触れていない。パターン4のレビューが実施されても、適切なタグがないと `format:verification-thin` 等の既存タグに無理にマッピングされるか、タグなしで書かれるリスクがある。

**改善案**: 計画MDの変更1に「004-1タグカタログへの追加」を作業ステップとして含める。最小限の追加タグ案:
- `plan:scope-unclear` — 計画の目的・スコープが曖昧
- `plan:tech-overengineered` — 技術選定が目的に対して過剰
- `plan:no-phased-validation` — 段階的検証計画（smoke/dev/prod）が欠落
- `plan:catalog-mismatch` — data_catalog.md との不整合

## Rebuild

### RD-1: パターン4の評価項目8個は学習フェーズ終了後に再設計すべき — 元指摘: SO独自 | 箇所: `計画MD:L101-L111` | 影響度: 高

**問題**: 8つの評価項目は論理的にはすべて妥当だが、1回のレビューで8項目を全て評価するのはトークンコストが高い。特に項目7「データカタログ整合」と項目8「抜け漏れ（横展開）」は、計画の種類（データパイプライン vs UIツール vs 分析スクリプト）によって重要度が大きく異なる。

計画MD自身もリスクL253で「初版の8項目が多すぎ/少なすぎの可能性 → 004-1蓄積ログで傾向を見て調整」と認識しており、この方針は正しい。ただし、**初版でも「必須4項目 + 任意4項目」のように優先度を分けておく**ことで、レビュアーが軽量レビュー（必須のみ）とフルレビュー（全8項目）を選択できるようにすべき。

**改善方針**:
- 必須（常に評価）: 項目2（技術選定）、項目3（既存システム統合）、項目5（リスク・コスト）、項目8（抜け漏れ）
- 任意（計画の種類に応じて評価）: 項目1（目的）、項目4（段階的検証）、項目6（完了条件）、項目7（データカタログ）
- この分離は初版から導入し、004-1蓄積ログの傾向分析後に必須/任意の配分を見直す
