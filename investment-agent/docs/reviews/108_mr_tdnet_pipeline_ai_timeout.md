## 【AI 誤読リスク】

### リスク1: 「バックフィル安全」の過度に広い解釈

- **箇所**: `013_tdnet_load.md:94`（`recent_only` パラメータにより過去年バックフィルの pending を横取りしない）
- **問題**: 「バックフィル安全」という表現が `resolve_date_range` の日付ガードのみを指しているが、AI は「バックフィルと日次の共存は安全」と広義に解釈する余地がある。Cloud Run Job のリソース競合、Workflows の同時実行、BQ テーブルへの同時書き込み等、別次元の競合リスクが存在するにもかかわらず、ここでの「安全」がそれらを包含していると誤読される
- **トリガー**: ユーザーが「バックフィルを投入して」と指示し、AI が 013 を読んで「バックフィル安全」を確認した時点で競合チェックをスキップする
- **影響**: 決算特別スケジュール中にバックフィルを投入し、事故1を再発させる

### リスク2: `resolve_date_range` の「月単位」仕様の見落とし

- **箇所**: `013_tdnet_load.md:563-564`（直近14日以内の最古 pending 月を自動選択）、`ai_processing_flow.yaml:86-100`
- **問題**: 「最古 pending 月を自動選択」という記述は正確だが、その帰結（複数月に pending が存在する場合に最新月が後回しになる）が明示されていない。特に `recent_only: true` でも14日ウィンドウ内に複数月の pending が共存し得ることが暗黙の前提になっている
- **トリガー**: 月末・月初の日次パイプラインで、前月の pending 残があるタイミング。事故2 のように4月 pending + 5月 pending の共存
- **影響**: 当日投入分が AI 処理されず pending のまま滞留。手動介入が必要になることを AI が予見できない

### リスク3: `trigger_ai` の非同期性の無意識化

- **箇所**: `workflows/tdnet_daily_pipeline.yaml:57-65`
- **問題**: CR-094 の指摘 #1（trigger_ai が子Workflow完了を待たない）は修正済みで `connector_params.timeout: 43200` が設定されているが、`executions.create` が LRO ではなく standard REST call であるという本質的な問題は残存している可能性がある。013 知見ファイルの運用実績 L81 では「合計59min」と記載されているが、これがパイプライン Workflow の完了時間なのか AI 処理自体の完了時間なのかが曖昧
- **トリガー**: パイプライン失敗時の原因調査で、AI が「trigger_ai SUCCEEDED = AI 処理完了」と誤認する
- **影響**: 実際には AI 処理が未完了なのに「パイプライン正常完了」と判断し、pending 滞留を見逃す

## 【パターン 2: 誤読・ミス原因分析】

### 事象

1. **事故1**: 2026-05-07、決算特別スケジュール中に 2022年バックフィル `tdnet-load-daily` ジョブが同時実行され、日次パイプラインの trigger_ai が 1800秒でタイムアウト
2. **事故2**: 同日、`ai_processing_flow` が `recent_only: true` で起動されたが、`resolve_date_range` が4月の最古 pending 月を選択し、5/7 の 275 pending が未処理のまま残存

### 読み手（AI）の解釈

- 013 知見ファイルの §決算特別スケジュール を読み、パイプラインの有効化・無効化手順を把握。§バックフィル運用 を読み、投入単位・時間帯推奨を把握。両セクションに交差制約の記述がないため、「バックフィルと日次パイプラインは独立に実行可能」と解釈
- §週次スケジューラの「バックフィル安全」記述を読み、「`recent_only` で安全に共存できる」と判断。この「安全」がデータレベル（pending 横取り防止）のみを指し、インフラレベル（Cloud Run Job 競合）を含まないことを区別できない
- `resolve_date_range` の「最古 pending 月を自動選択」を読み、「自動的に適切な日付を選んでくれる」と理解。複数月の pending 共存時に当日分が後回しになるエッジケースを予見できない

### 直接原因

1. **事故1**: 013 知見ファイルにバックフィルと日次パイプラインの Cloud Run Job 排他制約が未記載。バックフィル投入時に「日次パイプラインの実行時間帯（20:03 JST）を避ける」等の制約がない
2. **事故2**: `resolve_date_range` の月単位選択仕様が、複数月 pending 共存時に最新月を後回しにするエッジケースが 013 にも YAML コメントにも未記載

### 根本原因

- **013 知見ファイルの設計思想が「各コンポーネントの独立記述」に偏り、「コンポーネント間の相互作用・競合」の記述が構造的に欠落している**。決算特別スケジュール・バックフィル・週次 AI の各セクションはそれぞれ正確だが、同時実行時の振る舞いが記述されていない
- `resolve_date_range` の仕様は YAML 上は明確だが、「月単位選択」の帰結（月境界で当日分が後回し）が知見ファイルで言語化されていないため、AI が YAML を直接読まない限り予見不可能

## 【重大な指摘】（即修正）

### #1 バックフィルと日次パイプラインの競合制約が 013 知見ファイルに未記載

- **箇所**: `docs/knowledges/tools/013_tdnet_load.md:11-86`（決算特別スケジュール）、`013_tdnet_load.md:372-405`（バックフィル運用）
- **問題**: バックフィルが `tdnet-load-daily` Cloud Run Job を使用し、日次パイプラインも同じ `tdnet-load-daily` を使用する。両者が同時実行された場合の振る舞い（Cloud Run Jobs の並行実行制限、BQ streaming buffer 競合、Workflows timeout への影響）が一切記載されていない
- **AIの誤読パターン**: AI が §バックフィル運用 の投入時間帯推奨（L384-393: 平日 15:00-24:00 JST）を読み、「20:03 JST の日次パイプラインと重なる時間帯だが、推奨されている」と判断してバックフィルを投入する
- **トリガー**: ユーザーが決算特別スケジュール期間中に「バックフィルを投入して」と指示した場合
- **影響**: 事故1の再発。日次パイプラインの trigger_ai がタイムアウトし、当日分の AI 処理が中断
- **根拠**: 2026-05-07 の事故1が実際にこのパターンで発生
- **推奨対応**: 013 知見ファイルの §決算特別スケジュール セクション末尾に「運用中の注意事項」サブセクションを追加。以下を明記:
  - 決算特別スケジュール期間中はバックフィルの `tdnet-load-daily` 実行を避ける（20:03 JST の日次パイプラインと競合する）
  - やむを得ず実行する場合は、日次パイプライン完了後（翌朝以降）に投入する
  - バックフィル投入時間帯推奨（L384-393）にも日次パイプラインとの競合注意を追記
- **記載先**: `docs/knowledges/tools/013_tdnet_load.md` §決算特別スケジュール > 運用中の注意事項（新設）
- **MD修正だけで足りるか**: MD 修正で AI の判断材料は改善されるが、Workflows レベルの排他制御（例: `tdnet-load-daily` Job の max-instances=1 設定）がないため、同時実行自体は技術的に防がれない。ソースコード・仕組み側への波及セクション参照

### #2 `resolve_date_range` の月単位選択エッジケースが未記載

- **箇所**: `docs/knowledges/tools/013_tdnet_load.md:562-564`、`workflows/ai_processing_flow.yaml:86-100`
- **問題**: `resolve_date_range` は `MIN(SUBMISSION_DATE)` を `DATE_TRUNC(..., MONTH)` で月初に丸め、同月末までを `date_to` にする。これにより、14日ウィンドウ内に複数月の pending が存在する場合、最古月のみ処理され、最新月（当日分）は次回実行まで放置される。この仕様は YAML コメントにも 013 知見ファイルにも明記されていない
- **AIの誤読パターン**: 013 の「直近14日以内の最古 pending 月を自動選択」（L564）を読み、「14日以内の全 pending が処理される」と拡大解釈する。「最古 pending **月**」の「月」が月単位丸めを意味し、1回の実行で1ヶ月分しか処理しないことを見落とす
- **トリガー**: 月末（例: 4/30）〜月初（例: 5/7）にかけて pending が分散している状態で `recent_only: true` で起動した場合
- **影響**: 事故2の再発。当日分の pending が AI_STATUS='pending' のまま滞留し、手動介入が必要
- **根拠**: 2026-05-07 の事故2が実際にこのパターンで発生（4月分が優先され、5/7 の 275 pending が未処理）
- **推奨対応**:
  - 013 知見ファイルの §週次スケジューラ > バックフィルとの共存 セクションに「`recent_only` モードのエッジケース」サブセクションを追加
  - 具体的に記載すべき内容: (1) 14日ウィンドウ内に複数月の pending がある場合は最古月のみ処理される (2) 月境界（月末〜翌月初）は特にリスクが高い (3) 当日分を確実に処理するには `date_from`/`date_to` を明示指定して手動再投入する

## 【ソースコード・仕組み側への波及】

### 1. Cloud Run Job の同時実行制御

- **問題**: `tdnet-load-daily` Cloud Run Job は日次パイプラインとバックフィルの両方から呼ばれるが、`--max-instances` 設定による排他制御がない。Cloud Run Jobs はデフォルトで同名ジョブの並列実行を許可する
- **推奨**: `tdnet-load-daily` Job の `--max-instances=1` を設定し、同時実行を物理的にブロックする。ただしこれによりバックフィルが日次パイプラインをブロックする（または逆）ため、バックフィル用に別名の Job を作成するアプローチも検討すべき
- **代替案**: バックフィルには別の Cloud Run Job 名（例: `tdnet-load-backfill`）を使用し、日次パイプラインとリソースを完全分離する

### 2. `ai_processing_flow` の日付選択ロジック改善

- **問題**: `resolve_date_range` の月単位選択は、週次バッチ（pending をまとめて処理）には適切だが、日次パイプライン（当日分を即時処理）には不適切
- **推奨**: `tdnet_daily_pipeline.yaml` 側で当日日付を明示渡しする（改善提案 #3）。または `ai_processing_flow` 側に `pipeline_mode` パラメータを追加し、日次パイプラインからの起動時は当日日付を自動設定するロジックを入れる

### 3. パイプライン失敗時の自動リカバリ

- **問題**: 現在、パイプラインが失敗した場合の pending 回収は手動再投入または週次 AI（土曜）に依存。決算特別スケジュール期間中は最大5営業日の遅延が発生し得る
- **推奨**: 013 知見ファイルに「パイプライン失敗時のリカバリ手順」を明記する。加えて、Cloud Scheduler で翌朝（例: 06:00 JST）に pending チェック + 自動再投入する Workflows を検討する
