## 3. リスク・コスト

### 指摘3（高）: Bash echo追記のエンコーディング・改行コード問題

計画L72-103で059-1への追記手段として「Bash echo >> path」を推奨しているが、以下のリスクがある:

**(a) Git Bashでの日本語echo**: 計画L102に「日本語を含むechoはGit Bashで正常動作する（UTF-8デフォルト）」とあるが、CLAUDE.md 6章の規約では「ファイルopenはencoding=を必ず明示。ソースコード/JSON/YAML/MD -> utf-8」が必須。echoはencoding指定ができないため、Git Bashのロケール設定に依存する。Windows PowerShellからechoを実行した場合はUTF-16 LE（BOM付き）になる可能性がある。

**(b) 改行コード**: Bash echoはLFだが、Windowsで他ツール（Edit tool等）が当該ファイルを扱う場合にCRLF/LF混在になるリスクがある。既存の059本体がCRLFの場合、059-1がLFになると差分表示が壊れる。

**(c) 複数行テーブルの原子性**: 反省会テーブルのヘッダー行（5行）をechoで逐次追記する設計だが、途中でCtrl-Cやクラッシュが入ると不完全なMarkdownテーブルが残る。Edit toolなら原子的だがechoの連続実行は非原子的。

**推奨**: 以下のいずれかを059-1の書き込みルールに追記:
- Git Bash限定で実行する旨を明記（PowerShell echo禁止）
- ヘッダー5行は1回のechoで改行を埋め込む（`echo -e "line1\nline2\n..."` でまとめて出力）
- 長期的にはPythonスクリプト化してencoding=utf-8を保証する選択肢も記載
