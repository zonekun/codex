### 問題の本質

md-reviewer は各事故に対して「その事故が再発しない」個別ルールの追加を提案している。しかし4件の系譜が示しているのは、**個別ルールの追加では次の変種を防げない**という事実そのものである。

- MR-136 → §ユーザー異常報告時の自己検証追加 → **次は?**

各ルールは表層の**トリガー語彙**（「そのまま移植」「手動で」「A+Bで」「動いていない」）に反応する設計になっているため、トリガー語彙が異なる次の変種には発火しない。これは**ルール設計の構造的欠陥**であり、ルール追加では解決しない。

## Scoped Refactor

### SR-1: CLAUDE.md §注意事項の構造改善 — 「メタルール」と「個別ルール」の2層化

- 元指摘: 137_mr §4.根本原因分析 + 136_mr 重大指摘#3/#4（相互作用問題として統合発見）
- 箇所: `CLAUDE.md:330-342`（§注意事項 → §毎タスク適用）
- 現状の問題:

  CLAUDE.md §毎タスク適用には現在11個のルールが**フラットに並列**されている。「推測禁止」「ユーザー異常報告時の自己検証」「指示の字義優先」「マルチターン待機」等が全て同列。しかし実際にはこれらには階層がある:

  ```
  §指示の字義優先（メタルール: ユーザー指示 > AI判断）
    ├── §既存コード移植ルール（具体化: 移植時）     ← MR-071
    ├── §AI直接処理の指示ルール（具体化: 手段選択時） ← MR-131
    ├── §ステップ完了検証義務（具体化: プラン実行時）  ← MR-134
    └── §ユーザー異常報告時の自己検証（具体化: 障害対応時） ← MR-136
  ```

  この階層が明示されていないため、AIは各ルールを**独立した列挙**として処理し、列挙にない新しい場面（次の変種）ではどのルールも発火しない。

- 改善案:

  §指示の字義優先（L340）を**メタルール**として格上げし、4件の個別ルールとの親子関係を明示する。具体的には、§指示の字義優先の直下に「具体化ルールへのポインタ」を置き、かつ**メタルールの適用判定基準**を追加する:

  **before** (`CLAUDE.md:340`):
  ```markdown
  - **指示の字義優先**: ユーザー指示は、プランMDの構造・AIの技術的判断・慣習的実行単位より常に優先する。特にユーザーが同じ方向の指示を2回以上繰り返した場合、自分の前回の実装が指示に沿っていたか0ベースで再評価する。ユーザーから矛盾・不整合を指摘された場合、指摘された箇所だけでなく、同じ矛盾が波及している作業リスト全体を再検証すること。ただしユーザー指示は絶対ではない。指示が明らかに破壊的な結果を招く場合は実行リスクを提示する
  ```

  **after**:
  ```markdown
  - **指示の字義優先（メタルール — 以下の個別ルールの親）**: ユーザー指示は、プランMDの構造・AIの技術的判断・慣習的実行単位より常に優先する。**自分の判断で十分だと感じても、明示的に指定された手順・参照先・手段・ツールを省略/改変してはならない。** 省略/改変が合理的と判断した場合は、実行前にユーザーに確認する。特にユーザーが同じ方向の指示を2回以上繰り返した場合、自分の前回の実装が指示に沿っていたか0ベースで再評価する。ユーザーから矛盾・不整合を指摘された場合、指摘された箇所だけでなく、同じ矛盾が波及している作業リスト全体を再検証すること。ただしユーザー指示は絶対ではない。指示が明らかに破壊的な結果を招く場合は実行リスクを提示する
    - 具体化: §既存コード移植ルール（MR-071）、§AI直接処理の指示ルール（MR-131）、§ステップ完了検証義務（MR-134）、§ユーザー異常報告時の自己検証（MR-136）
    - **適用判定**: 「ドキュメント/指示に書かれた手段Xを、自分の判断で手段Yに置き換えようとしている」と認識した時点で本ルール発火。Xの具体的内容（ライブラリ/処理手段/調査手順/参照先/フラグ）を問わない。4件系譜: MR-071→131→134→136
  ```

  この改善により:
  1. AIが「これは§既存コード移植ルールの話ではない」と判断した場合でも、**メタルール自体**が発火する
  2. 「手段Xを手段Yに置き換えようとしている」という**抽象度の高い判定基準**で、表層が異なる変種にも対応できる
  3. 個別ルール群との親子関係が明示され、AIが「これらは§指示の字義優先の具体化である」と認識できる

- 影響度: 中

### RD-1: 事故系譜の「パターンDB」化 — 個別ルール増殖からパターン認識へのアーキテクチャ転換

- 元指摘: 137_mr §4.根本原因分析「なぜ個別対策が次の変種を防げなかったか」+ 136_mr §確認できなかった事項#2（相互作用問題として統合発見）
- 箇所: CLAUDE.md 全体の再発防止アーキテクチャ
- 現状の問題:

  現在の CLAUDE.md の再発防止は**ルール増殖モデル**:
  ```
  事故発生 → 表層特化ルール追加 → 次の変種発生 → 新ルール追加 → ...
  ```
  
  このモデルは O(n) でCLAUDE.mdが肥大化し、かつ**次の変種を事前に防げない**。4件の事故で4つのルールが追加されたが、4つ目の時点でもルール追加の限界が実証されている。

  md-reviewer の提案（137_mr）は「5件目が発生したらhook/validatorの導入を検討」としているが、これは**問題の先送り**である。5件目は「次に表層が異なる変種が発生した時」に自動的に発生するため、時間の問題。

- 改善方針:

  **ルール増殖モデル → パターン認識モデル** への転換を提案する。

  **具体案: `docs/knowledges/tools/004_coding_conventions.md` に §事故パターンDB セクションを新設**

  CLAUDE.md にはメタルール（SR-1で強化済み）を置き、**パターンの詳細・判定フローチャート・事故事例テーブル**は知見MDに委譲する。CLAUDE.md の§毎タスク適用からポインタで参照する。

  パターンDBの設計:

  ```markdown
  ## 事故パターンDB

  ### P-001: AI判断によるドキュメント/指示の上書き

  **パターン定義**: AIが「自分の判断で十分」と評価し、明示的に指定された手順・参照先・手段を省略/改変する

  **判定フローチャート**:
  1. いま実行しようとしている手段/手順は、ドキュメント/指示/プランに明示されたものと同一か?
  2. 異なる場合: 「自分の判断の方が良い」と感じているか?
  3. Yes → **本パターン該当**。実行前にユーザーに確認する

  **事故事例テーブル**:
  | # | MR | 表層 | 省略/改変された要素 | AIの判断内容 | 追加されたルール |
  |---|-----|------|-------------------|-------------|----------------|
  | 1 | 071 | そのまま移植→改良 | ライブラリ | Playwrightの方がモダン | §既存コード移植ルール |
  | 2 | 131 | 手動で→Python化 | 処理手段 | コードの方が効率的 | §AI直接処理の指示ルール |
  | 3 | 134 | プラン手順省略 | 調査手順 | AI知見で十分 | §ステップ完了検証義務 |
  | 4 | 136 | 知見MD未参照でCLI構成 | 参照先 | 記憶で構成できる | §ユーザー異常報告時の自己検証 |

  **共通構造**: 全事例で「自信度が高い → 参照/確認を省略する」が発動している

  **防止策（メタルール）**: CLAUDE.md §指示の字義優先を参照。「手段Xを手段Yに置き換えようとしている」と認識した時点で発火
  ```

  この設計のメリット:
  1. **次の変種発生時**: CLAUDE.md のメタルールが発火し、かつ詳細はパターンDBを参照することで、AIが「これは既知パターンP-001の変種か?」と判定できる
  2. **CLAUDE.md の肥大化防止**: メタルール（2-3行）+ポインタ（1行）で済み、事故事例テーブルは知見MDに委譲
  3. **事故発生時の対応**: CLAUDE.mdにルール追加するのではなく、パターンDBの事故事例テーブルに1行追加するだけで済む。これは**ルール追加ではなくデータ追加**
  4. **他パターンへの拡張**: 今後P-002, P-003として他の繰り返し事故パターンも同じ構造で管理できる

- 影響度: 高

**[苦情: レビュー記述が分かりづらく誤解を招いた]** RD-1の記述は「具体案: 004_coding_conventions.md に §事故パターンDB セクションを新設」というMD編集作業としてまとめられているが、RD-1の本質は「ルール増殖モデル→パターン認識モデルへのアーキテクチャ転換」という制度設計レベルの提案。メインエージェントはRD-1を「004にテーブルを追加する作業」と矮小化して理解し、テーブル追加だけで「RD-1完了」と報告した。ユーザーから「レビューのうわっつらをなめただけで理解不十分」と指摘された。レビュー出力は、具体的なファイル編集手順と、その背後にあるアーキテクチャ転換の意図・制度設計の必要性を明確に分離して記述すべき。「具体案」ラベルで両者を混在させると、AIは具体的なファイル編集のみを拾い、制度設計の趣旨を見落とす。
