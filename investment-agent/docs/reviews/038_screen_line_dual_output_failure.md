# 038: 画面+LINE双方向出力の繰り返し違反

**日時**: 2026-04-30 22:30 JST
**重大度**: High（同一セッション内で4回以上指摘されても改善できず）
**カテゴリ**: 運用ミス（アドホック指示への適応失敗）

## 事象

LINE双方向会話モード中、ユーザーから「画面とライン双方向両方にアウトプットを送ること」と明確に指示されたにもかかわらず、以下のパターンで繰り返し片方のみにしか出力しなかった。

| 回 | 状況 | 欠落した側 | ユーザー指摘 |
|----|------|-----------|------------|
| 1 | 30件サンプル解析結果の報告 | LINE未送信（ツール拒否後に再送せず） | 「さっきのアウトプット、ラインに送られていない」 |
| 2 | 作業順序確定+解析結果 | 画面テキスト出力なし（LINE送信のみ） | 「今度はこのアウトプットが画面に出ていない」 |
| 3 | パターン化不要の指摘への回答 | LINE未送信 | 「あと今回はアウトプットがラインに送られていない」 |
| 4 | 謝罪+プラン作成開始 | 画面テキスト出力なし（LINE送信のみ） | 「画面に出ていない」 |

**合計**: 4回連続で同じ指示に違反。回1,3はLINE欠落、回2,4は画面欠落と**交互に欠落側が変化**する「注意の振り子現象」が発生。

**影響**: 受注残高パイプライン設計作業が約30分遅延。ユーザーが毎回同じ指摘を繰り返す負担が発生。

## 根本原因

### 1. CLAUDE.md既存ルールとアドホック指示の構造的衝突

CLAUDE.md §ライン会話モード は「以降の全ての応答は `send_ntfy_and_wait()` を使う」と規定しており、画面テキスト出力への言及はない。ユーザーの「画面とLINE両方に出せ」はこの既存ルールを**上書きするアドホック指示**。この衝突を認識できなかったため、ターンごとにどちらか片方のモードにフォールバックした。

### 2. 注意の振り子現象

直前の指摘を受けて欠落側を意識した結果、もう片方を忘れる典型的パターン:
- 回1: LINE欠落 → 指摘 → 回2: LINEは送ったが画面を忘れた
- 回2: 画面欠落 → 指摘 → 回3: 画面は書いたがLINEを忘れた

**対策**: チェックリスト（注意力依存）ではなく**出力テンプレートの固定化**（構造で強制）が必要。

### 3. ツール拒否後のリカバリ欠如

回1では `send_ntfy_and_wait` がユーザーによりツール拒否されたが、その後のターンで同じ内容をLINEに再送しなかった。ツール拒否 = 内容自体の否定ではなく、タイミングやアプローチの問題である可能性を考慮すべき。

### 4. 指摘への対応が表面的

「以後必ず両方に送ります」と毎回宣言するが、次のターンですぐ破る。宣言ではなく、出力の構造を変える必要がある。

## 正しい出力テンプレート

「画面+LINE両方出力」指示を受けた場合、**毎ターン以下の構造を機械的に適用する**:

```
=== ターン出力開始 ===

[Step 1: 画面テキスト出力]
■タイトル
（マークダウンで内容を書く — ユーザーが画面で直接読める）

[Step 2: LINE送信]
send_ntfy_and_wait() で同じ内容を送信

=== ターン出力完了 ===
```

**発動条件**: ユーザーが「画面とLINE両方に出せ」「双方向に送れ」等を指示した時点から有効。
**終了条件**: ユーザーが「LINEだけでいい」「画面だけでいい」等を指示するか、LINE会話モード自体が解除されるまで。
**順序**: 画面テキスト出力を先に書き、その後 LINE 送信（画面出力が確実に生成されてからLINE送信に進む）。

## 再発防止

1. **CLAUDE.md §ライン会話モードに「画面+LINE両方出力」プロトコル追記**: ユーザーから画面出力も求められた場合のルールを明文化
2. **出力テンプレート固定化**: 注意力ではなく構造で強制。毎ターン「画面テキスト → LINE送信」の2ステップを機械的に実行
3. **068知見ファイルに拡張モード記載**: 通常LINE会話モード（LINEのみ）と拡張モード（画面+LINE）の使い分けを知見化
4. **ツール拒否後のリカバリ**: 内容が有効なら次のターンでLINE再送する
