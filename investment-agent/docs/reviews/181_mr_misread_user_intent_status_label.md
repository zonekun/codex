## 【パターン 4: 原因分析】

### 事象

013_tdnet_load.md の「決算特別スケジュール」→「決算特別シフト」リネーム作業中、ユーザーが「ステータス」というラベル語の曖昧さを指摘した。AIは3回連続でユーザーの意図と異なる修正を実施した。

具体的な経緯:
1. ユーザー「何のステータスかわからない」→ AIは「ステータス」を「文書ステータス」に変更しようとした（ユーザーの問いは「この語が何を指すか不明瞭」であり「正解は文書ステータスだ」という主張ではない）
2. ユーザー「ばかやろう ジョブスケジュールステータスだろう」→ AIはタイトル行に情報を移動し、ステータス行を「有効」のみに変更（ユーザーの発言は正解を教えたのではなく、ラベルが不明瞭だという指摘の強調）
3. ユーザー「違う「ステータス」ってなんのステータス？文書？プログラム？わからないでしょ その表現じゃ」→ ここでようやくユーザーの意図が「**ステータスという語自体を、ジョブスケジュールステータス等の明確なラベルに書き換えよ**」だと判明

### AIの思考回路（推定）

1. **初回**: ユーザー「何のステータスかわからない」を受け、「ステータス」の意味を特定する作業と解釈。「文書ステータス」という具体化案を自力で生成し、ユーザーに確認せず実行。**§4.1（確認優先）のトリガーが発火しなかった。**
2. **2回目**: ユーザーの怒りの表現「ジョブスケジュールステータスだろう」を「正解はジョブスケジュールステータスだ」と解釈し、ステータス行の情報をタイトルに移すことで対応。しかしユーザーの真意は「ステータスという語自体が何を指すか不明」であり、AIは「ステータス」ラベルそのものを修正対象と認識しなかった。**初回の解釈フレームワーク（「ステータスの中身を修正する」）に固着。**
3. **3回目**: ユーザーが明示的に「ステータスってなんのステータス？」と問いを繰り返した。§4.2「ユーザーが同じ指示を2回繰り返したら、前回の実装を0ベースで再評価」が発火すべきだったが、AIは依然として「ステータスの値や配置を変える」という解釈フレームから脱却できなかった。

**判断チェーンの誤り箇所**: ユーザーの指摘対象を「ステータスの中身」と認識した初回の時点で誤り。以降、§4.2の「0ベースで再評価」ルールが存在するにもかかわらず、同一の解釈フレーム内で微調整を繰り返した。

### 直接原因

1. **解釈固着（anchoring）**: 初回に「ステータスの中身が問題」と解釈し、以降のフィードバックを全てその枠内で処理した。ユーザーの指摘が「ラベル語そのものの曖昧さ」であることに気づかなかった。
2. **§4.2「0ベースで再評価」の不履行**: 2回目の指摘時点で§4.2が発火すべきだったが、AIは「前回と異なる修正をした」ことを「0ベースで再評価した」と誤認した可能性がある。0ベースとは「前回の解釈フレーム自体を破棄し、ユーザーの言葉を文字通り再解読する」ことであり、「同じ解釈の中で別の修正案を試す」こととは異なる。
3. **§4.1「確認優先」の不履行**: 「ステータス」が何を指すか不明瞭だとユーザーが指摘しているのに、AIは確認せず推測で修正を実行した。

### 根本原因

§4.2の「0ベースで再評価」ルールの**実行定義が曖昧**。ルール自体は存在するが、「0ベースで再評価する」が具体的に何を意味するか（解釈フレーム自体の破棄なのか、同一フレーム内での別案検討なのか）が明文化されていない。そのため、AIが「別の修正を試した」ことを「0ベースで再評価した」と自己評価してしまうリスクがある。

### MD上の原因

MDの記述は明確。問題は行動側にある。

ただし、§4.2の「0ベースで再評価」の運用定義に補強余地がある（後述）。

- **誤読パターン**: AIが修正フィードバックを受けた際、初回の解釈フレーム（「何を修正対象とするか」の認識）を維持したまま、修正の内容だけを変える。

- **影響**: 3回連続の誤修正によるユーザー体験の悪化。同種事故の再発（MR-136 と同パターン）。
- **根拠**: 本事故で実際に発生。AIは2回目・3回目で異なる修正を試みたが、「ステータスの中身を修正する」という解釈フレームは維持されたまま。
