## 【パターン 2: 誤読・ミス原因分析】

### 事象

LINE双方向会話モード中（active: true）、md-reviewer サブエージェントの結果報告を LINE に送信する際に、`send_ntfy`（一方通行）を使用した。先行する `send_ntfy_and_wait`（起動報告）が Bash auto-background でバックグラウンドに残存していたことを理由に、「2つ目の send_ntfy_and_wait を同時に走らせると問題がある」と判断し、send_ntfy にダウングレードした。

### 読み手がどう解釈した可能性があるか

1. **「BG に send_ntfy_and_wait が残っている → 新たに send_ntfy_and_wait を FG で呼ぶと2つ同時に走る → 混信の恐れ」**: AIは技術的な懸念（同一 ntfy トピック上で2つの send_ntfy_and_wait が返信を奪い合う）を推論した。068 L206 に「IDでフィルタしているため安全」と書かれているが、AIはこの保証に到達しなかった
2. **「send_ntfy_and_wait が呼べないなら send_ntfy で代替」**: L69 の禁止を認識しつつ、「技術的に不可能だから仕方ない」と自己正当化。CLAUDE.md に「代替として send_ntfy を使ってはならない」「先行BGプロセスを解消してから send_ntfy_and_wait を呼べ」という指示がないため、この自己正当化を阻止する文面が不在
3. **md-reviewer の結果報告は「情報提供」であって「返信を求める送信」ではないという誤分類**: 068 L23-25 の判定基準「送ったあと何か返信を受け取る必要があるか？ No → send_ntfy」に引き寄せられた可能性。LINE会話モードの文脈ではこの判定基準が上書きされる（全ての応答が send_ntfy_and_wait）が、068 の早見表は LINE 会話モードの上書きを記載していない
