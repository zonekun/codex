## 【パターン 4 固有: 誤読・ミス原因分析】

### 1. 事象

PSメニュースクリプトのパスを探すタスクにおいて、AIはCLAUDE.md §10 高頻度参照テーブルを確認せず、Grepでプロジェクト内を直接探索した。023知見MDの line 7-8 に `C:\Users\zonekun\Dropbox\stock\script\claude-investment-agent.bat` と `C:\Users\zonekun\Dropbox\stock\script\claude-investment-agent.ps1` が明記されており、Read 1回で完了するタスクだった。

### 1.5. AIの思考回路（推定）

1. 「PSメニュースクリプトのパスを探す」というタスクを受け取る
2. UserPromptSubmit hook が「[索引ファースト]」リマインダを出力する
3. AIはリマインダを認知するが、「ファイルパスを探す」タスクを「ファイル検索」と分類し、Grep/Glob が最も直接的な手段と判断する
4. CLAUDE.md §10 のテーブルには「PS1 / PSメニュー」エントリがあるが、AIはテーブル照合ステップを**スキップ**し、直接検索ツールに進む
5. **判断の分岐点**: AIは「知見MDを読んでパスを見つける」という間接経路よりも「Grepで直接パスを検索する」という直接経路を選択した。これは「ファイルパスの物理的探索」と「知見MDの情報参照」を別のタスクカテゴリと誤分類した可能性が高い

### 2. 直接原因

- AIが CLAUDE.md §10 高頻度参照テーブルの照合ステップを実行しなかった
- hook のリマインダが認知されたにもかかわらず行動に反映されなかった

### 3. 根本原因

- **意志依存型ルールの構造的限界**: 索引ファースト原則は「AIがルールを想起し、自発的に従う」ことに依存しているが、4回の再発実績が示す通り、この方式では安定的な遵守を実現できていない
- **リマインダ型hookの限界**: `keyword_md_gate.py` は毎回リマインダを表示するが、AIの行動を物理的にブロックする機構ではない。MR-066で導入された改善策（hook追加）が十分な効力を発揮していない
- **タスク分類の認知バイアス**: 「パスを探す」→「検索する」という思考パスが、「パスを探す」→「知見MDを読む」という思考パスよりも強く活性化される傾向がある。これはAIの行動パターンに内在する問題であり、MDの表現改善だけでは解決できない

### 4-1. MD上の原因

- **該当なし**: CLAUDE.md §10 の記述は十分に明確。「PS1 / PSメニュー | 023_powershell_menu.md」は「PSメニュースクリプトのパスを探す」タスクに意味的に該当することが明白。hook のリマインダも毎回出力されている。MD側に改善すべき曖昧性は見当たらない

### 4-2. MD構成原因

- **CLAUDE.md → hook → memory の3層導線は適切に構成されている**: CLAUDE.md §10（正本）→ `keyword_md_gate.py`（UserPromptSubmit hook、毎回発火）→ memory `feedback_claudemd_index_first.md`（補助）。リファレンスは適切に張られている
- **構造的強制の欠如**: 3層すべてが「AIの自発的行動」に依存している。CLAUDE.md は「～せよ」、hook は「～照合せよ」、memory は「～する」。いずれも命令形だが、違反を**阻止**する機構がない

## 【重大な指摘】（即修正）

### #1 索引ファースト hook（keyword_md_gate.py）がリマインダに留まり行動阻止力がない

- **箇所**: `scripts/keyword_md_gate.py`、`.claude/settings.local.json:122-129`
- **問題**: hook は毎回「[索引ファースト] ファイル探索・データ確認・回答検討する際は最初にCLAUDE.md §高頻度参照テーブルを照合せよ」と出力するが、AIがこのリマインダを無視しても何も起きない。MR-066で導入されて以来4回の違反が発生
- **AIの誤読パターン**: 誤読ではなくリマインダの無視。AIの内部優先度で「直接検索のほうが速い」と判断した場合、リマインダは抑止力にならない
- **トリガー**: 「パスを探す」「ファイルを見つける」「どこにある」等のファイル探索タスク
- **影響**: 知見MDに記載済みの情報を無駄に Grep/Glob で探索する時間・トークンの浪費。ユーザー体験の劣化
- **根拠**: MR-066（アダプタパス）、MR-117（会社名テーブル）、MR-123（BQスキーマ）、本件MR-153（PSメニューパス）の4件が同一パターン
- **推奨対応**: [方向性] PreToolUse hook（Grep/Glob 発火時）で「CLAUDE.md §10 を確認したか」を検証する仕組みの導入を検討する。Claude Code の hook API の制約調査が前提。調査結果に応じて、実装可能であれば `scripts/keyword_md_gate.py` を PreToolUse 対応に拡張する。実装不可能であれば、004 §事故パターンDB への集約で次善策とする
- **MD修正だけで足りるか**: 足りない。MD の記述は十分に明確。行動を物理的に制御する仕組みが必要

#### ユーザー判定: 却下（2026-05-12）

PreToolUse hook への昇格を検討したが、prompt型hookはUserPromptSubmitでもPreToolUseでも本質的に同じ（AIへのテキスト注入）であり、AIが無視すれば効かない点は変わらない。タイミングが「検索直前」に変わるだけで「貼り紙の場所が変わった」に過ぎず、実装コストに見合う効果は期待できない。本当に阻止するには `exit 1` でツール実行をブロックする必要があるが、「索引を先に見たか」をプログラムで判定するのは困難（直前のRead履歴パース等、複雑になる）。対策は打たず、CLAUDE.md §10 の記述のみで運用する。
