# レビュワー起動遅延パターン — 「レビュー提出せよ」でAgent起動に至らない再発事故

- 提出日: 2026-05-07 JST
- パターン: 2（誤読・ミス報告に対する改善レビュー）
- 報告者: メインエージェント
- 関連レビュー: 018_forgot_to_run_reviewer.md（同根の初発事故）

---

## 事象

ユーザーが「mdレビューに事故のレビュー依頼」と指示した。メインエージェントはレビューMD（093_mr_load_split_blind_spot.md）を作成したが、md-reviewer Agentを起動しなかった。ユーザーが「レビュー終わってない？」と催促して初めて起動忘れに気づき、md-reviewerを起動した。

これは018（2026-04-29）と**同一パターンの再発**であり、018で定めた再発防止策（提出→起動のアトミック制約、097_review_submission_guide.md §1-3）が機能していない。

### 会話ログ（該当部分）

```
ユーザー: mdレビューに事故のレビュー依頼　続く
ユーザー: （事故内容を入力）

AI: BGエージェント起動。MR-093（ロード分割の盲点）をレビューMDとして作成中です。
（← レビューMD作成のAgentは起動したが、md-reviewer Agentは未起動）

AI: レビューMD完成。内容を確認します。
（← 確認・修正を実施。しかしmd-reviewer起動なし）

AI: MR-093 作成完了。19:50 JST の CronCreate で2巡目の死亡確認後、
    分割configで再投入します。
（← 別タスクの話に移行。md-reviewer起動を完全に忘却）

ユーザー: レビュー終わってない？

AI: すみません、MR-093の作成は完了しましたが、
    MDレビュー（AI可読性レビュー）への提出がまだでした。
（← ここで初めてmd-reviewer Agentを起動）
```

### 問題の規模

ユーザーは「エージェント起動に至らない例が多数」と報告しており、018と今回の2件に限らず**構造的・反復的な問題**である。

---

## 根本原因分析

### 直接原因

レビューMDの「作成」と md-reviewer Agent の「起動」が認知的に分離されており、作成完了時点で「レビュー提出の作業は終わった」と誤認する。

### 018からの再発理由

018の再発防止策として097_review_submission_guide.md §1-3に「提出MD作成→Agent起動はアトミック。中断禁止。」が追記された。しかし以下の理由で機能していない:

1. **097ガイドを読んでいない**: レビュー提出時に097を毎回参照する習慣がない。CLAUDE.md高頻度参照テーブルにL247「レビュー提出」エントリは存在するが、AIの認知ラベル（「レビューMD作成」）とキーワード（「レビュー提出」）が一致せず照合に失敗していた（※初版で「行がない」と記載したのは事実誤認。md-reviewerレビュー#1で指摘）
2. **「レビューMD作成」と「レビュー提出」の混同**: BGエージェントにMD作成を委譲した場合、MD完成の通知を受けた時点で「提出完了」と認知する。実際にはmd-reviewer起動がまだ残っている
3. **BGエージェント委譲による認知分断**: MD作成をBGエージェントに任せると、作成完了通知 → 内容確認 → 修正 → 次タスク、と複数ステップが入り、md-reviewer起動のタイミングが曖昧になる
4. **高頻度参照テーブルのキーワード齟齬**: CLAUDE.md §高頻度参照テーブルにL247「レビュー提出」の行は存在するが、AIが「レビューMD作成」という認知でタスクに取り組んでいる場合にマッチしない（※初版で「行が存在しない」と記載したのは事実誤認。md-reviewerレビュー#1で指摘）

### パターンの構造的要因

```
ユーザー指示「レビュー提出せよ」
  ↓
Step 1: レビューMD作成（BGエージェント or 直接Write）
  ↓
  ← ここで「作成完了」の達成感が発生
  ← 内容確認・修正の作業が入る
  ← 別タスクの話題が入ることもある
  ↓
Step 2: md-reviewer Agent起動 ← ★ここが脱落する
```

提出MD作成は成果物（ファイル）が生まれるため「完了した」という感覚が強い。一方md-reviewer起動はAgent()の1コールで、成果物がない「配線作業」に過ぎない。認知的重要度の非対称性が脱落を招く。

## 再発防止案

### 案1: ~~CLAUDE.md高頻度参照テーブルにレビュー提出を追加~~ → キーワード改善に変更

~~テーブルにエントリがない~~ → 実際にはL247に既に存在。キーワードを「レビューMD作成・提出・Agent起動」に改善し、AIの認知ラベルとのマッチ率を上げる。（md-reviewerレビュー#1,#3採用に基づく訂正）

### 案2: レビューMD作成とmd-reviewer起動を同一ターンで実行する運用ルール

「レビューMD作成をBGエージェントに委譲 → 完了通知を待つ → 確認 → md-reviewer起動」ではなく、**メインエージェントがレビューMDをWriteで直接作成し、同一ターンでAgent起動する**。BGエージェント経由のMD作成は認知分断を招くため禁止。

### 案3: 097ガイドに「BGエージェント委譲時の注意」を追記

BGエージェントにMD作成を委譲した場合でも、完了通知受信後の**次のアクションは必ずmd-reviewer起動**であることを明記。

### 案4: PostToolUseフック（将来検討）

`docs/reviews/` にWriteした直後に「md-reviewer Agentを起動しましたか？」と警告するフック。現時点ではMD修正で十分と判断するが、再々発時は検討。

## 【AI 誤読リスク】

1. **高頻度参照テーブルのキーワード不一致**: L247の「レビュー提出・返却・苦情申し立て」は、AIが「レビューMDを作成する」「レビュー依頼を書く」という認知でタスクに取り組んでいる場合にマッチしない。AIは「レビューMDの作成」を「文書の作成タスク」として処理し、「レビューの提出」という別カテゴリとして認知しない。高頻度参照テーブルのトリガーキーワードと、AIの実際のタスク認知ラベルにギャップがある

2. **「レビューMD作成」で完結する認知構造**: AIがBGエージェントにMD作成を委譲し、完成を確認した時点で「Write完了→タスク完了」のメンタルモデルが成立する。Agent起動は「提出」プロセスの一部だが、AIの認知上はMD作成とAgent起動は別タスクに分類される。097ガイドに「アトミック」と書いてあっても、097を読む発火条件（=「レビュー提出」という認知ラベル）にAIが到達しなければルールは適用されない

3. **索引ファーストフックの限界**: `keyword_md_gate.py` は毎プロンプトで「CLAUDE.md §高頻度参照テーブルを照合せよ」と出力するが、AIがテーブルを照合する際に「今やっているタスクはレビューMDの作成だ」→テーブルに「レビューMD作成」の行はない→マッチなし、と判断する可能性がある。実際にはL247「レビュー提出」がマッチすべきだが、AIの認知ラベルとの齟齬が照合失敗を招く

## 【パターン 2: 誤読・ミス原因分析】

### 事象

ユーザーが「mdレビューに事故のレビュー依頼」と指示。メインエージェントはレビューMD（MR-093）を作成したが、md-reviewer Agentを起動しなかった。ユーザーの催促で初めて起動。018と同一パターンの再発。

### 読み手がどう解釈した可能性があるか

1. 「レビュー依頼」→「レビューMDを作成する」→タスク完了。「依頼」の完了条件を「MDファイルの作成」と認知し、「Agent起動」は別タスクと認知
2. 索引ファーストフックが発火し高頻度参照テーブルを照合したが、「レビューMD作成」というタスクラベルにL247「レビュー提出」がマッチしなかった（あるいは、L244「MDレビュー」にマッチしてmd-reviewerスキルの方を参照したが、スキルMDのメインエージェント側手順は§1に委譲しており、097を読みに行かなかった）
3. BGエージェントにMD作成を委譲した時点で「レビュー依頼の実行中」という認知が成立し、BG完了通知で「完了」に遷移。Agent起動という残タスクが認知上消滅

### 直接原因

097ガイド §1-3 のアトミック制約ルールが事故時に参照されなかった。高頻度参照テーブルにL247として導線が存在するにもかかわらず、「レビューMD作成」というAIの認知ラベルがこのエントリに結合されなかった。

### 根本原因

**018の再発防止策が「ルール追記」に留まり、構造的強制を伴わなかったこと。** 具体的には:

1. **ルールの到達性の問題**: 097にアトミック制約を書いても、097が読まれなければ無意味。高頻度参照テーブルにエントリはあるが、キーワードの齟齬（「レビュー提出」vs「レビューMD作成」）で照合に失敗する
2. **意志依存型の再発防止策**: 018レビューの推奨は「ステップ間に注意書きを追加」「即座に実行すべきことを明記」等のルール追記であり、いずれも「AIがルールを読み、遵守する」ことを前提とする意志依存型。ルールに到達できなければ機能しない
3. **構造的強制の先送り**: 018レビューでもPostToolUseフックが言及されたが「過剰」として見送られた。今回の提出MDでも案4として同じフックを提案しつつ「MD修正で十分」として先送りしている。018で導入していれば今回の再発は防げた

### 誤読を許した MD 上の原因

| 箇所 | 問題 |
|------|------|
| `CLAUDE.md:247` | 「レビュー提出・返却・苦情申し立て」のキーワードが「レビューMD作成」というAIの認知ラベルにマッチしない。テーブルには存在するが発見されない |
| `CLAUDE.md:242-247` | レビュー関連エントリが3行に分散（L242/L244/L247）。AIが「レビュー依頼」タスクでどのエントリを引くべきか不明瞭 |

### 再発防止の方向性

意志依存型（ルール追記）は018で失敗が証明された。構造的強制（フック）に移行すべき。

### 対策スコープ

本件は「レビュー提出」固有の問題に見えるが、より広いパターン「2ステップ操作の第2ステップ脱落」として汎用化できる。ただし現時点で同パターンの事故が他タスクで発生しているエビデンスがないため、まずはレビュー提出固有の構造的強制（PostToolUseフック）で対処し、他タスクでの再発時に汎用化を検討する。

### 副作用シミュレーション（8c）

**(i) 単体副作用**:
- PostToolUseフックが `docs/reviews/` への全Write時に発火する。レビュアー（サブエージェント）がレビュー結果を書き込む際にも発火する。サブエージェント側では「Agent起動」は不要なので、フックメッセージが不適切に見える可能性がある。対策: フックメッセージに「提出側（メインエージェント）のみ対象」と明記するか、ファイル名パターン（NNN_mr_/NNN_cr_/NNN_so_ の新規作成 vs 既存ファイルへの追記）で判定する

**(ii) クロスルール競合**:
- keyword_md_gate.py（UserPromptSubmit）と review_submit_hook.py（PostToolUse）は発火タイミングが異なり競合しない
- 097ガイド §1-3 のアトミック制約と、CLAUDE.md §ライン会話モードの「非同期サブタスク起動」パターン（018レビューで追記済み）は補完関係にあり競合しない

**(iii) 状態依存シナリオ**:
- ライン会話モード中のレビュー提出: フックがPostToolUseで発火するため、ライン会話モードの状態に依存しない。安全

**(iv) 再発防止策の実効性**:
- PostToolUseフックは構造的強制であり、意志依存ではない。Write完了後に自動発火するため、AIの認知状態に依存しない
- 残存リスク: AIがフックの警告を見ても無視する可能性。ただしフックは「具体的な行動指示」（Agent起動しましたか？）を含むため、無視するには意識的な判断が必要。意志依存型よりも強い

### 事後確認事項（8d）

- フックの発火がAIの作業フローを過度に阻害していないか確認する（低頻度イベントのため問題は少ないと予想）
