## 【パターン2: 原因分析】

### 1. 事象

- ユーザーが「OK」と発言 → Claudeが「21:40 待ちます」と返し無視
- ユーザーが「だからOK」と再発言 → 同じ応答を繰り返し無視
- ユーザーが「もう過ぎているぞ」と指摘して初めて動作
- ログ確認後の完了報告時も「2窓は正しく表示されましたか？」と余計な確認質問を追加

### 1.5. AIの思考回路（推定）

Claudeは「タスクが21:40に起動する予定」という内部状態を保持していた。「OK」を受け取った際、Claudeは次のような判断チェーンを実行したと推定される:

1. **文脈フレーム固定**: 「21:40まで待機する」という直前の発言フレームが強く残存していた
2. **「OK」の意味の文脈依存解釈**: 「了解した（引き続き待つ）」という意味に誤解釈した。§4.5 の「GOシグナル＝実行指示」というルールを参照せず、会話の流れの中で「承認的返答」として処理した
3. **GOシグナルルール不発火**: §4.5は「作業開始前の待機判定」として脳内に分類されており、「既に待機状態」の文脈では適用対象外と誤判断した可能性が高い
4. **時刻確認の欠如**: 「21:40になるまで待つ」という命題が前提として残存し、現在時刻を確認することなく「21:40待ちます」と繰り返した。§4.1「事実確認が可能なことを確認せずに発言しない」の発火条件（時刻は確認可能な事実）を見落とした
5. **完了後の確認質問**: 完了報告後に「2窓は正しく表示されましたか？」を追加したのは、ユーザーが既に「OK」を発していた事実を上書きして独自に確認フローを継続しようとした行動。完了宣言が「報告」ではなく「再確認トリガー」になった

**判断チェーンの分岐点**: §4.5 の「GOシグナル＝実行指示」が「待機中の状態遷移トリガー」としてではなく「タスク着手の前提条件」としてのみ解釈された。GOシグナルは状態に関係なく常に有効なはずが、「待機状態」というコンテキストによって上書きされた。

### 2. 直接原因

(a) **§4.5の適用スコープ誤認**: §4.5の「明示的GO（OK/進めて等）がなければ作業開始しない」という文言が「タスク開始前」にのみ適用されると誤解釈された。「既に待機状態にある」文脈でもGOシグナルは有効であるという明示がない。

(b) **時刻確認ルールとGO判定の統合不足**: §4.1「事実確認が可能なことを確認せずに発言しない」と、ユーザーが「OK」と言った時点での現在時刻確認が結びついていない。「21:40待ちます」という発言は時刻という事実の確認なしに行われた。

(c) **完了報告後の確認質問の抑制ルール不在**: ユーザーが既にGOシグナル（「OK」）を出している状況での完了報告後の追加確認質問を明示的に禁止するルールがない。

### 3. 根本原因

§4.5は「作業開始前の待機判定ルール」としての文脈で書かれており、「进行中の作業（待機フェーズ）でGOシグナルを受けた場合の状態遷移」という観点が含まれていない。GOシグナルが「状態に依存せず常に有効」であることが明示されていない。

また §4.1 の「事実確認が可能なことを確認せずに発言しない」は汎用原則として書かれているが、「時刻を言及する前に現在時刻を確認する」という具体的導線が §4.5 に存在しない。memoryの `feedback_check_timestamps.md` はジョブ経過時間に特化した記述であり、「時刻を言及する前のGet-Date確認」というより広い適用を明示していない。

### 4-1. MD上の原因

- `CLAUDE.md §4.5` L78: 「明示的GO（OK/進めて等）がなければ作業開始しない」→「作業開始」という表現が「タスク開始前」の適用と読めてしまう。「状態に関わらずGOシグナルは即トリガーとなる」という明示がない
- `CLAUDE.md §4.5` L81: 「判定基準: 『未完了シグナルの不在』ではなく『GOシグナルの存在』で判定する」→ これ自体は正確だが、「待機フェーズ中」でも同じ判定基準が適用されることが不明

### 4-2. MD構成原因

- §4.5 と §4.1 の間に「時刻を発言する前に Get-Date で確認する」という結びつきがない
- §4.5 の GOシグナル判定が「作業開始判定」という1つの状況にしか言及しておらず、「待機中のGO」「完了後のGO」など他の文脈での適用が明示されていない
- memoryの `feedback_check_timestamps.md` はジョブ経過時間に特化しており、「時刻を発言する前の確認」というより広い原則をカバーしていない

### 5. 再発防止

**MD側（§4.5）への追加**（CLAUDE.md §1 ポリシー適合: 原則1行＋ポインタ形式）:
- 「GOシグナルは会話状態に関係なく即トリガー。待機中・作業中を問わず有効」という1行を §4.5 に追加
- 「時刻に言及する前に Get-Date で現在時刻を確認する（§4.1 事実確認）」へのポインタを追加

**memory側（`feedback_check_timestamps.md`）の拡張**（CLAUDE.md §4.3 feedbackライフサイクル規則に従い更新）:
- 現在の「ジョブ経過時間」特化の記述を「時刻・経過時間を発言する前は必ず確認ツール（Get-Date/gcloud）を使う」という広い原則に拡張

**完了報告後の追加確認禁止**:
- ユーザーが完了確認済み（GOシグナル発話済み）の状況での再確認質問を §4.1 または §4.5 で明示禁止化

### 6. 新規リスク

## 【重大な指摘】

### 指摘1: §4.5 のGOシグナル判定が「作業開始前」に限定して読める

- **箇所**: `CLAUDE.md §4.5` L77-81
- **問題**: 「明示的GO（OK/進めて等）がなければ作業開始しない」という文言が「タスク着手前の判定」としてのみ解釈される余地がある。「待機中」「確認待ち中」「作業中」のいずれの状態でもGOシグナルは即トリガーとなるべきだが、その明示がない
- **誤読パターン**: 「自分はすでに待機状態にある → §4.5 は作業開始前ルール → この文脈では適用外 → 『OK』を待機継続の承認と解釈」
- **トリガー条件**: 「21:40まで待つ」等の内部状態を持っている会話フェーズで「OK」が来た場合
- **影響**: GOシグナルが無視され、ユーザーが同じ指示を繰り返す必要が生じる
- **根拠**: 本事故の再現。CLAUDE.md §4.5 L81「GOシグナルの存在で判定する」は正確だが、適用スコープ（状態依存しない）が不明
- **推奨対応**: §4.5 の先頭行または「GOシグナル」bullet の後に「**GOシグナルは会話状態に依存しない。待機中・確認中・作業中を問わず即トリガー**」を1行追加（CLAUDE.md §1 ポリシー: 原則1-3行）
- **MD修正で足りるか**: Yes（1行追加。構造的強制は不要）

### 指摘2: 時刻発言前の確認義務がCLAUDE.mdに導線なし

- **箇所**: `CLAUDE.md §4.1`（事実確認優先）と memory `feedback_check_timestamps.md`
- **問題**: §4.1 の「日付属性は python/date で確認」はBQデータ属性を想定した記述。「現在時刻を発言前に Get-Date で確認する」という日常会話文脈の適用が明示されていない。memory の feedback はジョブ経過時間に特化しており、スコープが狭い。コンテキスト圧縮後にmemoryが消えると当該ルールへの導線がゼロになる
- **誤読パターン**: 「『21:40になったら』という文脈で『OK』が来た → 21:40まで待機が継続 → 現在時刻を確認せずに『21:40待ちます』と発言」
- **トリガー条件**: 時刻に言及する応答（「X時まで待ちます」等）を行う際
- **影響**: 実際には時刻が過ぎているにもかかわらず「待ちます」と発言し続け、ユーザーに指摘されるまで気付かない
- **根拠**: 本事故。memory `feedback_check_timestamps.md` は存在するが「ジョブ経過時間」に限定した記述。CLAUDE.md §4.1 には「時刻を言及前に確認」の明示なし
- **推奨対応**: §4.1 の「日付属性は python/date で確認」を「日付・時刻に言及する前は必ず確認ツール（Get-Date 等）で実値確認。推測・記憶で発言禁止」に拡張（1行以内で収まる）
- **MD修正で足りるか**: Yes
