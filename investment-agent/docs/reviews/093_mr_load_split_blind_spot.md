# MR-093: ロード分割の盲点 — タイムアウト延長のみ提案

**作成日**: 2026-05-07
**種別**: 運用レビュー（ユーザー指摘）
**重大度**: 中（ユーザー指摘で即是正）

---

## 事象

2026-05-07、2022年H1バックフィルの Load ジョブ（tdnet-load-daily）が約32,400件を1本の Cloud Run Job execution で処理しようとし、task-timeout 21,600秒（6h）でタイムアウト死した。タイムアウト後、maxRetries:1 による自動2巡目も同じタイムアウトで死ぬ見込みだった。

### タイムライン

| 時刻 (JST) | イベント |
|-------------|---------|
| 07:46 | 1巡目 Load 開始（32,400件 / 1 execution） |
| ~13:46 | 6h 経過でタイムアウト死。抽出は完了していたが BQ アップロード前に打ち切り |
| 13:47 | エージェントが2巡目自動開始を検知 |
| — | ユーザーから「時間長くない」と指摘 → タイムアウトが原因と特定 |
| — | **エージェントの提案: 「task-timeout を 43,200秒（12h）に延長して再投入」のみ** |
| — | **ユーザーから「並行でロード件数を分割　タイムアウト延長より 分割すべき」と指摘** |
| — | 指摘後に config 修正（4 load / parallel_loads: 2）で是正 |

### 背景データ

- 2021-H2: 31,508件 → 4h57m で成功（1本で収まった）
- 2022-H1: ~32,400件 → 6h で抽出のみ完了。BQ アップロードに到達せずタイムアウト
- `monitor_backfill.py` は `parallel_loads` パラメータで複数 load の並行実行を既にサポートしていた
- Workflow は既に Q1a/Q1b/Q2a/Q2b の4分割で設計済みだった（OOM 対策）

---

## 問題分析

### なぜ「タイムアウト延長」しか提案できなかったか

1. **直近の成功体験への固着**: 2021-H2 が31,508件/1本で成功していたため、「32,400件も1本で行ける、タイムアウトさえ伸ばせば」と短絡した。件数がほぼ同じでも処理時間が線形とは限らない（データ特性・GCS blob 構成・PDF サイズ分布の差異）ことを考慮しなかった

2. **設計の非対称性を見逃した**: Workflow（抽出側）は Q1a/Q1b/Q2a/Q2b の4分割で設計されているのに、Load は1本のまま。「抽出は分割するのに Load は分割しない」という非対称性に違和感を持つべきだった。分割粒度が揃っていないこと自体が設計不整合のシグナル

3. **既存の並列化機能を活用しなかった**: `monitor_backfill.py` の `parallel_loads` パラメータの存在はコード読みで把握済みだった。にもかかわらず、タイムアウト発生時にこのパラメータの活用を想起できなかった。「知っている」と「使える」の間にギャップがあった

4. **「対症療法」で止まる思考パターン**: タイムアウト → タイムアウトを延長、という1手だけで提案を終えた。「なぜタイムアウトしたか」の原因（処理件数過多）に遡り、原因側を解消する選択肢を検討するステップが欠落していた

### なぜ監視中にタイムアウトを予防検知できなかったか（苦情 093-1 による追加分析）

上記の分析は「タイムアウト発生後にどう対処すべきだったか」に焦点を当てているが、より本質的な問題はその手前にある: **監視中にタイムアウト死を予防できなかった**。

1. **監視対象が execution status に限定されていた**: 監視中に確認していたのは execution の状態（RUNNING/SUCCEEDED/FAILED）のみ。ジョブの内部フェーズ（テキスト抽出 → BQアップロード）の進捗を Cloud Logging で確認していなかった

2. **フェーズ進捗から完了見込みを推定していなかった**: 抽出フェーズだけで6時間消費していた事実は、Cloud Logging で「抽出 N件目 / 全M件、経過Xh」を確認すれば、タイムアウト3-4時間前に「BQアップロードの時間が残らない」と検知できた

3. **自己策定ルールの不遵守**: `093_monitoring_obligation.md` §ジョブの進捗確認手法 に「Cloud Logging を直接読む」「フェーズ遷移ログ → 現在どの段階か」「最終ログのタイムスタンプ → 想定処理時間に対して古すぎればstallの疑い」と明記しており、エージェント自身が策定したルールに自分が従っていなかった

これは「タイムアウト後にどう対処するか」ではなく、「タイムアウト前に予防監視できたか」の問題である。

### 構造的な問題

「件数が増えたらタイムアウトを伸ばす」はスケールしない。2022-H2、2023 と件数が増え続ければ、いずれ Cloud Run Job の最大タイムアウト（24h）にも達する。分割・並行化こそがスケーラブルな解であり、既にその仕組み（`parallel_loads`、4分割 config）が用意されていたのに、第一選択に上がらなかったのが本質的な問題。

## 再発防止

### ルール1: Cloud Run Job / バッチ処理のタイムアウト発生時の検討フロー

Cloud Run Job やバッチスクリプトがタイムアウトした場合、以下の2つを**必ず両方**検討し、分割可能なら分割を第一選択とする:

| 選択肢 | 適用条件 | 注意 |
|--------|---------|------|
| **処理分割（第一選択）** | 処理単位が分割可能で、並列化インフラが存在する | スケーラブル。件数増加に耐える |
| タイムアウト延長（次善策） | 処理が原理的に分割不可能な場合のみ | 場当たり。Cloud Run Job 最大24hの天井がある |

「タイムアウト延長」のみの提案は禁止。分割を検討した上で不可能な理由を明示する場合のみ延長を提案してよい。

### ルール2: パイプラインの分割粒度は対称であるべき

Workflow（抽出）と Load（取り込み）の分割粒度は揃える。一方だけ分割で他方が一枚岩になっていたら設計不整合のシグナル。config 作成時に「抽出N分割 → Load も N 本（または parallel_loads で並行化）」の対称性を確認する。

### ルール3: 既存の並列化パラメータを常に検討する

スクリプトに `parallel_loads`、`--workers`、`--parallel` 等の並列化パラメータが存在する場合、ジョブのスケーリング問題が発生した時点でそれらの活用を第一に検討する。「コードを読んで知っている」だけでは不十分。問題発生時に想起・提案するところまでが「知っている」。

### ルール4: 長時間ジョブ監視中のタイムアウト予防チェック（苦情 093-1 による追加）

ルール1-3 はタイムアウト**発生後**の対処策。本ルールはタイムアウト**発生前**の予防策。

監視中の定期チェック（ScheduleWakeup / CronCreate）で、以下を毎回確認する:

1. Cloud Logging でジョブの現在フェーズと処理進捗を確認する
2. 「経過時間 + 残りフェーズの推定所要時間」が task-timeout を超えないか推定する
3. 残りタイムアウト < 推定残り処理時間 × 1.5 の場合、その時点でユーザーに警告し、対処（分割・延長・中断）を提案する

「処理は進んでいるが遅すぎてタイムアウトに間に合わない」ケースは、stall 検知では捕捉できない。速度とタイムアウト残量の比較が必要。
