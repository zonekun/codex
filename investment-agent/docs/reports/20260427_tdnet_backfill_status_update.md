## 4. 運用ミス分析（md-reviewer パターン2）

### 発覚経緯

ユーザー指示でMD反映作業を実施 → 013_tdnet_load.md が「待ち」のまま、active_jobs.md にエントリなし → ユーザーから「なぜ漏れていた」の指摘

### 直接原因

1. **プラン「後片付け」チェックリストの不備**: `013_tdnet_load.md` 更新と `memory` 更新が後片付け項目に含まれていなかった
2. **PostToolUse フック不発火**: `monitor_backfill.py` 内部からの gcloud 呼び出しではフックが発火せず、active_jobs.md に自動追記されない
3. **セッション跨ぎの伝播不全**: 3セッションにまたがる実行で、プランヘッダーのみ更新し包括的な状態伝播が最終セッションで行われなかった

### 根本原因

バックフィル完了時に「どこを更新すべきか」の包括リストが未定義。完了状態が4箇所（プラン / 013 / active_jobs / memory）に散在し、同期メカニズムがない。

### 再発防止方向性

1. バックフィルプラン「後片付け」に 013/active_jobs/memory 更新を標準化
2. 013 インライン状態に最終確認日を必須化（今回対応済み）
3. monitor_backfill.py 完了時の active_jobs.md 自動追記の検討
