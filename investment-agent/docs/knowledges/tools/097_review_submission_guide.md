# レビュー提出・返却・苦情申し立てガイド

> 本ファイルは **提出側（メインエージェント）** のワークフローを定義する。
> レビュワー側の実行手順は各スキル正本（`skills/code-reviewer.md`, `skills/md-reviewer.md`, `skills/structure-optimizer.md`）を参照。

---

## 1. レビュー依頼の提出

> **レビュー提出 = MD作成 + Agent起動（セットで中断禁止）。** MD作成だけでは何も起きない。詳細は §1-3。

### 1-1. 提出用 MD の作成

| スキル | ファイル命名 | 配置先 |
|--------|-------------|--------|
| code-reviewer | `NNN_cr_<slug>.md` | `docs/reviews/` |
| md-reviewer | `NNN_mr_<slug>.md` | `docs/reviews/` |
| structure-optimizer | `NNN_so_<slug>.md` | `docs/reviews/` |

- `NNN` は `docs/reviews/` 内の既存ファイルから空いている最若番を 001 から連番で採番（3桁ゼロ埋め）
- `<slug>` は対象を端的に表す英字スネークケース

### 1-2. 提出 MD に記載する内容

| 項目 | 必須 | 説明 |
|------|------|------|
| レビュー対象ファイルパス | Yes | 複数可。対象が明確でないとレビュワーが探索に時間を使う |
| レビューパターン（code-reviewer / md-reviewer） | Yes | パターン 1〜4 のいずれか。structure-optimizer は不要 |
| 事象・背景 | Yes | なぜレビューを依頼するか |
| 補足情報 | No | 関連コミット・既知の制約・スコープ限定等 |

### 1-3. Agent 起動（アトミック）

提出 MD 作成後、**中断せず即座に** Agent ツールでサブエージェントを起動する。

> **提出MD作成→Agent起動はアトミック。中断禁止。** 提出 MD を作成しただけではレビュワーは起動しない（ファイル監視・自動起動の仕組みは存在しない）。LINE返信等の割り込み処理を挟まないこと（2026-04-29 事故教訓）。

```
Agent(
  description="<スキル名> パターン N",
  prompt="<スキル名>スキル（skills/<スキル>.md）としてレビューを実行せよ。
    提出 MD: docs/reviews/NNN_xx_<slug>.md
    対象: <レビュー対象のファイルパス>
    <追加コンテキスト>"
)
```

### 1-4. メインエージェントの禁止事項

- 004-1 蓄積ログ（`docs/knowledges/tools/004-1_code_review_findings_log.md`）に触れない（サブエージェントのみが書き込み可能）
- スキル MD を Read してインライン実行しない（提出元とレビュアーの境界消滅を防止）

---

## 2. レビュー結果の返却（採用/見送り記録）

レビュワーから結果を受け取ったら、**提出側メインエージェント**は以下を行う。

### 2-1. 各指摘の判定

提出側メインエージェントは、レビュー MD の各指摘に対し、以下のいずれかのステータスを付記する:

| ステータス | 意味 | 記法 | 次のアクション |
|-----------|------|------|---------------|
| 採用 | 指摘を受け入れ、対応する | `[採用]` | 修正を実施する |
| 見送り | 指摘内容は理解したが、現時点では対応しない | `[見送り: <理由>]` | 記録のみ（対応不要） |
| 異議あり | 指摘自体が不適切と考える（→ §3 苦情申し立てへ） | `[異議あり]` | §3 の手順に進む |

### 2-2. 記入方法（末尾追記・Read禁止）

レビュー MD の**末尾に `## 返却` セクションを追記**する。Bash `printf >>` を使い、Read/Edit は使わない（トークン節約）。

```bash
printf '\n---\n\n## 返却 YYYY-MM-DD\n\n- #1: [採用]\n- #2: [見送り: 理由]\n- #3: [異議あり] 理由\n' >> docs/reviews/NNN_xx_slug.md
```

- 指摘番号は `#N` で対応付ける（レビュワーの見出し番号に対応）
- 指摘本文のインライン編集は禁止（従来通り）
- 1回の `printf` で全指摘分をまとめて出力

### 2-3. 提出

判定を追記したレビュー MD をコミットする（プレフィックス: `docs:`）。レビュワーへの再送は不要（レビュワーは苦情申し立てがあった場合のみ再起動される）。

---

## 3. 苦情申し立て（指摘への異議）

レビュー結果の指摘が不適切と判断した場合の手順。

### 3-1. 提出側がやること

1. §2-2 の返却セクション内で該当指摘に `[異議あり]` + 理由を記載する（インライン編集不要）
2. ユーザーに異議内容を報告し、レビュワー再起動の承認を得る

```bash
printf '\n---\n\n## 返却 YYYY-MM-DD\n\n- #1: [異議あり] #1と#3は実質同一の重複指摘\n- #2: [採用]\n' >> docs/reviews/NNN_xx_slug.md
```

### 3-2. 提出側がやらないこと

- **タグ判定をしない**: `reviewer:scope-overreach` 等のタグ分類はレビュワー側の責務
- **004-1 蓄積ログを編集しない**: レビュワーのみが書き込み・削除可能
- **指摘本文を削除・改変しない**: ステータスとコメントの追記のみ

### 3-3. レビュワー側の対応（参考）

苦情を受けたレビュワーは以下を行う（詳細は各スキル MD の苦情受付窓口セクション）:

1. 異議内容を評価し、タグを判定する
2. 妥当な異議の場合: 004-1 の該当エントリを削除し、レビュー不備として自身の誤りを記録する
3. レビュー MD の指摘に `[取消: YYYY-MM-DD — <理由>]` を付記する

---

## 注意事項

- **レビューバック事項の自動適用禁止**: レビュワーが返した指摘・推奨対応・修正文案は、ユーザーの明示的な適用指示があるまで実施してはならない。[採用]ステータスを付けることと、実際に修正を適用することは別のアクション。適用はユーザーが内容を確認し「やれ」「GO」等で指示した後に行う（MR-139: レビュー結果を承認なしに全件適用した事故）
- **レビューMD上の指摘本文はレビュワーの成果物**: 提出側は追記（ステータス付与）のみ。本文の編集・削除は禁止
- **返却は任意ではない**: レビュー結果を受け取ったら、全指摘にステータスを付けて返却する（放置しない）
- **異議と見送りの違い**: 「見送り」は指摘自体は正当だが対応しない判断。「異議あり」は指摘自体が不適切という主張。異議ありの場合のみレビュワー再起動の対象
- **異議ありの典型例**: スコープ外の事象を指摘された / 既に修正済みの問題を再指摘された / 複数の指摘が実質同一内容の重複だった
