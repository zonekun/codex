## 概要

松井証券リサーチネット（QUICKリサーチネット）から株主優待情報をスクレイピング取得する。`update_conse_quick.py` のログイン・ブラウザ操作部分を流用。

## アーキテクチャ（v2: 2段階処理 × 2系統ルート）

### 処理段階

| 段階 | 担当 | 入出力 |
|------|------|--------|
| 1. 生データ取得 | Claude Code（Selenium） | Web → 中間JSONL |
| 2. 構造化加工＋Excel生成 | Claude Code **または** Codex | 中間JSONL → Excel (.xlsx) |

Claude Codeはページのテキストをそのまま保存する。構造化加工（2段階プロンプト）→ シート振り分け → Excel生成は段階2で行う。

### 加工ルート選択

| ルート | 用途 | トリガー |
|--------|------|---------|
| Claude Code直接 | テスト期間中 / Codex不調時のフォールバック | 手動指示 |
| Codex委任 | 本番運用 | 中間JSONL完了後に伝言板経由で委任 |

- **Claude Code直接**: AIテキスト処理（2段階プロンプト）で加工し、openpyxlでExcel生成
- **Codex委任**: 加工指示プロンプトMD＋中間JSONLパスを伝言板に記載。Codex完了時にExcelパスを伝言板に返却

## 画面遷移フロー

既存の `update_conse_quick.py` と共通部分（1〜3）+ 分岐部分（4〜6）。

1. **ログイン**: `https://www.deal.matsui.co.jp/ITS/login/MemberLogin.jsp` → ID/PASS → SMS OTP認証
2. **リサーチネット起動**: GMフレーム「情報検索」→ LMフレーム「リサーチネット」→ CTフレーム「起動する」→ 別ウィンドウ
3. **銘柄検索**: `qrn_frame_menu` 内の `#text input[type='text']` にTICKER入力 → `input[alt='検索']` クリック
4. **株主優待リンク検出**: `qrn_frame_main` 内で `report_yuutai.asp?rcode=XXXX` を含む `<a>` タグを探す
5. **優待ページ遷移**: リンク要素は `ElementNotInteractableException` になるため、**`driver.execute_script(window.location.href=URL)` で遷移**する（`.click()` 不可）
6. **データ抽出**: Table 18（`［権利確定］`〜`［株主優待］`以降のテキスト全体）を取得

### 優待なし銘柄の判定

検索結果の `qrn_frame_main` に `report_yuutai.asp?rcode=XXXX` リンクが存在しなければ優待なし → スキップ。

## 構造化加工ルール（Claude Code担当）

中間JSONLの生テキストを読み、以下のルールで構造化CSVに変換する。

### 出力フォーマット（v2）

- **形式**: Excel (.xlsx)、1ファイル
- **シート構成**: `01`〜`12`（月別）+ `随時`
- **列**: `権利月`, `TICKER`, `会社名`, `優待内容`
- **出力先**: `C:\Users\zonekun\Dropbox\stock\優待\yutai_YYYYMM.xlsx`
- **権利月表記**: 月末基準日は `X月末`（`X月30日` とは書かない）、月中基準日は `X月XX日`
- **シート振り分け**: `kenri_kakutei` テキストを `、` `，` `,` で分割 → 各要素から `(\d{1,2})月` で月番号抽出 → 2桁ゼロ埋めのシートに格納。マッチしない or 「随時」→ シート `随時`。1銘柄が複数月にマッチ → 各シートに1行ずつ出力

### フォーマットルール

| ルール | 説明 | 例 |
|--------|------|-----|
| 選択肢の提示 | 複数選択肢は `(1)Xまたは(2)Y`。多数なら「いずれか一つ」も可 | `(1)菓子または(2)ギフト` |
| ティア内の選択 | 「/」ではなく「または」 | `100:(1)3枚または(2)1,500ポイント` |
| ティア内の複合 | 「+」ではなく「および」 | `2000:(1)16枚および(2)1枚` |
| 異なる優待種別 | 4スペース区切りで独立セクション、各セクションに必要株数 | `...    食事券3枚 必要株数：100` |
| 継続保有条件 | **生データの記載を忠実転記**。株数条件・登録回数も含む。ティア情報との重複を理由に省略しない（v2: 2970事故対応） | `※900株以上を1年以上継続保有（4月・10月の株主名簿に同一株主番号で連続3回以上記載）した株主のみに贈呈` |
| 継続保有の位置 | 各セクション末尾に※で | `...5000:(2)11,500円相当 ※1年以上継続保有した株主のみに贈呈` |
| 権利判定方法 | ティア内に保有期間が含まれていても、権利判定の具体的方法（株主名簿の連続記載回数等）は※注記として**独立記載**する（v2: 4767/5589事故対応） | `※同一株主番号で連続して記載及び記録された回数をもとに算出` |
| 利用条件・補足 | ※で付記、複数は◆で区切り | `※「MyBook」等で利用可◆※1注文につき1枚利用可` |
| 5年以上の増額 | 別ティア行列ではなく※ノートで | `※5年以上継続保有の場合100株以上は500円増...` |
| 将来の制度変更 | ※で付記 | `※27年以降は1年以上継続保有...に変更` |
| 見学会・抽選等 | 本体とは独立セクション化 | `...    抽選で素泊まりプラン無料券 必要株数：1000` |
| 随時優待 | 「随時」プレフィックス付き | `随時 住宅機器付与サービス(工事請負契約時)...` |

### 除去対象（ノイズ）

- 贈呈時期（`贈呈時期：...`、`≪贈呈時期≫`）
- 送付先情報（`≪送付先≫`）
- 免責文言（`●株主優待情報を...`）
- 日付表記（`（2026年4月21日現在）`）
- 写真キャプション（`［写真1］※写真は...`）
- 適用時期セクション（`【適用時期】...`、`【適用実施日】...`）
- 権利確定月・基準日の記述（`※年N回(X月・Y月)`、`※年2回(6月・12月)` 等）— 権利確定月は別列で管理するため優待内容に含めない（v2: 9441/9419事故対応）
- 自明な利用条件（`※新規・既存会員とも利用可`、`新規・既存問わず` 等）— 誰でも使えることを述べているだけの文言（v2: 9557事故対応）
- ランキング・メニュー等のページUI要素

### 保持対象

- 優待品の品名・金額・数量
- 株数ティア別の内容
- 継続保有条件（具体的な登録回数まで）
- 利用条件（利用可能店舗、選択方法等）
- 将来の制度変更予告
- 随時優待の内容

### `?` マーク修復（v2追加）

中間JSONLに `?` が含まれる場合、文字化け・エンコーディング起因の可能性がある（例: 2498「前年6月末?」→「前年6月末日」）。構造化加工時に以下で処理:

1. `?` を検出したら前後の文脈から本来の文字を推定し、近しい文字列に**置換**する
2. 推定不能な場合は `?` を除去する（`?` をそのまま残さない）
3. 修復・除去した箇所をログに記録（ticker, 修復前→修復後）

### 複数権利確定月の銘柄の処理

- 権利確定月ごとに1レコード出力（例: 3月末・9月末 → 2レコード）
- `～変更前～` / `～変更後～` がある場合: 現在適用される方を使う
- 月ごとに優待内容が異なる場合: 各月の内容を切り出して個別レコード化
- 全月共通の優待の場合: 各月のレコードに同じ内容を記載

## プロンプト分離設計（v2）

継続保有条件の脱落が複数件（2970, 4767, 5589）発生した根本原因: 一発プロンプトで「優待内容＋ティア＋継続保有条件」を同時抽出すると、AIが情報の重複排除を過剰に行い保有条件が消える。

### 2段階抽出

| パス | 責務 | 入力 | 出力 |
|------|------|------|------|
| Pass 1 | 優待品名・ティア構造の抽出 | 生テキスト全文 | アイテム一覧、株数ティア別内容、随時優待 |
| Pass 2 | 継続保有条件・権利判定方法の抽出 | 生テキスト全文 | 保有条件一覧（株数・期間・判定方法） |

### マージルール

1. Pass 1 の出力を基本構造とする
2. Pass 2 の保有条件を各セクション末尾に※注記として付加
3. **保有期間×株数の二次元ティア**（例: 1000株×1年以上3年未満:500円、3年以上:2,000円）の場合: Pass 1 がティア構造に保有期間を含めて出力し、Pass 2 が権利判定方法（同一株主番号の連続記載回数等）を補完する。両パスの保有期間情報が矛盾する場合は生テキストを再参照して解決

### 各パスのプロンプト指針

- Pass 1: 「保有条件の記載は不要。ティア構造に保有期間が組み込まれている場合はそのまま含める」
- Pass 2: 「ティア内容は不要。保有条件・判定方法のみ抽出。株数条件を含む全要素を忠実転記」

## 既知の問題・次回改修メモ

- **`?` マーク混入**: 生データ中の文字化け・エンコーディング起因で `?` が混入するケースあり（例: 2498「前年6月末?」）。次回改修時にスクレイピング段階でのエンコーディング確認、または構造化加工時の `?` 検出・警告を検討
- **継続保有条件の株数脱落**（2970）: 生データ「400株以上を6ヶ月以上継続保有」→ フォーマット後「※6ヶ月以上継続保有」と株数条件が脱落。原因: 必要株数（`必要株数：400`）とティアが1段しかないため、AIが「400株は自明」と判断し保有条件から省略した。しかし継続保有条件は「何株を何ヶ月保有すれば権利発生するか」の独立した要件であり、ティア表記とは別の情報。フォーマットルールに以下を追加すべき:
  - **継続保有条件は生データの記載を忠実に転記する。ティア情報との重複を理由に省略しない**
- **継続保有条件の丸ごと脱落**（4767）: 生データでは株数ティアが保有期間で分岐する構造（1000株以上×1年以上3年未満:500円、3年以上:2,000円）。フォーマット後はティア表記に保有期間を埋め込んだが、※注記での継続保有条件（「同一株主番号で連続して記載及び記録された回数をもとに算出」）が丸ごと欠落。原因: ティア表記に期間を組み込んだことで「保有条件は表現済み」と判断し、※注記を省略した。しかしティア内の期間表記は「何をもらえるか」の説明であり、「権利判定方法（同一株主番号×連続記載回数）」は別の情報。対策:
  - **ティア内に保有期間が含まれていても、権利判定の具体的方法（株主名簿の連続記載回数等）は※注記として独立記載する**
- **権利確定月の過剰記載**（9441, 9419）: 「※年2回(6月・12月)」は優待内容ではなく権利確定タイミングの情報。権利確定月は別列で管理する予定のため、優待内容フィールドには含めない。除去対象に「権利確定月・基準日の記述（※年N回(X月・Y月)等）」を追加すべき。複数銘柄で同パターン発生を確認
- **自明な利用条件の過剰記載**（9557）: 「※新規・既存会員とも利用可」は自明な情報であり記載不要。除去対象の基準に「誰でも使えることを述べているだけの文言（新規・既存問わず等）」を追加すべき
- **継続保有の判定方法脱落**（5589）: 生データの※2に「基準日において200株以上保有し、かつ前年基準日に同一株主番号で100株以上保有」という具体的判定ロジックがあるが、フォーマット後は「※200株以上かつ1年以上継続保有の場合15,000円分」と要約され判定方法が消えた。4767と同根。継続保有の「どう判定するか」は省略不可
- **構造化加工のプロンプト分離検討**: 継続保有条件の脱落が2件（2970, 4767）続いた。一発プロンプトで「優待内容＋ティア＋継続保有条件」を同時抽出すると、AIが情報の重複排除を過剰に行い保有条件が消える傾向がある。対策案: プロンプトを2段階に分離する — (1) 優待品名・ティア構造の抽出 (2) 継続保有条件・権利判定方法の抽出 — を別パスで行い、最後にマージする。これにより各パスの責務が明確になり、省略バイアスを抑制できる可能性がある。**注意**: 保有期間がティア金額に直結するケース（例: 1年以上:1,000円、3年以上:3,000円）では、保有期間情報がティア構造の一部でもあるため、分離時に片方のパスだけでは正しく組み立てられない。マージロジックで保有期間×株数の二次元ティアを正しく再構成する設計が必要
