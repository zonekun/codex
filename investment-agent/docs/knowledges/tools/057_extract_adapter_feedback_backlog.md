## フィードバック先A: アダプター作成プログラム (build_monthly_extractor.py)

### A-1. 年バグ: .*? を含む row_label_regex が年テキストを誤抽出

**件数**: 170件（初回突合）
**症状**: `our_value = 2025` または `2026` など年の数字が返る
**根本原因**: `build_monthly_extractor.py` が生成するアダプターの `row_label_regex` に `.*?` が入っており、
`re.search(pattern, full_text, re.DOTALL)` でマッチした後、`rest = src_line[m.end():]` から
最初の数字を取得するロジックが年テキスト（「2025年」「2026年」）を掴んでしまう。

**確認済み銘柄**:
- 2991: `不動産売買事業における.*?取引件数は` → 修正済（キャプチャグループ化）
- 2750: `consolidated_sales_million_yen = 2025` → regex が年にマッチ
- 141A: 固定値をregexにハードコード（`^売上高\s+101\.4\s+98\.3`等）→ 月が変わると古い値を返す

**修正指示（アダプター作成プログラムへ）**:
```
1. row_label_regex には必ずキャプチャグループ（丸括弧）を付与し、
   グループ1で「値」を直接キャプチャするよう生成すること。
   NG: "不動産売買事業における.*?取引件数は"
   OK: "取引件数は\\s*([\\d,]+)件"

2. .*? を row_label_regex に使う場合は、マッチ範囲内に年テキスト（2025等）が
   入らないようにキャプチャグループで値を限定すること。
   NG: "業績は.*?前年同月比で"  →  rest から 2025 を拾う
   OK: "前年同月\\s*比で\\s*[+＋]?([\\d\\uff10-\\uff19.]+)[%\\uff05]"

3. 固定値（特定月の数値）を regex にハードコードしないこと（141A の例）。
   数値は必ずキャプチャグループで動的取得すること。
```

### A-2. 複数フィールド同値: 1つの regex が複数フィールドにヒット

**件数**: 212組（初回突合）
**症状**: `our_value` が複数フィールドで同じ値
**根本原因**:
1. **Rolling table で行特定できない**: 9823 の旧アダプターが `全店.*?売上高\s+\d+\.?\d*\s+\d+\.?\d*\s+\d+\.?\d*\s+\d+\.?\d*\s+(\d+)` と
   固定4列のパターンを想定したが、`STRING_AGG` 後は空白区切りになりかつ列数が月により変動するため
   全フィールドが年間集計値（108.0等）を返していた。
2. **セクション区別なし**: 2461 の旧アダプターが両フィールドに `合計` を使い区別不可。
3. **STRING_AGG の空白区切り**: 元文書の改行は `STRING_AGG` で全て空白に変換されるため、
   `\n` を含む regex は常に NO_MATCH になる。これに気づかずに書かれたアダプターが多数存在。

**確認済み銘柄と修正方法**:
- 9823: 全6フィールドが年間集計値108.0 → `全店\s+前年比\s+（％）\s+売上高\s+([...])` のセクション固有パターン + use_last_number=True に変更済
- 2461: 売上高/取扱高の合計が同値 → セクションヘッダ（売上高/取扱高）で区別済
- 2778: `existing_stores_customers_yoy` と `existing_stores_customer_spend_yoy` が同値 103.7 → 未修正

**修正指示（アダプター作成プログラムへ）**:
```
1. STRING_AGG (空白区切り) を前提としてアダプターを生成すること。
   元文書の改行位置を考慮した `\n` を含む regex は動作しない。
   全て `\s+` で代替すること。

2. 複数フィールドが同一の row_label_keyword を持つ場合（合計、売上高等）、
   セクションヘッダや前置文字列を regex に含めて一意に区別すること。
   NG: "合計"
   OK: "報告セグメント別売上高.*?合計\\s+[\\d,]+\\s+([\\d.]+)"

3. rolling table（複数月の数字が横並び）パターンでは:
   - セクション固有の見出し語を prefix に含める
   - `use_last_number: true` を明示的に設定する
   - 年間集計行との混同を避けるため、セクション名と（％）等の単位記号を regex に含める
   例: "全店\\s+前年比\\s+（％）\\s+売上高\\s+([\\d.]+(?:\\s+[\\d.]+)*)"
       + use_last_number: true
```

### A-3. 抽出位置ズレ: 表の列順を誤認識

**件数**: 推定50件以上（9936等）
**症状**: `our_value` が百万円の売上ではなく前年比（%）の値を返す
**根本原因**: テーブルが `店舗数 前年比 売上高 前年比 ...` の形式で、
アダプターが売上高列でなく前年比列の数字を返している。

**確認済み銘柄**:
- 9936 (餃子の王将): `direct_all_stores_sales_million_yen = 100`（our）vs `9,470`（BC）
  - 実テキスト: `99.7 1,274 107.9 8,428 103.6 6,677 ... 9,470`
  - 100/103 は前年比% → regex が売上高を飛ばして前年比にマッチしている

**修正指示（アダプター作成プログラムへ）**:
```
1. 表形式データでは列の型（金額列 vs %列）を明示的に区別すること。
   金額列の後ろに前年比列が来る場合:
   "売上高\\s+([\\d,]+)\\s+[\\d.]+\\s+"  # 金額([\\d,]+)、次の数字(%列)は非キャプチャ

2. フィールド名が `_million_yen` や `_billion` を含む場合、
   カンマ区切り数字（[\\d,]+）を優先的にキャプチャし、
   小数点のみの数字（前年比%）は誤抽出しないよう regex を設計すること。
```

## フィードバック先B: 数値化プログラム (extract_monthly_data.py)

### B-1. 全角数字の変換漏れ

**件数**: 少数だが発生（2991 等）
**症状**: `our_value = '７'`（U+FF17 全角7）として返る → BC比較で変換エラーまたは不一致
**根本原因**: PDF抽出テキストに全角数字（０-９、U+FF10-FF19）が混入する場合があり、
`_extract_from_match()` がキャプチャグループをそのまま返すと全角文字列になる。
`float()` 変換は `float('７')` でエラーになる（または NaN）。

**確認済み例**:
- 2991: `前年同月\s*比で\s*[+＋]?([\\d\\uff10-\\uff19.]+)[%\\uff05]` で `'７'` を取得

**修正指示（数値化プログラムへ）**:
```python
# 値を数値に変換する前に全角→半角変換を追加すること
import unicodedata
def normalize_value(raw: str) -> str:
    """全角数字・記号を半角に変換する"""
    return unicodedata.normalize('NFKC', raw)

# _extract_from_match() または_extract_numbers() の冒頭で呼ぶ
raw = normalize_value(raw)
```

**件数**: 17件（初回突合）
**症状**: `our_value ≈ bc_value - 100`（例: our=16.5, bc=116.5）
**根本原因**: 文書が「前年同月比 +16.5%」（増減値）、BC が「116.5」（比率）で表現する場合に不一致。
現状の extract_monthly_data.py には「抽出値 + 100」の変換フラグがない。

**修正指示（数値化プログラムへ）**:
```

value_type="percentage" かつ offset_100=true の場合に extracted_value + 100 して保存する。

アダプター例:
{
  "key": "all_store_sales_yoy",
  "row_label_regex": "...",
  "value_type": "percentage",
  "offset_100": true,
  "_note": "文書は増減値(+7.2%)、BCは比率(107.2%)で表現"
```
