# IDEA: サプライチェーン決算連鎖（先行好決算 → 後攻決算またぎ）

## データソース
- @virtualgcn (X/Twitter) — 2026-05-13
- URL: https://x.com/virtualgcn/status/2054543391732711806
- ユーザー着想: イビデン好決算 → ユニオンツール決算またぎの連想

## 根拠となった箇所
> イビデン(4062) 26/3期決算: 経常+27%、純利益+89%。AI基板需要急拡大。26〜28年度に約5,000億円の設備投資計画。
> → 上流の基板メーカーが好調なら、基板に穴を開けるドリルメーカー（ユニオンツール）も好調のはず。

サプライチェーン上の上流・下流関係にある企業ペアで、先に決算発表した企業が好業績なら、後から決算発表する企業も好業績である蓋然性が高い。後攻企業を決算前に買うことで、決算またぎのアルファを狙う。

## 投資アイディア
サプライチェーン上流下流ペアを網羅的に収集し、先行企業の決算が好業績だった場合に後攻企業を決算前に買い、決算反応で利益を得る。「ピックアンドショベル」的連想を体系化・自動化する戦略。

## 因果連鎖
1. 先行企業の業績好調 → 同一サプライチェーン上の需要/供給が好調 → 後攻企業の業績も好調の蓋然性 → 決算発表で株価に反映
2. （逆方向）先行企業が業績悪化 → 後攻企業も悪化の蓋然性 → ショートまたは回避

## 時間軸（仮説）
- 先行決算発表日 → 後攻決算発表日の間（通常数日〜数週間）
- 決算シーズン（1月末〜2月中旬、4月末〜5月中旬、7月末〜8月中旬、10月末〜11月中旬）に集中
- エントリー: 先行企業決算発表翌日〜後攻企業決算発表当日
- エグジット: 後攻企業決算発表翌日

## 対象（粗い絞り込み）
- サプライチェーン上流下流のペア全般（東証上場企業）
- 既知ペア例:
  - イビデン(4062) → ユニオンツール(6278): 半導体パッケージ基板 → PCBドリル
  - 任天堂(7974) → メガチップス(6875): ゲーム機 → カスタムLSI
  - （要収集: 自動車・半導体・素材・化学等の主要サプライチェーン）

## 分析の方向性（粗いイメージ）
### Phase 1: ペア収集（これがカギ）
- 有価証券報告書の「主要な顧客」「仕入先」情報から自動抽出
- EDINET XBRLから取引先情報をパース
- 業界レポート・アナリストレポートからの手動収集
- 株価相関クラスタリングからの候補発見（011系の手法流用）
- Web検索/LLMによるサプライチェーンマッピング

### Phase 2: 決算日ペアリング
- J-Quants `/fins/announcement` で決算発表日を取得
- ペアの決算発表日差（先行-後攻）を計算
- 十分なギャップ（2営業日以上）があるペアをフィルタ

### Phase 3: バックテスト
- 先行企業の決算サプライズ（実績 vs コンセンサス）を計算
- サプライズが正の場合に後攻企業を買い、決算発表翌日に売り
- CARイベント分析で有意性検証

## 必要データ（想定）
- **決算発表日**: J-Quants `/fins/announcement` or BQ `fins_announcement`
- **決算実績・予想**: J-Quants `/fins/statements` or BQ
- **コンセンサス予想**: BQ `consensus` テーブル（QUICK）
- **株価日次**: BQ `stock_prices` or J-Quants
- **サプライチェーンペア**: 要収集（最重要・最難関）
  - EDINET有価証券報告書「主要な販売先」
  - TDnet適時開示（取引先変更等）
  - Web検索・業界情報

## メモ
- 「サンバイオ云々は関係なし」（元ツイートのサンバイオ部分はノイズ）
- 収集の自動化度合いが戦略の成否を決める
- ペア数が少ないとサンプル不足で統計検定が効かない → 幅広いセクターで収集必要
- 同業他社ペア（例: トヨタ好決算→日産買い）とは異なる。上流下流の異業種ペアが本質

## データ管理の設計方針

### 2層構造: 直接取引ペア vs 連想ペア

| | 直接取引ペア | 連想ペア |
|---|---|---|
| 定義 | A社がB社に売上10%超を依存（法定開示あり） | A好決算→B買い（需要ドライバー共有の推論） |
| 例 | 任天堂→メガチップス（売上50%） | イビデン好決算→ユニオンツール買い |
| 性質 | ファクト（取引関係） | 推論（共通需要・隣接関係） |
| 管理先 | **本MD**（種データ・参考情報として十分） | **CSV/BQ**（バックテスト・シグナル生成に直接使う） |
| 拡充方法 | EDINET有報「主要な販売先」、バフェットコード等 | Web調査・ツイート・LLM・裁量判断 + 直接取引ペアからの派生 |
| スケール | 少数（有報開示は10%超のみ） | 数十〜数百（実際にトレードに使うペア） |

### ペアデータの調達手段

| 手段 | カバレッジ | 精度 | コスト | 自動化 |
|---|---|---|---|---|
| EDINET有報「主要な販売先」 | 売上10%超のペアのみ | ◎ 法定開示 | 低 | XBRL or Gemini抽出 |
| 株探テーマページ | 主要グループ数十テーマ | ○ | 低 | スクレイピング |
| バフェットコード関連企業 | 上場企業全般 | ○ | API次第 | API |
| LLM一括生成 | 広い | △ 幻覚リスク | 低 | 即座 |
| FactSet Supply Chain DB | 53,000社 | ◎ | 高額（個人不可） | — |

- EDINET有報は直接取引ペア（ファクト）の最良ソース。連想ペアの種になる（→ §EDINET調査結果 参照）
- 株探テーマ・バフェットコードは連想ペア候補の発見に有用
- LLMは初期リスト作成に使えるが裏取り必須
- FactSetは個人では使えないが、論文の再現実装時にはEDINET有報で代替可能

### 連想ペアの3パターン

1. **共通需要ドライバー型**: A好業績 = 需要X好調 → 同じ需要Xに乗るBも好調のはず
   - 例: イビデン(基板製造)好調 → ユニオンツール(基板用ドリル)も好調
   - サプライチェーン上の直接取引は不要。同じマクロ需要を共有していればよい

2. **直接取引型**: 顧客A好業績 → サプライヤーBの受注も好調のはず
   - 例: 任天堂好決算 → メガチップス(売上50%が任天堂)も好決算
   - 直接取引ペアCSVから機械的に生成可能

3. **設備投資波及型**: A社が大型投資を発表 → 装置・設備を納入するBに恩恵
   - 例: TSMC設備投資増 → 東京エレクトロン受注増
   - 決算数値だけでなくガイダンス・CAPEX計画が先行指標

### 本MDのペアマップの位置づけ

上記セクションA〜Hのペアマップは**直接取引ペアと連想ペアが混在している現状**。
将来的にはこう分離する:
- **直接取引ペア（ファクト）** → 本MDに参考情報として残す（数が少なく種データとしての役割）
- **連想ペア（トレードシグナル）** → `data/master/association_pairs.csv` に移行（BT結果・依存度・決算日差を列追加して拡張）
- **パターン2（直接取引→連想）** → 直接取引ファクトから機械的に連想ペアCSVへ変換

## EDINET有報「主要な販売先」調査結果（2026-05-13実施）

### データソース

`gmailpj-357912.STOCK.ir_documents_enhanced`
- 2025年度有報: **3,619社**カバー（ほぼ全上場企業）
- チャンク化テキスト + メタデータ（security_code, filer_name, section_category, submission_date）

### ヒット件数

| クエリ条件 | チャンク数 |
|---|---|
| `chunk_text LIKE '%主要な販売先%'` | 440 |
| `chunk_text LIKE '%販売実績%' AND ('100分の10' OR '10％')` | 1,226 |

1,226件は「販売実績」セクションで10%基準に言及するチャンク。「該当なし」と「具体的販売先名+割合あり」が混在。

### テキスト構造の例

**構造化あり（理想）** — スーパーツール(5990):
```
顧客の名称 / 売上高（千円） / 売上高割合（％）
トラスコ中山㈱  1,561,788  29.8
㈱山善          1,021,998  19.5
```

**自由記述** — ミタチ産業(3321):
```
当社グループの主要な販売先として、株式会社デンソー等がありますが、
これらの販売先への依存度が高いため...
```

**該当なし（除外対象）**:
```
主要な販売先については、総販売実績に対する割合が100分の10以上に
該当する相手がいないため、記載を省略しております。
```

### 抽出方針

1. 1,226件から「該当なし/省略」を除外 → 具体的販売先名ありのチャンクを絞り込み
2. 構造化抽出: `{supplier_code, supplier_name, customer_name, revenue_pct}` に変換
3. customer_nameを銘柄コードに名寄せ（`stock_code_list` マスタとJOIN）
4. → `data/master/supply_chain.csv` として保存（サプライチェーンファクト。連想ペアではない）

## スクリーニング実装

`scripts/screen_earnings_cascade.py` — リアルタイム決算カスケードスクリーニング。

**判定ロジック**:
1. **発表済み判定**: `V_LATEST_DISCLOSURE` で `DISCLOSED_DATE >= season_start` かつ `LATEST_TYPE IS NOT NULL` → 発表済み（期種別不問）
2. **Leader条件**: 発表済み ＋ 翌日株価リターン ≥ 閾値（デフォルト3%）
3. **Follower条件**: 未発表（fin_summaryにレコードなし）
4. **出力**: leader→followerペアをleaderリターン降順で出力

**注意事項**:
- fin_summaryが100%正（J-Quantsロード遅延あるが正確）
- EARNINGS_DISCLOSURE_CALENDARの予定日(S)は参考情報のみ
- 12月期企業の1Q等も「発表済み」扱い（期種別フィルタしない）
- **決算シーズン跨ぎ**: 5月決算→6月決算のように月をまたぐ連鎖もあり得る。`season_start` を単月で切ると漏れる。シーズン境界は柔軟に設計すること（例: 4月末〜6月中旬を一括で「1Qシーズン」扱い）
