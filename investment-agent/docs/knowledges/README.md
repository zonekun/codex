# 知見蓄積 (docs/knowledges/)

分析によって得られた知見を md ファイルとして蓄積するディレクトリ。
Claude Code が新しい分析を行う際は、ワークスペース全体をスキャンせず、
**このディレクトリ内を優先的にスキャンする**。

## カテゴリ

> **`analysis/` カテゴリは必須記載項目あり** → 後述「analysis カテゴリの必須項目」参照

| ディレクトリ | 内容 | 対象ステータス |
|-------------|------|--------------|
| `analysis/` | 投資アイデアの分析・バックテスト結果（成功も失敗も） | NEW〜BACKTEST_FAIL まで |
| `data/` | 取得済みデータの情報、定期取得ジョブの設定・仕様 | — |
| `tools/` | 作成したPythonパッケージ・スクリプトの**使用方法・仕様**（実装の記録） | — |
| `api/` | 外部APIの仕様・制約・認証方法 | — |
| `strategies/` | **BACKTEST_PASSを経て運用候補になった戦略の設計・パラメータ** | BACKTEST_PASS以降のみ |

### `analysis/` vs `strategies/` の使い分け【重要】

```
アイデア検討中・バックテスト中・BACKTEST_FAIL
  → analysis/ に記録（失敗も貴重な知見として蓄積）

BACKTEST_PASS → CANDIDATE（デモトレード中）→ TRADER（本運用）→ RETIRED
  → strategies/ に記録（実際に使える・使った戦略の設計を管理）
```

| 記録内容の例 | 置き場所 |
|-------------|---------|
| 野菜価格分析: BACKTEST_FAIL（アルファなし）| `analysis/` ✅ |
| 逆日歩ランク分析: ANALYZED_PASS, バックテスト中 | `analysis/` ✅ |
| 逆日歩ロング戦略: BACKTEST_PASS, デモ運用中 | `strategies/` ✅ |
| ~~野菜価格ショート戦略~~ | ~~`strategies/`~~ ❌（BACKTEST_FAILのため） |

> **BACKTEST_FAILの案件を `strategies/` に置かない**。
> 有効性が確認できていない戦略を戦略知見として管理すると、
> 将来誤って参照・実装してしまうリスクがある。

## `docs/knowledges/tools/` vs `skills/` の使い分け

紛らわしいが、**性格が異なる**。

| | `skills/` | `docs/knowledges/tools/` |
|---|---|---|
| **性格** | 手順書・実行ガイド | 知見・仕様の記録 |
| **使われ方** | タスク開始時に能動的に呼び出す | 疑問が生じたときに参照する |
| **主語** | 「Claudeがこの手順でやれ」 | 「こういう経験・仕様がある」 |
| **例** | `skills/planning.md`（計画の立て方）<br>`skills/correlation_analysis.md`（アルゴリズム選択フロー） | `tools/002_timeseries_correlation_algorithm.md`（野菜分析での実装記録）<br>`tools/001_convert_bond_history.md`（スクリプト仕様） |

### 判断基準

> 「次の分析を始めるときに、このファイルを開いて手順に沿って作業するか？」
> → **YES** → `skills/`
> → **NO（過去の記録を参照するだけ）** → `docs/knowledges/tools/`

典型的に `skills/` に入るもの:
- 分析手法の選択フロー（どのアルゴリズムを使うか）
- データ取得の操作手順（どのAPIをどう叩くか）
- 定型作業の実行ガイド（計画作成、レポート生成 等）

典型的に `docs/knowledges/tools/` に入るもの:
- 特定スクリプトの引数・出力仕様
- 過去の分析で使ったライブラリの挙動メモ
- 実装上のハマりポイント・バグ修正記録

## analysis カテゴリの必須記載項目

`analysis/` 配下のファイルは、分析フェーズごとに以下を**必ず**記載する。
テンプレート: `src/knowledge/templates/analysis.md`

**なぜ必須か**: 記載がないと分析がブラックボックスになり、結果の良し悪しを判断できない。
（実例: 野菜価格分析002の初期版でアルゴリズム選択理由・前処理詳細が不足していた）

| 必須セクション | 記載すべき内容 |
|-------------|-------------|
| **使用データ** | データソース名・対象銘柄/セクター・粒度（日次/週次/月次/四半期）・使用した項目（列名）・期間・件数・前処理内容 |
| **使用アルゴリズム** | アルゴリズム名・**選択理由**（なぜ他の手法でなくこれか）|
| **結果** | p値・相関係数・効果量等を銘柄別・ラグ別に表形式で記載 |
| **判定と理由** | ANALYZED_PASS/FAILの根拠を数値で示す |

フェーズが複数ある場合（フェーズ1→フェーズ2→バックテスト等）は、
**各フェーズにこの4項目を繰り返す**。

## 知見ファイルを追加・更新したときの必須作業

`docs/knowledges/` 配下にファイルを追加または更新した場合、
以下を **セットで** 行うこと。

```
① docs/knowledges/ にファイルを追加・更新
    ↓
② CLAUDE.md の「タスク別必読ファイル」一覧を確認
   → 新しいファイルが特定タスクに対応するなら行を追加
   → 既存ファイルの内容が変わったなら説明を更新
    ↓
③ ①②をまとめて git commit
```

**「タスク別必読ファイル」一覧の場所:**
`CLAUDE.md` → `6. 知見蓄積（docs/knowledges/）` セクション内

**追加が必要なケース（例）:**
| 追加した知見ファイル | CLAUDE.md への追記内容 |
|--------------------|----------------------|
| `api/003_edinet_api.md` | EDINET APIを使うタスク → このファイルを読め |
| `tools/003_backtest_engine.md` | バックテストエンジンを使うタスク → このファイルを読め |
| `strategies/001_xxx.md` | 特定戦略の実装・運用タスク → このファイルを読め |

**追加が不要なケース:**
- `analysis/` への追記（分析結果の蓄積は都度スキャンするため個別指定不要）
- 既存ファイルへの小規模な追記（タスク対応関係が変わらない場合）

## ファイル命名規則
```
<category>/NNN_<slug>.md
```
例: `analysis/001_gyakuhibu_buyer_strategy.md`

## ステータス
各ファイルのヘッダに記載:
- **有効**: 現在も参照すべき知見
- **要検証**: 再検証が必要
- **廃止**: 古い・不要になった知見（削除対象）

## 操作コマンド（Claude Code に指示）
```
知見一覧を見せてください
分析知見（analysis）を一覧してください
docs/knowledges/analysis/003_xxx.md を削除してください
廃止ステータスの知見をすべて削除してください
```

## 注意
- **データストアのキャッシュ（data/cache/）は当ディレクトリには保管しない**
- ここに保管するのは「人間とClaudeが読んで理解できる知見」のみ
