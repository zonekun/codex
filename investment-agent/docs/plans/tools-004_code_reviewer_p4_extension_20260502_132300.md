## 背景・動機

### 問題

現在のレビュー体制に以下の空白がある:

| レビュー対象 | 現在の担当 | レビュー内容 |
|---|---|---|
| ソースコード | code-reviewer パターン 1/3 | ロジック・設計・セキュリティ |
| 既存コード改修プランMD | code-reviewer パターン 2 | 改修方針の妥当性・副作用・抜け漏れ |
| Markdown の AI可読性 | md-reviewer パターン 1/2/3 | AI誤読リスク・文書構成品質 |
| **新規開発の計画MD** | **誰もいない** | **設計妥当性・リスク・抜け漏れ・実現可能性** |

「この計画の設計方針は妥当か？リスクはないか？抜け漏れはないか？」を評価する役割が空白。

### 選択肢の検討結果（structure-optimizer 分析）

| 評価軸 | A: code-reviewer拡張 | B: md-reviewer拡張 | C: plan-reviewer新設 |
|---|---|---|---|
| トークン効率 | +30〜40行 | +80〜100行 | +150〜200行 |
| AI判断安定性 | 高 | 低（二重責務） | 最高（単一責務） |
| 到達可能性 | 高（既存導線の延長） | 中（認知的不整合） | 低（新規導線3箇所） |
| スキル数 | 3維持 | 3維持 | 4に増加 |

→ **選択肢A: code-reviewer パターン4 新設** を採用。

### 根拠

- パターン2の評価フレーム（妥当性/副作用/抜け漏れ/新規リスク）を新規計画にも転用可能
- 「コードが書かれる前に計画を検証する」という思考プロセスはパターン2と共通
- スキル数3つ維持（ユーザー意向に適合）

### 追加箇所: `skills/code-reviewer.md`

#### 1a. §起動パターン に「パターン4」を追加

パターン3（L149〜）の直後に挿入:

```markdown
### パターン 4: 新規開発・設計計画のレビュー

**入力**:
- **計画MD**（`docs/plans/*.md` のパス）— `skills/planning.md` §テンプレート に準拠した汎用テンプレート形式
- 補足情報（関連する既存システム・知見MD等）

**目的**: ソースコード実装前の段階で、計画の**内容的妥当性**（設計方針・リスク・抜け漏れ・実現可能性）をレビューする。MD のAI可読性は md-reviewer の責務であり、本パターンでは評価しない。

**パターン2との判定基準**:
- `_template_refactor.md` フォーマット（P0/P1/P2 + 7フィールド構成）→ **パターン2**
- 汎用テンプレート（目的/背景/作業ステップ/成果物/完了条件）→ **パターン4**
- 迷う場合: 「対象ファイル」に既存コードのパスがあるか → あり=パターン2、なし=パターン4

**出力**（2段階）:

**① docs/reviews/ にレビュー本体を作成**:
- `docs/reviews/NNN_cr_<slug>.md` を新規作成（採番ルール・出力テンプレートはパターン1と同一）
- **レビュー本体の正本はこちら**

**② 計画MDにポインタを追記**:
- 提示された計画MDの末尾にレビューMDへのポインタを追記:

  ```markdown
  ---

  ## レビュー追記: YYYY-MM-DD HH:MM JST — code-reviewer

  → `docs/reviews/NNN_cr_<slug>.md`
  ```

**パターン 4 固有の評価項目**:

1. **目的・スコープの明確性** — 計画の目的が1-2文で言い切れているか。非スコープが明示されているか
2. **技術選定の妥当性** — 選択した技術・アーキテクチャ・データソースが目的に対して適切か。過剰設計や不足がないか
3. **既存システムとの統合** — 既存のコード・BQテーブル・GCSパス・Cloud Run Job・スケジューラとの接合ポイントが洗い出されているか。既存機能との重複・競合がないか
4. **段階的検証計画** — いきなり本番でなく、smoke test → dev → prod の段階が設計されているか。各段階の成功基準が具体的か
5. **リスク・コスト** — GCP課金・API制限・ディスク容量・処理時間の見積もりがあるか。失敗時の撤退基準が定義されているか
6. **完了条件の検証可能性** — 「完了条件」が主観的でなく、具体的に検証できる条件になっているか
7. **データカタログ整合** — 使用するデータが `data_catalog.md` に存在するか。新規データの場合、カタログ追加が計画に含まれているか
8. **抜け漏れ（横展開）** — 類似の既存機能・パイプラインとの整合性。計画が触れていない関連ファイル（設定YAML・Dockerfile・Workflows・監視クエリ等）への必要変更
```

## 変更2: md-reviewer 責務境界の明文化

### 追加箇所: `skills/md-reviewer.md`

§既存 code-reviewer との関係（L622〜）の直後に 1 段落追加:

```markdown
### 計画MDのレビュー分担

計画MD（`docs/plans/*.md`）は2つのレビュー軸を持つ:

- **AI可読性**（md-reviewer の責務）: 計画MDをAIが誤読しないか。文書構成・曖昧表現・指示優先順位の評価
- **内容的妥当性**（code-reviewer パターン4 の責務）: 計画の設計方針・リスク・抜け漏れ・実現可能性の評価

md-reviewer が計画MDを受けた場合は AI可読性のみを評価し、設計内容の妥当性判断には踏み込まない。設計レビューが必要な場合は code-reviewer パターン4 への引き継ぎを提案する。
```
