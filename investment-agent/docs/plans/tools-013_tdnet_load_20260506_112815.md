## 指摘項目

### P0-1. ページマーカー文字列が `_MIN_TEXT_LEN` 閾値判定をすり抜ける 🚨

**症状**: PyPDF2 がテキストを 0 文字しか抽出できない PDF でも、`[PAGE 1]\n\n\n[PAGE 2]\n\n...` のマーカー文字列だけで `len(text)` が 120〜240 になり `_MIN_TEXT_LEN = 50` を超える。結果、pdfminer フォールバックも Gemini Vision OCR フォールバックも発動せず、ページマーカーだけの空テキストが BQ に格納される。

**該当箇所（6箇所）**:

**(a)** `scripts/tdnet_load_parallel.py:L621-L631` / `phase1_scan_and_extract()` 内（load モード）

```python:L621-L631
        text, page_count = _extract_text_pypdf2(pdf_bytes)
        extract_method = "pypdf2"

        if len(text) < _MIN_TEXT_LEN:                    # ← マーカー込みで判定
            text_pm = _extract_text_pdfminer(pdf_bytes)
            if len(text_pm) >= _MIN_TEXT_LEN:
                text = text_pm
                extract_method = "pdfminer"
                logger.log(f"  フォールバック抽出 (pdfminer) 成功: {blob.name}")

        needs_vision = len(text) < _MIN_TEXT_LEN         # ← マーカー込みで判定
```

**(b)** `scripts/tdnet_load_parallel.py:L1634-L1645` / `phase1_extract_for_docs()` 内（ai-prepare モード）

```python:L1634-L1645
        text, page_count = _extract_text_pypdf2(pdf_bytes)
        doc.extract_method = "pypdf2"
        if len(text) < _MIN_TEXT_LEN:                    # ← マーカー込みで判定
            text_pm = _extract_text_pdfminer(pdf_bytes)
            if len(text_pm) >= _MIN_TEXT_LEN:
                text = text_pm
                doc.extract_method = "pdfminer"

        doc.text = text
        if page_count:
            doc.page_count = page_count
        doc.needs_vision = len(text) < _MIN_TEXT_LEN     # ← マーカー込みで判定
```

**根本原因**: `_extract_text_pypdf2()` (L387-L404) が各ページに `f"[PAGE {idx}]\n{normalized}"` を付加するため、`page.extract_text()` が空文字を返しても結合後のテキスト長がマーカー分だけ膨らむ。`_MIN_TEXT_LEN = 50` は「実コンテンツが十分か」を判定する閾値だが、マーカー文字列もカウントしてしまい意味をなさなくなった。004 には直接該当するアンチパターンは無いが、「前処理で付加したメタデータが後段の品質判定を汚染する」構造。

**修正方針**: マーカーを除外した「実コンテンツ長」で判定する関数を導入。`src/llm/page_aware_text.py` に既存の `PAGE_MARKER_PATTERN` を活用。

```python
# before（6箇所共通）
if len(text) < _MIN_TEXT_LEN:
if len(text_pm) >= _MIN_TEXT_LEN:

# after
def _content_length(text: str) -> int:
    """ページマーカーと空白を除いた実コンテンツの文字数を返す。"""
    from src.llm.page_aware_text import PAGE_MARKER_PATTERN
    stripped = PAGE_MARKER_PATTERN.sub('', text)
    return len(stripped.split())  # 非空白トークン数（改行のみで閾値超えを防止）

# 6箇所すべてで:
if _content_length(text) < _MIN_TEXT_LEN:
if _content_length(text_pm) >= _MIN_TEXT_LEN:
```

`_content_length()` は `_MIN_TEXT_LEN` 定義の直後（L358 付近）に配置。import は module-level に移動（`src.llm.page_aware_text` は現在未 import のため新規追加）。

**改行残留対策（レビュー #1 改善提案）**: `.strip()` ではなく `.split()` で非空白トークン数を返す。50ページ超PDFでもマーカー除去後の改行のみで閾値を超えない。実コンテンツがあれば数百〜数万トークンになるため `_MIN_TEXT_LEN = 50` との比較は問題なし。

**呼び出し側への波及**:
- `scripts/tdnet_load_parallel.py:L624` — `if len(text) < _MIN_TEXT_LEN:` → `if _content_length(text) < _MIN_TEXT_LEN:`
- `scripts/tdnet_load_parallel.py:L626` — `if len(text_pm) >= _MIN_TEXT_LEN:` → `if _content_length(text_pm) >= _MIN_TEXT_LEN:`（**レビュー #1 重大指摘: pdfminer結果もマーカー含む**）
- `scripts/tdnet_load_parallel.py:L631` — `needs_vision = len(text) < _MIN_TEXT_LEN` → `needs_vision = _content_length(text) < _MIN_TEXT_LEN`
- `scripts/tdnet_load_parallel.py:L1636` — 同 L624
- `scripts/tdnet_load_parallel.py:L1638` — 同 L626（**レビュー #1 重大指摘**）
- `scripts/tdnet_load_parallel.py:L1645` — 同 L631
- `scripts/tdnet_load_parallel.py:L804` — Phase 2 Vision 結果の `if len(text) >= _MIN_TEXT_LEN:` — Vision 結果にはマーカーが無いため変更不要（コメントで理由を明記）

**検証**: 6823（リオン）の直近 FY 決算短信 PDF（GCS: `tdnet/6823/20260428_...pdf`）をローカルで `_extract_text_pypdf2()` → `_content_length()` → pdfminer フォールバック発動を確認。pdfminer でもテキストが取れない場合は `needs_vision = True` になることも確認。

**ロールバック**: コード変更は `git revert` で戻せる。BQ データへの影響は無い（既存データは変更しない）。

### P1-1. 既存抽出失敗データのリカバリ ⚠️

**症状**: BQ `TDNET_DOCUMENTS_ENHANCED` に TEXT_LENGTH < 300 かつ CHUNK_TEXT がページマーカーのみの DOC が約 2,100 件存在。決算短信 453 件、決算説明資料 212 件を含む。

**該当**: BQ テーブル `gmailpj-357912.STOCK.TDNET_DOCUMENTS_ENHANCED`

```sql
-- 対象件数の確認
SELECT MAIN_CATEGORY, COUNT(DISTINCT DOC_ID) as cnt
FROM `gmailpj-357912.STOCK.TDNET_DOCUMENTS_ENHANCED`
WHERE TEXT_LENGTH < 300
GROUP BY 1
ORDER BY cnt DESC
```

**根本原因**: P0-1 のバグにより、過去のパイプライン実行でフォールバックが発動せずマーカーのみのテキストが格納された。

**修正方針（リカバリ手順）**:

P0-1 のコード修正を先にデプロイした上で、以下の手順でリカバリする。

```
Step 1: 対象 DOC_ID リストを BQ から抽出
  → SELECT DISTINCT DOC_ID, TICKER, SUBMISSION_DATE, FILE_NAME
    FROM TDNET_DOCUMENTS_ENHANCED
    WHERE TEXT_LENGTH < 300

Step 2: 対象 PDF を GCS から再取得し、修正済みコードで再抽出
  → tdnet_load_parallel.py に --reextract モード追加
     または recovery.py の extract_pdf_info() 相当のスタンドアロンスクリプト

Step 3: 再抽出結果で BQ 行を UPDATE（DELETE → INSERT）
  → 既存の冪等パターン（DOC_ID 単位 DELETE → INSERT）に従う

Step 4: リカバリ結果を確認
  → 再抽出後も TEXT_LENGTH < 300 のものは本当にテキスト抽出不可能な PDF
```

具体的なリカバリスクリプト設計:

```python
# before: リカバリ手段なし

# after: tmp_reextract_failed_docs.py（一時スクリプト）
# 1. BQ から TEXT_LENGTH < 300 の DOC_ID + FILE_NAME を取得
# 2. GCS から PDF をダウンロード
# 3. 修正済み _extract_text_pypdf2 → _content_length 判定 → pdfminer → Gemini Vision
# 4. 成功分を BQ に DELETE → INSERT（既存チャンクも再生成）
# 5. --dry-run で10件目視確認 → 本実行
```

**呼び出し側への波及**: 無し（スタンドアロンのリカバリスクリプト）

**並列度・API課金概算（レビュー #3 改善提案）**:

- **並列度**: GCS DL + pdfminer テキスト抽出は `ThreadPoolExecutor(max_workers=10)` で並列化。Vision API 対象は Batch API でまとめて投入（レート制限回避）
- **Vision API 課金概算**:
  - 対象 2,077 DOC のうち、pdfminer で成功する分は費用ゼロ（ローカル処理）
  - Vision 必要分の推定: 30〜50%（620〜1,040件）
  - Gemini 2.5 Flash: 入力 $0.10/1Mトークン、出力 $0.40/1Mトークン
  - 平均 15ページ × 300トークン/ページ = 4,500 入力トークン/DOC、出力 ~3,000トークン/DOC
  - **楽観 $1.0 / 保守的 $1.7 / 最悪（全件Vision）$3.4**
  - Batch API 利用時は 50% OFF → 最悪 $1.7
- **スクリプト配置**: `tmp_reextract_failed_docs.py` として一時スクリプト（完了後削除）

**検証**:
1. `--dry-run --limit 10` で 10 件分の再抽出結果を目視確認（pdfminer/Vision で実テキストが取れているか）
2. 6823 と 5905 を含めて確認
3. dry-run 結果が妥当なら `--limit 100` → 全件と段階的に拡大

**ロールバック**: BQ の DELETE → INSERT は DOC_ID 単位。失敗時は該当 DOC_ID の行を DELETE して元の（マーカーのみの）データに戻す。ただし元データ自体がマーカーのみで価値がないため、実質的にロールバックの必要性は低い。

## 検証戦略

1. **smoke test**: ローカルで 6823 の PDF 1 件を対象に `_extract_text_pypdf2()` → `_content_length()` が 0 を返すこと、pdfminer フォールバックが発動することを確認
