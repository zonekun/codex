### 🚨 次回バックフィル投入前の改善事項

**Gemma runner TPU プリエンプション耐性が不十分**（2026-05-04 調査）

- **現状**: workflow に `retry: max_retries: 3`（デプロイ済み）。worker.py に GCS checkpoint（`gemma_CURRENT.jsonl` 逐次 append + 再開時 `done_ids` スキップ）あり
- **問題1 — リトライ回数不足**: max_retries: 3 では Q1 のように連続4回以上プリエンプトされると exhausted → FAILED。手動再投入が必要になった

- **被害**: 2021-H1 で Q1×4 execution + Q2a×2 execution = 計6回 FAILED。~13hロス
- **改善プラン**: `docs/plans/tools-013_gemma_preemption_resilience_20260504_212000.md`
- **優先度**: 2021-H2 投入前に対応推奨。ただし現状でも動作はする（手動介入が必要なだけ）

## 方針

### アーキテクチャ

2024/2025 バックフィルと同一の新アーキ（`tdnet-load-daily` + `ai_processing_flow` Workflows）を使用。

### AI 処理スコープ（⚠️ 重要）

| AI ステップ | 2023年以降 | **2022年以前** |
|-----------|-----------|-------------|
| Gemma TPU（カテゴリ分類） | ✅ 実行 | **✅ 実行** |
| Gemini Flash Batch（決算短信 受注判定） | ✅ 実行 | **❌ スキップ** |
| Embedding Batch（3カテゴリ） | ✅ 実行 | **✅ 実行** |

**理由**: 受注判定（Gemini Flash Batch）は 2023年以降のリアルタイム分析向け。2022年以前のデータに受注高/受注残高のサブカテゴリは不要。カテゴリ分類（Gemma）と Embedding は全年共通で必要。

### バッチ分割

- **投入単位**: 3ヶ月/回（既存バックフィル慣例準拠）
- **Load**: 6ヶ月一括（H1/H2）
- **AI 処理**: 3ヶ月単位（Q1-Q4）で Workflows 投入。**ただし 15K 超の 6Q は 2ヶ月+1ヶ月に分割**
- **同一 H 内の Q 並列**: monitor_backfill.py の TPU retry（max3回, 指数backoff）で安全に吸収（2024/2025 実績あり）。H 跨ぎ並列は非推奨
- **6時間制約**: 各 H の全処理（Load + AI）を 6 時間以内に完了させる
- **Gemini スキップの効果**: ai-finalize は Gemma TPU + Embedding のみ。Gemini Flash Batch 省略で **処理時間 ~30% 短縮**
- **年単位**: 1年 = Load 2回 + AI 4-6回（分割 Q 数に依存）
- **全体**: Load 12回 + AI **30回**（通常Q 18回 + 分割Q 6×2=12回）= **42 Workflows 実行**

## コード改修: ai-finalize Gemini スキップ

### 改修対象

`scripts/tdnet_load_parallel.py` — `run_tdnet_batch_etl()` 内の ai-finalize ブロック（L2287-L2294）

### 現状コード（L2287-L2294）

```python
# 2. Gemini Flash Batch（決算短信のみ、受注判定）
phase_gemini_tanshin_batch(docs, bucket, genai_client, logger)
_log_rss(logger, "after gemini batch")
logger.flush_to_gcs()

# 3. 受注判定を Gemma SUB にマージ（決算短信以外は Gemma 結果そのまま）
_merge_gemini_juchu(docs, logger)
logger.flush_to_gcs()
```

### 改修後コード

```python
# 2. Gemini Flash Batch（決算短信のみ、受注判定）
#    2022年以前は受注判定不要 → スキップ
skip_gemini = date_to < "20230101"
if skip_gemini:
    logger.log(f"Gemini Flash Batch: date_to={date_to} < 20230101 → スキップ（2022年以前バックフィル）")
else:
    phase_gemini_tanshin_batch(docs, bucket, genai_client, logger)
    _log_rss(logger, "after gemini batch")
    logger.flush_to_gcs()

# 3. 受注判定を Gemma SUB にマージ（決算短信以外は Gemma 結果そのまま）
#    Gemini スキップ時もマージは実行（Gemma 結果をそのまま確定させるため）
_merge_gemini_juchu(docs, logger)
logger.flush_to_gcs()
```

### 改修のポイント

1. **判定条件**: `date_to < "20230101"`（文字列比較で十分、YYYYMMDD フォーマット保証）
2. **`date_to` の可用性**: `run_tdnet_batch_etl()` の引数。ai-finalize ブロック内でスコープ内
3. **`_merge_gemini_juchu` は常に実行**: Gemini 未実行時も `doc.sub_categories` には `_apply_gemma_results`（L1853）で設定済みの Gemma 結果が残っている（空ではない）。マージ関数は `sub_categories_gemma`（バックアップ）を基準に受注判定の差分を適用するが、Gemini が動いていないため差分はゼロ → Gemma 結果がそのまま確定。正常動作
4. **環境変数による制御は不要**: date_from/date_to が Workflows から渡されるため、既存のフローで判定可能
5. **日次運用（2023年以降）への影響なし**: 日次 load は `date_to` が当日日付のため条件に該当しない

## 推定スケジュール

### 所要時間の見積（1H あたり、6時間以内必須）

2024年バックフィル実績（32,395 docs、H1+H2 計 ~7h）を基準に、Gemini スキップ分を補正。

| ステップ | 所要時間 | 根拠 |
|---------|---------|------|
| Load（6ヶ月一括） | ~1.5h | 206 docs/min × ~25-31K docs |
| AI Q（3ヶ月、Gemini なし） | ~1-1.5h | Gemma TPU + Embedding のみ。Gemini Batch 省略で通常 2-3h → **~1-1.5h** |
| AI 分割 Q（2ヶ月+1ヶ月） | ~1h + ~0.5h | 分割によりさらに短縮 |
| **H 合計（Load + Q 並列）** | **~3-4.5h** | Load 1.5h + max(Q1,Q2) 1.5h + stall margin 0.5h |
| **⚠️ 上限** | **6h** | 超過時は Workflows 停滞疑い → stall 検知で介入 |

> **Gemini なしの効果**: 通常 ai-finalize は Gemma TPU → Gemini Flash Batch → Embedding → BQ insert の 4 段階。2022年以前は Gemini Batch をスキップするため 3 段階のみ。2024年バックフィルの実測で Gemini Batch が全体の ~30% を占めていたことから、**1Q あたり ~1-1.5h** と見積もる。

### 投入タイミング

- **推奨**: 平日 15:00〜24:00 JST or 週末（TPU spot preemption 最小化）
- **1日に1年分（H1 + H2）**: 朝投入 → 日中完了。H1 ~3-4h → H2 ~3-4h = **~6-8h/年**
- **全6年**: **6-8日**（毎日1年分投入、週末含む）

## 注意事項

1. **`ALLOW_FULL_BACKFILL=1`**: 31日超の日付範囲は backfill ガードで拒否される。必須
2. **`--job-mode=load`**: 新アーキ必須引数。旧 `RUN_MODE=full` は使わない
3. **AI は 3ヶ月単位**: TPU preemption リスク抑制。load は 6ヶ月一括 OK
4. **同一 H 内の Q 並列は可**: gemma-runner の TPU 作成 retry（max3回, 指数backoff 60→600s）で競合を吸収。2024/2025 実績あり。H 跨ぎ並列（Q2+Q3 同時等）は非推奨
5. **既存データへの影響なし**: load は FILE_NAME dedup でスキップ、Workflows は AI_STATUS='pending' のみ処理
6. **日次ロードとの干渉**: load の dedup で安全だが、AI Scheduler が有効化された場合は 30日ガードで過去バックフィルは対象外
7. **2016年データ**: 既に 47,591 docs が BQ に存在（irbank 経由）。再ロード不要
