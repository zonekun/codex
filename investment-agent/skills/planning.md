# スキル: 作業計画（Plan mode 代替）

## 概要
作業前に計画を立て、`docs/plans/` にmdファイルとして保存する。
Claude Code 標準の Plan mode (`/plan`) は使用しない。
Plan mode は `~/.claude/plans/` に自動命名で保存されるため後から参照しづらいため。

## 重要
- **Plan mode (`/plan` コマンド) は絶対に使わないこと**
- 計画はすべて本スキルで `docs/plans/` に出力する

## 使い方
```
この作業の計画を立ててください: <作業内容>
```

---

## プラン分類（2026-04-20 改訂）

計画立案時に以下3段階で分類してから作成する。

| 分類 | 典型例 | 知見MD要否 | ファイル接頭辞 |
|---|---|---|---|
| **(a) 恒久知見型** | 新規機能実装・アーキ設計・新カテゴリ調査で将来参照される | **新規 or 既存追記 必須** | `<category>-<number>_` |
| **(b) 継続改修型** | 既存機能の改修・バックフィル運用・モデル更新 | **既存MDへの追記のみ**。新規MD不要 | `<category>-<number>_` |
| **(c) 一過性型** | ホットフィックス・一時調査・実験スパイク | **知見MD不要**。計画MDで完結、完了後archive/削除 | `ad-hoc_` |

### 分類判定の自問

1. **この作業で得られる知見は、3ヶ月後の自分・他者が参照したくなるか?**
   - YES → (a) or (b)
   - NO → (c)

2. **既存の関連知見MDがあるか?**
   - YES → (b)。既存 MD に追記
   - NO → (a)。ただし次の Step 3 で新規 MD 作成を厳しく判定
   - (c) なら不要

3. **新規 MD 作成の判定基準** (a のみ):
   - 新規スクリプトファイル（別 .py）
   - 新規 BQ テーブル（別名）
   - 新規データソース（新 API / 新スクレイピング対象）
   - 新規アルゴリズム（論文由来等）

**判定迷ったら (b) を選ぶ**。既存 MD への追記は剥がすのが容易だが、新規 MD を乱立すると整理困難。

## ファイル命名規則（2026-04-20 改訂）

```
docs/plans/<category>-<number>_<slug>_YYYYMMDD_HHMMSS.md      ← (a)(b)
docs/plans/ad-hoc_<slug>_YYYYMMDD_HHMMSS.md                    ← (c)
```

- `<category>`: `analysis` / `tools` / `api` / `data` / `strategies` （知見 MD フォルダ名と一致）
- `<number>`: 親知見 MD のゼロパディング番号（例: `007`, `081`, `006`）
- `<slug>`: 親知見 MD と **同一の slug**（スネークケース英語）
- `YYYYMMDD_HHMMSS`: 作成日時（JST、末尾）

### 例

```
docs/plans/tools-081_shareholder_composition_20260420_155621.md    (a) 新規知見MD付随
docs/plans/analysis-007_tob_ml_prediction_20260420_143200.md       (b) 既存知見MD追記付随
docs/plans/api-006_edinet_api_20260420_160000.md                   (b) 既存知見MD追記付随
docs/plans/ad-hoc_fix_xbrl_parse_bug_20260420_160000.md            (c) 一過性
```

**従来形式** (`YYYYMMDD_HHMMSS_<slug>.md`) は廃止。新規プランは新形式で作成する。既存の旧形式プランは遡及リネーム不要（完了時 archive 移動時にリネームで可）。

## 双方向リンク義務（2026-04-20 追加）

計画 (a)(b) は**必ず**関連知見 MD とバックリンクを相互に張る。

### 計画 → 知見MD（テンプレ既存）
計画 MD の「背景・動機」または「関連ファイル」欄で言及。

### 知見 MD → 計画MD（今回追加、必須）
知見 MD の冒頭メタ情報または末尾「関連」節に:
```markdown
**計画**: `docs/plans/<category>-<number>_<slug>_YYYYMMDD_HHMMSS.md`
```

### 検証
計画 MD 保存時に以下で 1件以上ヒットすることを確認:
```bash
grep -rl "plans/<category>-<number>_<slug>_" docs/
```
ヒット 0 件なら知見 MD 側のバックリンク張り忘れ。

### 違反パターン
- 計画 MD 作成したが関連知見 MD が未特定 → 発見困難化の元凶
- 知見 MD へのバックリンク追加忘れ → 計画が孤立
- テンプレの「関連ファイル」欄を空欄で提出

## 知見 MD 作成の原則（2026-04-20 改訂）

**原則**: 新規知見 MD 作成は**最終手段**。以下フローで既存 MD 追記を優先。

### 判定フローチャート

```
新しい作業・改修が発生
   ↓
Step 1: 対象物（スクリプト・テーブル・概念）は既存 MD に存在するか?
   → grep -rl "<対象物キーワード>" docs/knowledges/
   ├─ 1件でもヒット → 既存 MD に追記（新規 MD 禁止）
   └─ 0件ヒット → Step 2
   ↓
Step 2: 対象物は以下のいずれかに該当するか?
   - 新規スクリプトファイル（別 .py）
   - 新規 BQ テーブル（別名）
   - 新規データソース（新 API / 新スクレイピング対象）
   - 新規アルゴリズム（論文由来等）
   ├─ YES → 新規 MD 作成 OK
   └─ NO → 既存 MD のどれかに追記（どこに書くべきか再検討）
```

### 追記する節のパターン

| 作業種別 | 追記先セクション |
|---|---|
| 機能追加 | `(YYYY-MM-DD) 機能追加: XXX` 節 |
| 改修履歴 | `変更履歴` 節（時系列） |
| バックフィル | `バックフィル実績` 節 |
| バグ修正 | `既知バグ / 落とし穴` 節 |
| 運用ノウハウ | `運用` 節 |
| 個別事例 | `個別裏取り事例` 節 |

### 禁止パターン

- 似た話題で新規 MD を立てる（`analysis/001` の後に `analysis/002` を類似内容で作る）
- 同じスクリプトの改修で MD を分割
- 1回の改修で 2つ以上の新規 MD を作成
- 5秒以上「どこに書くか」迷う → それ自体が「既存 MD で十分」のシグナル

## 完了後の配置ルール（2026-04-20 追加）

| status | 配置先 |
|---|---|
| 未着手 / 進行中 | `docs/plans/<category>-<number>_<slug>_<timestamp>.md`（直下） |
| 完了 / 中止 | `docs/plans/archive/YYYYMM/<元ファイル名>.md` に移動 |

`docs/plans/` 直下は **active な計画のみ**、一目で現在進行中が把握可能。

移動時に知見 MD 側のバックリンクを `sed` で一括更新:
```bash
sed -i 's|docs/plans/\(tools-081_.*\)\.md|docs/plans/archive/202604/\1.md|g' docs/knowledges/tools/081_*.md
```

## 改修プラン / バグ修正指示書 MD フォーマット

**適用対象**: 既存コードの改修・バグ修正・リファクタリングを指示するプラン MD（`docs/plans/` 配下、code-reviewer スキルでレビュー対象）。

**クイックスタート**: ゼロから書かず `docs/plans/_template_refactor.md` をコピーして差分編集する。

プランは以下の構造で書く。**適合性の正式チェックはレビュアー（`skills/code-reviewer.md`）側の責務**だが、**作成者はテンプレート末尾の「提出前セルフチェック」を通す義務がある**。セルフチェック未済のプランはレビュー差戻し対象。頻出のフォーマット違反（アンチパターン対応表欠落・検証戦略不足・ロールバック手順欠落）は作成段階で防止する。

### 1. 冒頭メタ情報（必須）

```markdown
**作成日時**: YYYY-MM-DD HH:MM JST
**ステータス**: 未着手 / 進行中 / 完了 / 中止
**対象ファイル**: `scripts/foo/bar.py`（N 行、commit <hash> 時点）
**対象読者**: code-reviewer サブエージェント / 次セッション担当
**目的**: <1-2文で改修の主旨>
```

### 2. 前提サマリ（必須）

```markdown
## 前提サマリ

- 過去修正: <commit hash> で N 件修正済み（<内訳>）
- 残存: <このプランで扱う件数>
- 実機検証の有無: <dev / prod / 未検証>
```

### 3. 優先度分け（必須）

```markdown
## 優先度の定義

- **P0**: <ブロッカー条件。例: scheduler RESUME 前必須、データ破壊・セキュリティ・SLO 違反>
- **P1**: <次のリリース/バックフィル前に消化>
- **P2**: <余力で、ブロッカーではない>
```

### 4. 各項目の必須フィールド

```markdown
### P0-N. <短いタイトル> <絵文字>

**症状**: <何が起きるか。観測事実>

**該当**: `path/to/file.py:L1-L2` / 関数名
```L1-L5
<実コードの抜粋（3-10 行）>
```

**根本原因**: <なぜ発生するか。004/T-x/G-x のどのアンチパターンに該当するか>

**修正方針**: <変更の骨子。関数シグネチャ変更あれば明示>
```python
<修正後の最小 diff（before/after の両方）>
```

**呼び出し側への波及**: <影響を受ける行のリスト。無ければ「無し」と明示>
- `path/to/file.py:L100` — <どう変わるか>
- `path/to/file.py:L250` — <どう変わるか>

**検証**: <単体で挙動確認する手順。smoke test の入力条件も>

**ロールバック**: <失敗時の戻し方。無い場合は「取り消し不可」と明記>
```

### 5. アンチパターン対応表（必須）

```markdown
## 対応アンチパターン

| plan ID | 004 | T-x | G-x |
|---|---|---|---|
| P0-1 | B-1, B-3 | T-7 | G-2 |
| P0-2 | — | T-6 | — |
```

### 6. 検証戦略（必須）

```markdown
## 検証戦略

1. **smoke test**: <最小入力・期待結果>
2. **dev 実機**: <スケール・期間・コストガード（DOCS_LIMIT 等）>
3. **本番適用判断基準**: <smoke + dev 両方 PASS で初めて prod>
4. **回収手順**: <本番で問題発覚時の被害最小化手順>
```

### 7. 関連ドキュメント（必須）

- 関連知見 MD（`docs/knowledges/...`）
- 関連 commit（hash と 1 行要約）
- 関連 incident / 実機ログ（あれば）

### 8. 実装記録（実装後に記入）

実装完了時に以下を記入する。CLAUDE.md §4.3「プランMD更新」義務の具体的実現。

- **ステータス更新**: 冒頭メタ情報の `**ステータス**` を `完了` または `中止` に変更
- **実装 commit**: hash と日時
- **検証結果**: smoke test / dev 実機 / 本番適用の各結果
- **code-reviewer 推奨の採否**: 推奨ごとに 採用 / 不採用 / 次回対応 + 理由
- **実装後チェック**: テンプレート末尾のチェックリストを全消化
- **archive 移動**: 完了プランは `docs/plans/archive/YYYYMM/` に移動（§完了後の配置ルール）

### 書く時のポイント

- 基準 commit hash を冒頭に置く（行番号の根拠）
- 「既に〜がある」系の前提は実コードを Read で確認してから書く
- 呼び出し側への波及は該当行リストで書く（形容詞で済まさない）
- 修正方針は before/after の両方

### 呼び出し側からの参照

- プラン作成時は本節を読む（テンプレは `docs/plans/_template_refactor.md`）
- 汎用のバッチ・ETL アンチパターン集 (A-x〜F-x) は `docs/knowledges/tools/004_coding_conventions.md` を参照
- 適合性チェック（禁止パターン・抜け漏れ）は `skills/code-reviewer.md` 側で実施
- レビューで検出された不備は `docs/knowledges/tools/004-1_code_review_findings_log.md` に蓄積され、**傾向が見えた段階で本節のルールに反映**される（一件一件の即時対策はしない）
- 新規開発計画（汎用テンプレート形式）の内容妥当性レビューは `skills/code-reviewer.md` パターン4 で実施

## テンプレート

> **レビュー**: このテンプレートで作成した計画は `skills/code-reviewer.md` パターン4 で内容妥当性レビューが可能。AI可読性レビューは `skills/md-reviewer.md`。

以下のテンプレートで計画ファイルを生成する:

```markdown
# 作業計画: <タイトル>

**作成日時**: YYYY-MM-DD HH:MM (JST)
**ステータス**: 未着手 / 進行中 / 完了 / 中止
**分類**: (a) 恒久知見型 / (b) 継続改修型 / (c) 一過性型
**親知見 MD**: `docs/knowledges/<category>/<number>_<slug>.md`  ← (a)(b)のみ、(c)は「該当なし」
**関連アイディアID**: （あれば記載、なければ「-」）

## 目的
（何を達成したいか。1〜2文で簡潔に）

## 背景・動機
（なぜこの作業が必要か。関連する知見ファイルやアイディアがあればリンク）

## 作業ステップ
1. [ ] ステップ1の内容
2. [ ] ステップ2の内容
3. [ ] ステップ3の内容
...

## 必要データ
（data_catalog.md を参照して、使用するデータとその所在を列挙）

| データ | ストレージ層 | パス/テーブル |
|--------|------------|--------------|
| 例: 株価日次 | (c) ローカルCSV | data/csv/prices_daily.csv |

## 成果物
（何が出来上がるか: コード、分析レポート、知見ファイル、スキル等）

## 完了条件
（何をもって完了とするか。具体的かつ検証可能な条件）

## 見積もり
- 想定所要時間: （例: 2時間）
- 難易度: 低 / 中 / 高

## 振り返り（作業後に記入）
- 実際の所要時間:
- うまくいった点:
- 改善点:
- 得られた知見: （knowledge/ にも保存したか？）
```

## 計画作成時の必須チェックリスト

計画ファイル保存後、以下を**必ず**実行する:

1. **分類判定**: (a)(b)(c) のどれかを決める（計画 MD 冒頭に記載）
2. **関連知見 MD 特定**:
   - `docs/knowledges/{analysis,tools,api,data,strategies}/` 配下を grep
   - CLAUDE.md 索引から該当タスク行を起点に辿る
   - (c) の場合は「該当なし」を明記
3. **ファイル命名**: 新命名規則に従う（`<category>-<number>_<slug>_<timestamp>.md`）
4. **バックリンク (a)(b)のみ)**:
   - 親知見 MD に「**計画**: `docs/plans/...`」行を追加
   - `grep -rl "plans/<自計画ファイル名>" docs/` で 1件以上ヒットすることを確認
5. **知見 MD 作成判定** (a のみ):
   - Step 1-2 のフローを通過したか確認
   - 迷ったら (b) で既存 MD 追記に切り替える

---

## 計画の更新
- 作業開始時: ステータスを「進行中」に変更
- ステップ完了時: チェックボックスを `[x]` に更新
- 作業完了時: ステータスを「完了」に変更し、振り返りセクションを記入
  - その後 `docs/plans/archive/YYYYMM/` に移動
- 中止時: ステータスを「中止」に変更し、理由を記載。archive へ移動

> **改修プラン**の場合は上記に加えて §8「実装記録」のフィールドを全て記入し、実装後チェックを消化すること。
